# Ignium 架构设计原则

## 一句话定位

纯微内核(内核只含 IPC/调度/内存/能力)+ **用户态** OpenHarmony 兼容栈。

## 核心设计哲学

**微内核(机制最小化、策略外移)+ 能力(授权统一)。**"极致精简"是微内核的
自然推论,不是口号:内核只保留机制(分页 / 线程 / IPC / 能力),一切策略
(文件、驱动、网络、兼容层)都外移到**用户态服务进程**(uart_server 是第一个)。
授权只经**能力** —— 引用即授权,不可伪造,无 ambient authority;内核不设
fd/权限位这类独立的授权面。

### 与 Linux "一切皆文件"之辨

Linux 的"一切皆文件"统一的是**接口**(fd + VFS 命名空间),授权是另一套
体系(DAC 的 uid/gid/mode 位 + 后加的安全模块);Linux 的 "POSIX
capability"(`cap_*` 位)是**权限位**,不是对象能力。Ignium 不设 fd 命名
空间 —— 不是用"能力"替代"文件",而是把**授权本身做成唯一抽象**:做不了的
事不是"权限不够",而是你**根本没有指向该对象的引用**。两者不在同一维度。

### "一切皆能力"的落地进度(如实标注)

| 对象 | 状态 |
|---|---|
| 进程引用 `Cap::Proc` / 共享内存 `Cap::Shm`(可 dup / revoke) | ✅ 已能力化 |
| 服务发现:注册表 + `service_connect` 双向授予(号 10/11) | ✅ 已能力化 |
| 设备页:`map_device` 白名单 + 排他 claim(号 12) | ⏳ 半程(无 `Cap::Dev`、无特权校验,见 DEFERRED D31) |
| 物理页发配:内存服务 | ⏳ M3-3(`Cap::Page`) |
| 文件 / 命名空间 | ❌ 未能力化(随 ramfs 服务化设计) |

现状是**扁平定槽能力表**(每进程 `MAX_CAPS=8`),非 seL4 式 C-space;能力图
规模、全对象 revoke、spawn 能力引导为后续演进方向(见 ROADMAP / DEFERRED)。

## 分层

```
+------------------------------------------------------------------+
| OpenHarmony 应用 / POSIX 应用(用户态)                            |
+------------------------------------------------------------------+
| musl libc(鸿蒙版)| syscall 翻译层(OpenHarmony syscall -> IPC)    |
+------------------------------------------------------------------+
| 服务进程:fs_server / net_server(lwIP)/ uart_server / spawn_server |
+------------------------------------------------------------------+
| 内核(唯一特权层):IPC + 调度 + 内存 + 能力                         |
+------------------------------------------------------------------+
| 硬件(arch 层,riscv64 优先)                                       |
+------------------------------------------------------------------+
```

## 铁律

1. **内核只认 IPC 一种原语**。所有系统调用在用户态被翻译层转换成能力调用。
2. **兼容代码零进入内核**。OpenHarmony/POSIX 兼容全部在用户态库与进程。
3. **接口对齐 LiteOS-A,代码自研**。参考其 POSIX 子集与行为,不复制实现。
4. **架构隔离第一天做起**。`src/arch/<arch>/` 独立,通用代码不得出现架构分支。

## arch 层接口(通用代码的唯一依赖)

- `arch_mmu_map / arch_mmu_unmap / arch_tlb_flush`(M1 现状:Sv39
  实现位于顶层 `mmu.rs` 模块,接口形态见其模块头注释;x86_64 移植
  时下沉为 `arch::mmu` 并按本契约收敛,通用代码零改动)
- `arch_thread_switch`
- `arch_timer_init / arch_timer_set_next`
- `arch_irq_enable / arch_irq_disable`
- `arch_syscall_entry`(由通用代码分发)

x86_64 移植 = 重写这些接口,通用代码零改动。

## 能力模型(阶段 2 引入)

- 每个进程持有 capability 表(定槽,`MAX_CAPS=8`);IPC 目标必须是已授权 cap
- 小消息走寄存器;大消息走共享内存页映射
- 未授权调用返回错误,不 panic
- M3-2 落地:服务注册表 + `service_connect` 双向授予(号 10/11)、设备页
  `map_device` 白名单授予(号 12);哲学与"半程"状态见上文「核心设计哲学」

## 验证策略

- 每个里程碑:QEMU 集成测试(启动 -> 操作 -> 断言输出)进 CI
- 崩溃注入:任意服务可被杀且系统存活
- 性能基线记录在 docs/benchmarks.md(M1.5 已建基线,阶段 4 扩充)

## 已落地(M2 收官)

- **多核**:4 核 QEMU 全部 hart 进入调度,per-hart 陷阱栈(D7)+ 副核唤醒
  (D8)+ 控制台输出锁(D9)+ per-CPU 调度与线程亲和(D19,T3b)。
- **用户态 + 每进程地址空间**:U 模式线程 + ecall 系统调用(T1)、独立 satp
  根表与同 VA 隔离(T1.5)、用户栈守护页(D20)。
- **用户态异常恢复(D12)**:用户进程故障(页故障/非法指令等)→ 杀进程,
  系统存活、其余进程不受影响;杀进程 = 清 IPC 挂起 + 标记线程退出 +
  撤捐赠(双向)+ 切内核根表 + **进程销毁/页回收**(`process::destroy` /
  `mmu::destroy_root`,共享页能力先 revoke 防 double-free)。内核态故障
  仍停机(属内核 bug)。
- **IPC**:同步 IPC(寄存器消息 5 字 + 阻塞配对 + 简化能力表,未授权 →
  `-errno`)+ 优先级继承 PIP(T2b)+ 共享内存大消息/能力 revoke/dup(T3c)。

## 已知限制(截至 M3-2 收官)

> M3 入口已消项两条:内核线程栈守护页(M3 T3,见 docs/M3-DESIGN.md §9
> 风险表)与跨核 kill/TLB shootdown(M3 T2)。

- **带 proc 内核线程的栈守卫**:内核线程栈守护页仅在 `kernel_root` 生效;
  若内核线程带进程根表运行(当前均 proc=None,守卫生效),其守护页须在
  该进程根表也有效 —— 需跨根表拆分传播,见 M3-DESIGN 风险表,**延后**。
- **多核 IPC 跨核语义**:SCHED 全局锁保持(正确性优先,缩放留待 M4)。
- **slab 空页懒回收**:全空的**非 head** slab 页在下次任一档 grow 时被
  懒回收摘链归还 buddy(2026-08-30 完成);head 页保留作每档快复用缓存,故
  单槽 alloc→dealloc churn 不触发取/还页;若某档峰值后不再有 grow,空页
  暂留(有界,非无界泄漏)。
- **FDT 单内存 bank / 单 cells**(D24):真机多 bank 时按 DEFERRED 落地。
- **每进程单线程下自发自收会阻塞**(能力表授权语义下正常)。

## 风险与对策

| 风险 | 对策 |
|---|---|
| IPC 性能陷阱 | 同步 IPC + 寄存器消息起步,禁止过早引入异步/共享内存 |
| "从零"诱惑 | 先读透 seL4 架构论文与 rCore/zCore 代码,前 3 个月重文档轻代码 |
| 兼容范围失控 | 严格按 L1 -> L2 -> L3 顺序,每个级别有验收标准 |
