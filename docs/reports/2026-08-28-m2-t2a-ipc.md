# M2 T2a 报告:同步 IPC + 寄存器消息 + 简化能力表 + D22 woken 抢占

- 日期:2026-08-28
- 阶段:M2(微内核骨架)子任务 T2a(IPC 核心)
- 提交:`feat: M2 T2a - sync IPC (reg-message) + simplified capability + D22 woken preemption`

## 1. 摘要

M2 T2 按 `docs/M2-DESIGN.md` §9 分 T2a/T2b 两拍落地。本次完成 **T2a 核心**:

- **D22 woken 抢占**(优先级继承前置):`on_tick` 抢占路径原只认
  `frame_valid`(帧捕获)线程,被 `wake()` 唤醒的线程仅 `ctx_valid`(协作
  上下文)有效、`frame_valid=false`,不可被抢占 —— 可被同/更高优先级
  忙循环饿死。本次把被唤醒线程的 ctx 展开为 S 模式陷阱帧,并放宽抢占
  候选谓词,落地「woken 线程可抢占」。
- **同步 IPC**:`ipc_send(dst_cap, msg)` / `ipc_recv(src_cap)`,收发双方
  都未就绪则阻塞(先到者入 pending 队列),配对后唤醒;消息走寄存器
  (a1-a5,5 字),经新模块 `kernel/src/ipc.rs`。
- **简化能力表**:每进程 `MAX_CAPS=8` 个能力槽;IPC 目标必须是已授权 cap
  (槽 → 目标进程 pid),未授权 → 返回 `-errno`(`-EACCES`/`-EINVAL`)不阻塞、
  不 panic。
- **不做的部分**(T2b/T3,见 §5):优先级继承(PIP)、IPC 压力测试、共享
  内存大消息、revoke、进程销毁/页回收。

## 2. 发现明细

### 2.1 D22:woken 线程不可被抢占(缺陷,本次修复)

- **级别**:功能缺陷(饥饿,优先级继承前置依赖)。
- **位置**:`kernel/src/sched.rs` 抢占路径(`on_tick` / `pick_next(need_ctx=false)`)。
- **触发条件**:HIGH 线程经 `block_current` 阻塞(wake 前),LOW 线程忙循环
  数 tick 后 `wake(HIGH)`;抢占扫描只在 `frame_valid` 线程中选候选。
- **影响**:被唤醒的 HIGH 线程 `ctx_valid=true`、`frame_valid=false`,
  扫描看不到 → 只能等 LOW 主动 yield 才运行;若 LOW 永不 yield,HIGH
  被饿死。这是 PIP(优先级继承)落地的基础:IPC 阻塞唤醒后必须能立即
  抢占。

### 2.2 自检期间 main(idle)线程 SIE 恒为 0(开发实证)

- **级别**:测试环境陷阱(非内核缺陷)。
- **位置**:`sched::self_test` D22 第 6 项(阶段 2 纯自旋)。
- **触发条件**:引导期 main 以 idle 身份运行,每次 `yield_` 恢复引导时
  `irq_save` 保存的 SIE 值(0);自检期间从未显式开中断。
- **影响**:阶段 2 自旋期间定时器中断永不触发 → LOW 无法被调度 → 死等
  超时。**修复**:自旋前显式 `crate::arch::irq_enable()`。

### 2.3 RISC-V 12 位有符号立即数溢出(开发实证)

- **级别**:手写编码错误(引导测试用户程序)。
- **位置**:`tests.rs` boot_ipc_test S 程序完成标记 `0x888`。
- **触发条件**:`0x888`=2184 > 2047(12 位有符号立即数上限),`addi t1, x0,
  0x888` sign-extend 为负 → 完成标记读出 `0xfffff888`,轮询超时判负。
- **影响**:IPC 往返超时报错;误判为 IPC 逻辑缺陷(实为编码)。
- **修复**:完成标记改 `0x777`(12 位正立即数),并逐条核对所有 S/I 型
  立即数编码。

### 2.4 addi 目标寄存器编码算术错误(开发实证)

- **级别**:手写编码错误。
- **位置**:`tests.rs` boot_ipc_test 两处 `addi a1, x0, <imm>`。
- **触发条件**:`11<<7 | 0x13` 误算为 `0x583`(应为 `0x593`);`0x1110_0583`
  实际解码为 `lw a1, 0x111(x0)`(LOAD opcode 0x03)→ 加载地址 0x111 触发
  TRAP(scause=0xd,sepc=0x40000008,stval=0x111)。
- **修复**:两处改 `0x1110_0593`;借助陷阱 dump 的 sepc/stval 定位。

## 3. 修复明细

### 3.1 sched.rs:D22 woken 抢占

- `on_tick`/`pick_next(need_ctx=false)` 候选谓词从「仅 `frame_valid`」放宽为
  **`frame_valid || (ctx_valid && woken)`** —— 仅限「被唤醒的 ctx 线程」,
  保守直击饿死;yield 的线程维持现状(协作路径不变)。
- 新增 `expand_ctx_to_frame(id)`:把被唤醒线程的协作上下文(ctx.ra/sp/
  s0-s11)展开为 S 模式陷阱帧(sepc=ctx.ra、sstatus=SPIE|SPP=1、sp=ctx.sp、
  gp=内核 gp、s0-s11 填帧槽),置 `frame_valid=true, ctx_valid=false`。
  选中者若 `!frame_valid` 先展开,再经 `frame_restore` sret(SPP=1)回其
  内核恢复点 —— 与既有被抢占内核线程帧恢复一致,无新机制。
- D22 回归测试(第 6 项):HIGH 先 `block_current()`;LOW 忙循环 ~20 tick、
  第 3 tick 起 `wake(HIGH)`;**阶段 2 main 纯自旋不 yield**(排除协作路径
  选中 HIGH 的假阳性);断言 HIGH 记录 tick < LOW 完成 tick。banner:
  `M2 T2a: woken-thread preemption ok (D22)`。

### 3.2 sched.rs:阻塞与唤醒原语

- `block_user_from_trap(frame) -> !`(镜像 `exit_from_trap`):当前用户帧
  复制进 TCB(state=Blocked、frame_valid=true、ctx_valid=false、woken=false)
  → `set_sscratch_trap_top()` → pick_next(true) → do_switch;醒来经
  frame_restore sret 回用户态,结果已由配对方写入帧。
- `ipc_wake_with_msg(tid, msg: Option<&[usize]>)`:锁 SCHED,debug_assert
  state==Blocked,写帧 `a0=0`、`a1..a5=msg`(None 时仅状态)、`sepc+=4`,
  入队。**不置 woken**:IPC 唤醒由 pending 队列保证无丢失,避免陈旧标志。

### 3.3 ipc.rs(新模块):同步 IPC 状态机

- `MSG_WORDS=5`;`PendingSend { sender_tid, sender_pid, dst_pid, msg }`、
  `PendingRecv { recver_tid, recver_pid, src_pid }`,存于 `IpcState`
  (`SpinLock` + 两条 FIFO `VecDeque`)。
- `send(pid, slot, msg) -> Result<SendBlock, usize>`:①`cap_target` 校验失败
  返回 `-errno`(不登记、不阻塞);②查 `recvs` 中 `recver_pid==dst &&
  src_pid==pid` → 命中则 `ipc_wake_with_msg(recver_tid, msg)` + `Done`;
  ③未命中 push PendingSend → `NoPeer`(调用方随即阻塞)。
- `recv(pid, slot) -> Result<RecvBlock, usize>`:对称 —— 查 `sends` 中
  `sender_pid==src && dst_pid==pid`,命中则 `ipc_wake_with_msg(sender_tid,
  None)`(仅 ack)+ 返回消息;未命中 push PendingRecv → `NoPeer`。
- 错误码与 M2-DESIGN §4.1 一致(负数 `-errno`):`IPC_ERR_EINVAL=usize::MAX`
  (-1,槽越界)、`IPC_ERR_EACCES=usize::MAX-1`(-2,未授权/空槽)。
- **锁序契约**(模块头注释):`process::cap_target`(TABLE)→ IPC → SCHED,
  全程不逆序;IPC 锁只在 trap/syscall 或引导期取,**绝不在 ISR 取**;命中
  配对先 drop IPC 锁再取 SCHED 唤醒(锁不重叠)。
- **原子性**:`NoPeer`(已登记 pending)→ 调用方 `block_user_from_trap`
  之间无调度点(单核、trap 上下文中断关),登记与配对不丢。

### 3.4 process.rs:简化能力表

- `MAX_CAPS=8`;`Process` 增 `caps: [Option<usize>; MAX_CAPS]`(数组定长保
  `Process` Copy;槽 → 目标进程 pid,None = 未授权)。
- `grant_cap(pid, slot, target_pid) -> Result<(), CapError>`:覆盖写入幂等;
  槽越界 → `InvalidSlot`,进程不存在 → `NotFound`。
- `cap_target(pid, slot) -> Result<usize, CapError>`:供 IPC 目标解析;
  空槽/进程不存在 → `NotFound`。`create()` 初始化 `caps=[None; MAX_CAPS]`。

### 3.5 syscall.rs:IPC 系统调用

- 常量 `SYSCALL_IPC_SEND=3`、`SYSCALL_IPC_RECV=4`;GPR_A1..A5 为
  `arch::gpr::X_A1..X_A5` 别名(帧索引单一来源,禁手写魔数)。
- SEND 分支:取 a0=slot、a1-a5=msg → `ipc::send(current_proc(), slot, msg)`:
  `Done` → a0=0 + sepc+4;`NoPeer` → `block_user_from_trap(frame)`(不返回);
  `Err(code)` → a0=code + sepc+4(不阻塞)。
- RECV 分支:对称;`Done(msg)` → a0=0、a1-a5=msg、sepc+4。
- `main.rs` 增 `mod ipc;`;`arch/riscv64.rs` 的 `mod gpr` 改 `pub mod gpr`。

### 3.6 tests.rs:boot_ipc_test

- R 程序(16 条指令):写 ready 标记 0x51 → `recv(0)`(阻塞)→ 存 status+msg
  → exit。S 程序(23 条指令):先 `send(2, …)` 期望 `-EACCES`(未授权槽,
  不阻塞)→ 再 `send(0, [0x111,0x222,0x333,0x444,0x555])`(与 R 的 pending
  recv 配对)→ 存 status → exit。
- 引导期协作确定性顺序:R 先就绪入队 pending recv → main 轮询到 ready 后
  spawn S → S 配对唤醒 R。断言:R status==0、R 收到 5 字消息、S 未授权槽
  == `-EACCES`。banner:`M2 T2a: sync IPC ok (reg-msg roundtrip, cap
  -EACCES reject)`。
- 门禁同步:`Makefile`(test/test-rva23)与 `.github/workflows/ci.yml`
  (build/rva23)四处各加两条 banner 的 `grep -q` 断言。

## 5. 遗留风险

| 项 | 说明 | 计划 |
|---|---|---|
| 优先级继承(PIP) | T2a 未做;D22 抢占基础已就绪,可直接落地 | T2b |
| IPC 压力测试 | 万次配对/唤醒并发校验尚未做(需 PIP/多线程配合) | T2b |
| 共享内存大消息 | 大消息仍不可用(仅 5 字寄存器消息) | T3 |
| revoke/duplicate 能力操作 | 能力表仅 grant/解析,无回收 | T3 |
| 进程销毁/页回收 | 进程退出不回收地址空间页(D12 一并) | T2b/T3 |
| 自发自收 | 每进程单线程,自发自收会阻塞(pending 自己);能力授权语义下正常 | 多线程后重审 |
| 多核 IPC 语义 | IPC 状态机全局单锁,单核正确;跨核语义需 D7-D9 前置 | 多核阶段 |
| 内核线程栈守护页 | 既有预留(仅 boot/trap 栈有) | 后续硬化 |

五门禁全绿下验证通过,本拍结束;下一步 T2b(优先级继承 + 压力测试)。
