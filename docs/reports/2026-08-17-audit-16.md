# 报告:外部审计第 16 轮处置(2026-08-17)

## 1. 摘要

外部 max 审计(`docs/audit-reports/20260817-135011-deepseek-v4-pro.md`):
**3 CRITICAL / 6 HIGH / MED/LOW**。全部核实处置。本轮 3 个 CRITICAL
均为真实架构缺陷(混合切换机制、新线程帧、sscratch 恢复)。

## 2. 修复明细

### CRITICAL

| # | 发现 | 修复 |
|---|---|---|
| C1 | **混合切换机制缺陷**:被抢占线程状态在帧里,但协作路径(yield/block/exit)可能用**陈旧 ctx** 切换到它 → 错乱 | **ctx_valid 协议**(与 frame_valid 互补):协作路径只选 ctx_valid;抢占路径只选 frame_valid;on_tick 捕获后 cur.ctx_valid=false、选中者=true;pick_next(need_ctx) 按需过滤(无分配轮转扫描,不丢候选) |
| C2 | **新线程帧无效**:sp=0(恢复路径 ld sp 崩溃)、gp=0(gp 相对寻址风险) | 初始帧设置 `frame[1]=sp`、`frame[2]=__global_pointer()`(link_name 引用) |
| C3 | **恢复路径污染 sscratch**:抢占切换的帧在堆里,`sscratch=帧+帧长` 是堆地址 → 下次 trap 嵌套检测误判"嵌套"停机 | 汇编判断:`帧+帧长 == 陷阱栈顶` 才复位 sscratch(TCB 帧不动) |

### HIGH

| # | 修复 |
|---|---|
| H4 | 抢占自检有效性:驳回(附分析 —— busy 线程 frame_valid=true,主线程被捕获后也可选) |
| H5 | **ISR 可能分配**(enqueue 的 push_back 扩容,与堆锁死锁):就绪队列/reaper/线程 Vec **init 预留容量**(MAX_THREADS=64),ISR 零分配 |
| H6 | Condvar wait 不唤醒互斥等待者:驳回(经典语义,15 轮已述) |
| H7 | —(同 C1 场景,已修) |

### MEDIUM

| # | 修复 |
|---|---|
| M7 | **idle_entry 永不进入,reap 不跑,退出栈泄漏**:回收移入 `yield_` 锁作用域(释放他人栈,安全) |
| M8 | **栈分配/释放布局不匹配**(Box<[u8]> drop 用 align=1):`KernelStack` 自定义 Drop(同布局 dealloc) |
| M9 | dealloc 界检查收窄到 **real_count**(过宽的 MAX_PAGES 检查放行 padding 区指针) |

## 3. 验证

  上下文切换 211ns(轮转扫描代价,可接受)。

  (150ms 忙线程)覆盖。
