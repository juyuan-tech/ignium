# Independent AI audit (deepseek-v4-pro)

- date: 20260817-131129
- model: deepseek-v4-pro
- tool: scripts/ai_audit.py (external reviewer, not the author)

## Executive summary

The codebase has progressed well beyond the stated “M0 boot chain” milestone and contains a full M1 feature set (trap handling, timer, buddy allocator, Sv39 identity mapping, heap, scheduler, mutex/condvar). The overall structure is sound, and several hard problems are handled thoughtfully: boot-hart arbitration, CSR sanitation, trap-frame validation, FDT endianness parsing, linker-script separation of stack/allocator, and meaningful QEMU smoke tests.

However, I found several correctness and memory-safety problems that are currently masked by QEMU, specific compiler code generation, favorable timing, or incomplete test coverage. The most serious are:

- **UB from mutating an immutable Rust `static`** (`PAGE_META`)
- **Use-after-free of a thread’s own stack during `exit()`**
- **Stale trap-frame reuse after `yield_()`** (`frame_valid` not invalidated)
- **Buddy allocator accepting interior “stale head” pages as valid frees**
- **Classic lost-wakeup races in mutex/condvar**, some of which can deadlock or hang under timer preemption
- **Preemptive scheduler design that cannot resume yielded/blocked threads**, making the “preemption” selftest largely vacuous

These should be fixed before M1.5 hardening.

## Findings (severity-ranked)

### Finding 1 — CRITICAL: `PAGE_META` is an immutable `static` mutated through a raw pointer
**File:** `kernel/src/mem.rs:50-52`, `kernel/src/mem.rs:132`

`PAGE_META` is declared as:

```rust
static PAGE_META: [PageMeta; MAX_PAGES] = ...
```

Later, `BuddyAllocator::init` does:

```rust
self.meta = (&raw const PAGE_META).cast::<PageMeta>().cast_mut();
```

and `meta()` hands out `&mut PageMeta` references. Under Rust’s memory model, mutating an immutable `static` allocation through a raw pointer is UB. The compiler may place it in read-only memory later (especially after page-permission splitting in M1.5), may assume its value cannot change, and `&mut` references from this pointer violate aliasing rules.

**Fix:** Use a mutable allocation with raw-mut access:

```rust
static mut PAGE_META: [PageMeta; MAX_PAGES] = ...
```

and initialize from `addr_of_mut!(PAGE_META)` / `&raw mut PAGE_META` with an unsafe block. Even better, wrap it in `UnsafeCell` if you want to avoid `static mut` references. Do not cast from an immutable `&raw const`.

### Finding 2 — CRITICAL: `exit()` frees the currently executing thread’s stack
**File:** `kernel/src/sched.rs:388-404`

`exit()` does:

```rust
s.threads[cur].stack = alloc::vec![].into_boxed_slice();
```

which drops the old `Box<[u8]>` containing the stack currently in use by the executing function. Afterwards, the function calls `arch::context_switch()`. The generated function call may spill operands/state to the current stack, and the call/return machinery assumes the current stack is live. Freeing a heap allocation while your stack pointer is inside it is use-after-free.

The comment’s argument that no memory is touched after the free is not guaranteed at the Rust semantics level: compiler-generated spills, argument setup, or future code changes can write into the freed region. The allocator may also reuse part of that block.

**Fix:** Do not free the exiting thread’s own stack in `exit()`. For M1.5, either leak thread stacks until a reaper thread runs on a different stack, or transfer the stack handle to a reaper/cleanup queue and free it after switching to a safe context.

### Finding 3 — CRITICAL: `yield_()` does not invalidate `frame_valid`, so stale trap frames can be reused as live contexts
**File:** `kernel/src/sched.rs:yield_` around `enqueue(cur)`

`block_current()` and `exit()` correctly set:

```rust
s.threads[c].frame_valid = false;
```

But `yield_()` only enqueues the current thread and switches through `Context`:

```rust
let cur = s.current;
s.enqueue(cur);
s.ticks_run = 0;
let next = s.pick_next();
s.current = next;
...
```

If that thread had previously been preempted (`frame_valid == true` in its TCB), that stale trap frame remains valid. Later, `on_tick()` scans `ready` queues for threads with `frame_valid == true`, may select this yielded thread, and returns its **old preemption frame**. The thread would `sret` back to an old program point, effectively replaying execution before its `yield_`, corrupting scheduler state.

**Fix:** Add `s.threads[cur].frame_valid = false;` in `yield_()` before/after enqueueing. Any cooperative transition (`yield_`, `block_current`, `exit`) must invalidate the preemption frame.

### Finding 4 — HIGH: buddy allocator can accept stale interior pages as valid block heads
**File:** `kernel/src/mem.rs:alloc()`, `kernel/src/mem.rs:free()`

`alloc()` only writes metadata for the block head:

```rust
let m = self.meta(idx);
m.order = order as u8;
m.used = true;
```

Interior pages retain whatever metadata they had previously. That becomes unsound when a page was previously an allocated block head (`used = true`, `order = k`), later freed/merged into a larger block, and then the larger block is allocated:

1. Allocate order k at page P: `P.used = true`, `P.order = k`
2. Free P; merge it into a larger free block whose head is Q
3. Allocate the larger block Q; P is now interior to Q
4. `free_pages(P)` sees:
   - `P` is in range
   - `P.is_multiple_of(1 << k)` — true
   - `meta(P).used` — true
   - `meta(P).order = k <= MAX_ORDER`

So it accepts the interior address as a block head, marks it free, and pushes it into a free list. It now overlaps the allocated block Q. This silently corrupts the allocator and can hand out overlapping memory.

The current selftest only checks `h + PAGE_SIZE` on a freshly allocated block, where the interior page still has `{order:0, used:false}`, so it does not catch this stale-head case.

**Fix:** Either:
- add a `head: bool` or dedicated state to `PageMeta`, or
- on every large allocation, clear all non-head pages to an inert `{order:0, used:false}` state, or
- maintain a stricter “head” invariant and check a `head` flag instead of `used`.

Also add a selftest that creates exactly the stale-head scenario and asserts the interior free is rejected.

### Finding 5 — HIGH: mutex/condvar lost-wakeup races between `irq_restore()` and `block_current()`
**File:** `kernel/src/sync.rs` `Mutex::lock()`, `Condvar::wait()`, and `kernel/src/sched.rs` `block_current()`/`wake()`

`wake()` only enqueues a thread if it is `Blocked`:

```rust
if s.threads[id].state == ThreadState::Blocked {
    s.enqueue(id);
}
```

But the blocking paths have a window:

```rust
arch::irq_restore(irq);   // interrupts enabled here
sched::block_current();   // state still Running/Ready
```

A timer IRQ can fire in this window, preempt the thread, and allow a notifier to run. The notifier calls `wake()`, sees the target still `Running`/`Ready`, does nothing, then the target resumes and finally calls `block_current()` — and blocks forever.

The `block_current()` guard for `state == Ready` does not cover this because `wake()` never moves a non-`Blocked` thread to `Ready`.

**Fix:** Keep interrupts disabled across the entire “register waiter → unlock → transition to Blocked” sequence. The cleanest approach is to make `block_current()` assume interrupts are already disabled and remove the `irq_restore()` before it, or introduce a wait-channel primitive where wake/block state transitions are atomic under the scheduler lock with IRQs disabled. Then add a stress test that deliberately injects timer interrupts during the race window.

### Finding 6 — HIGH: `Condvar::wait()` releases the mutex without waking mutex waiters
**File:** `kernel/src/sync.rs:168-178`

Instead of calling `m.unlock()`, `Condvar::wait()` does:

```rust
m.locked.store(false, Ordering::Release);
```

That releases the mutex but does not pop/wake any thread already registered in `m.waiters`. A third thread blocked in `Mutex::lock()` can remain asleep indefinitely even though the mutex became available.

**Fix:** Replace the direct store with the mutex’s release path (factor a `release_locked()` that assumes IRQs are disabled, or call `m.unlock()` while the outer `irq_save()` state is still active). The release must wake one registered mutex waiter as usual.

### Finding 7 — HIGH: preemptive scheduling cannot resume yielded/blocked threads; current selftest does not actually prove preemption
**File:** `kernel/src/sched.rs:on_tick()`

`on_tick()` only considers `ready` threads whose:

```rust
state == Ready && frame_valid
```

But threads that have previously `yield_()`-ed or `block_current()`-ed have `frame_valid == false`. Such threads are silently ignored by preemption. A woken high-priority thread may therefore stay unselected until the current thread cooperatively yields or exits. This is priority inversion / starvation in the core scheduler.

The “preemption” selftest spawns `test_busy` while all other ready threads have `frame_valid == false`, so `on_tick()` never switches away from `test_busy`. The test passes only because `test_busy` eventually exits cooperatively. That makes the test a false positive.

**Fix:** Design an explicit ISR-to-scheduler path that can resume a yielded/blocked thread via its cooperative `Context`, or prepare a fresh trap frame for such threads. Do not rely only on saved preemption frames. Update the selftest to assert an actual tick-driven switch occurred (for example, have the busy thread increment a per-thread counter and verify another thread made progress before the busy thread exited).

### Finding 8 — HIGH: unsound `unsafe impl Sync` for `SpinLock<T>` and `Mutex<T>` without `T: Send`
**File:** `kernel/src/sync.rs:25-31`, `kernel/src/sync.rs:75-81`

The current impls:

```rust
unsafe impl<T> Sync for SpinLock<T> {}
unsafe impl<T: ?Sized> Sync for Mutex<T> {}
```

allow any `T`, including `Cell<T>`, `Rc<T>`, or non-`Send` types, to be shared across kernel threads. For `Mutex<Cell<u32>>`, multiple threads could obtain `&Cell<u32>` via lock and perform non-atomic `Cell` mutations, which is UB. The standard library requires `T: Send` for such impls.

**Fix:**

```rust
unsafe impl<T: Send + ?Sized> Sync for SpinLock<T> {}
unsafe impl<T: Send + ?Sized> Sync for Mutex<T> {}
```

and document the safety argument. This may surface compiler errors if the current types are not `Send`; adjust those types explicitly rather than weakening the impl.

### Finding 9 — MEDIUM/HIGH: FDT header bound checks do not prevent reads past `RAM_END`
**File:** `kernel/src/mem.rs:fdt_size()`, `kernel/src/mem.rs:init()`

`mem::init()` validates only:

```rust
fdt.is_multiple_of(4)
&& (RAM_START..RAM_END).contains(&fdt)
```

It then calls `fdt_size(fdt)`, which reads bytes at `fdt` and `fdt+4`. If a hostile/broken bootloader supplies `fdt = RAM_END - 4`, the header reads go past the end of RAM. This can cause an early access fault and halt before the kernel can recover.

**Fix:** Before reading, require:

```rust
fdt.checked_add(8) <= RAM_END
```

and ideally verify `fdt + totalsize` also fits within `RAM_END` before converting it to reservation pages. If validation fails, skip reservation or panic intentionally.

### Finding 10 — MEDIUM: scheduler APIs panic on attacker/invalid IDs and priorities
**File:** `kernel/src/sched.rs:spawn()`, `kernel/src/sched.rs:wake()`

`spawn()` indexes:

```rust
self.ready[prio as usize]
```

with no `prio < PRIO_LEVELS` check. `wake(id)` indexes:

```rust
self.threads[id]
```

with no `id < threads.len()` check. Future syscalls/IPC will ultimately expose variants of these APIs to user-influenced values. A bad `prio`/`id` becomes a kernel panic.

**Fix:** Validate at API boundaries, return `Result`/`Option`, clamp priorities, and keep indexing infallible internally. Add a dedicated debug assertion or error path.

### Finding 11 — HIGH: `block_current()` early-return path restores IRQs before dropping the scheduler lock
**File:** `kernel/src/sched.rs:block_current()`

The early return for `state == Ready` does:

```rust
arch::irq_restore(irq);
return;
```

while `s` (the `SpinLockGuard` over `SCHED`) is still alive until function exit. If a timer interrupt fires between `irq_restore` and guard drop, `on_tick()` attempts to lock `SCHED`, spins forever, and the CPU never returns to drop the guard. This is a deadlock window.

**Fix:**

```rust
drop(s);
arch::irq_restore(irq);
return;
```

Audit all other functions for the same “IRQ enabled while guard still alive” pattern (`notify_all()` currently has a similar structural hazard).

### Finding 12 — MEDIUM: `irq_save()` is not an atomic read-and-clear
**File:** `kernel/src/arch/riscv64.rs:irq_save()`

```rust
asm!("csrr {}, sstatus", out(reg) s, options(nostack));
...
asm!("csrci sstatus, 2", options(nostack));
```

There is a window between reading `SIE` and clearing it. On RISC-V, `csrrci` provides a single-instruction atomic read-clear of `sstatus.SIE`.

**Fix:**

```rust
asm!("csrrci {}, sstatus, 2", out(reg) s, options(nostack));
```

That removes the interrupt window and makes the `irq_save` semantic explicit.

### Finding 13 — MEDIUM: `mmu::self_test()` hardcodes UART LSR address as a `u32` pointer
**File:** `kernel/src/mmu.rs:self_test()`

```rust
let lsr = unsafe { core::ptr::read_volatile(0x1000_0005u32 as *const u8) };
```

This is brittle, mixes pointer-width casts, and breaks as soon as UART moves. Use:

```rust
(crate::board::UART_BASE + 5) as *const u8
```

or a named `UART_LSR` constant.

### Finding 14 — MEDIUM: UART divisor is 9600 baud, not the documented/expected rate
**File:** `kernel/src/uart.rs:100-106`

The register constants are labeled “formally correct” for a 1.8432 MHz reference and divisor `0x0C`, which gives 9600 baud. On a real NS16550 with a different reference clock, this will be wrong. QEMU’s virtual UART tolerates arbitrary programming.

**Fix:** In M1.5, calculate divisor from a board/FDT clock and requested baud, with a known default for QEMU.

### Finding 15 — LOW: trap nested-detection has a small ambiguity window
**File:** `kernel/src/arch/riscv64.S:trap_vector`

The nested check is:

```asm
addi t0, t0, -TRAP_FRAME_SIZE
bne t6, t0, 4f
```

Before the outer handler writes `sscratch = frame_base`, `sscratch` contains the displaced old `t6` from the interrupted context. If that old `t6` happened to equal `_trap_stack_top`, a synchronous double trap during the first few instructions could look exactly like a first trap and overwrite the outer frame. This is unlikely under current QEMU paths, but on real hardware with corrupted trap stacks it should be made deterministic.

**Fix:** Immediately install an unambiguous value in `sscratch` after the `csrrw` (for example, a known per-hart kernel marker), and use that marker for nested detection.

### Finding 16 — LOW/MEDIUM: lockless logger can interleave with timer-ISR/preemption contexts
**File:** `kernel/src/logger.rs:log()`, `kernel/src/uart.rs:putc()`

A long `info!` emitted after `irq_enable()` can be interleaved with an exception-path log (`TRAP:`) or corrupted by concurrent UART access once threads/multiple harts log. `AtomicU64` tick is safe, but the formatted line is not atomic as a UART stream.

**Fix:** Add a short UART/log lock in M1.5, or an IRQ-disabled diagnostic writer for trap/panic paths; document panic-path lock ordering so it does not deadlock with a held console lock.

## What looks correct (so the author knows what not to change)

- **Linker-script organization (`kernel/linker.ld`)** is carefully reasoned: entry at `0x80200000`, `.text.entry` first, explicit `_alloc_start` red line, stack and trap stack outside `_kernel_end`, and debug/orphan sections not placed in allocatable space.
- **Boot path (`kernel/src/entry.S`)** correctly clears `SIE`, sets `tp = hartid`, installs an early trap stub, clears `satp` and TLB, initializes `gp`, arbitrates boot with `amoswap`, and zeroes BSS + both stacks through `_trap_stack_top`.
- **CSR sanitation (`kernel/src/arch/riscv64.rs:sanitize_csr`)** clears `sie`, writable `sip`, and `SUM`/`MXR`/`FS` bits before timer setup; this is a good habit for hostile bootloaders/hot reset.
- **Trap frame validation (`trap_handler`)** with subtraction instead of `ptr + size`, bounds check, alignment check, and the restore path’s `SIE`/`SPIE` handling are solid.
- **FDT endianness handling (`fdt_size`)** correctly reads big-endian fields bytewise; the earlier `read_volatile::<u32>` trap is avoided.
- **Compile-time frame-size assertion (`TRAP_FRAME_WORDS * 8 == 288`)** ties Rust and assembly constants together.
- **UART DLAB ordering and `fence iorw, iorw`** are correct for real NS16550/weakly ordered hardware.
- **Boot smoke tests (`Makefile`, `ci.yml`)** wait for the full QEMU run before grepping, and check for multiple `uptime:` lines, panic/trap absence, and SMP single-boot arbitration.
- **Deadline-increment timer programming** avoids cumulative drift and SSTC write/readback gives a loud failure on unsupported platforms.

## Blind spots & suggestions for the next milestone (M1: trap handling)

1. **Fix the scheduler frame state machine first.** Any further work on traps/scheduling should treat `frame_valid` as a precise invariant:
   - cooperative yield / block / exit: `frame_valid = false`
   - preemption capture: `frame_valid = true`
   - preemption restore into a thread that then yields: must invalidate it again

2. **Replace the “sret-to-frame only” preemption model.** M1/M1.5 should have a proper ISR-to-scheduler exit that can resume cooperative contexts, not only previously preempted or never-run threads.

3. **Add per-hart trap stacks and per-hart timer state before SMP.** The current single `_trap_stack_*` and global `TIMER_DEADLINE` are only valid because secondary harts park before trap setup. `sscratch` should be loaded from a per-hart array indexed by `tp`/`hartid`.

4. **Strengthen allocator metadata tests.** Add randomized buddy torture that specifically:
   - allocates/frees various orders around a pattern known to leave stale interior metadata,
   - asserts interior frees are rejected after merging/larger allocation,
   - runs with M1.5’s IRQ-safe allocator variant.

5. **Add preemption-aware synchronization tests.** The mutex/condvar tests currently run mostly uncontended and are timing-sensitive. Inject timer-generated preemption slices during lock/condvar stress (10k–100k operations), and assert no lost wakeups, no duplicate scheduling, no stale frame resumes.

6. **Move to `csrrci` for `irq_save`** and audit every IRQ-restore/guard-drop ordering. Consider writing a lint or checker script to enforce “drop guard before `irq_restore`”.

7. **Before page-permission splitting (M1.5), fix `PAGE_META` mutability UB.** If `.rodata` becomes RX-only, the current page-metadata writes would fault on real hardware. A `Head` flag or explicit mutable allocation should land first.

8. **Add PMP** to the M1.5 plan. The kernel currently trusts OpenSBI/QEMU memory protection. For a security-focused microkernel, early PMP setup should be part of trap/memory bring-up, not deferred until user mode.

9. **Do not free a thread’s own stack in `exit()`** without a reaper. If memory reclaim is required, design a zombie-thread reaper running on a separate stack and make it explicit.

10. **Test with timer enabled earlier in boot.** Moving `irq_enable` before the M1 selftests would expose many of the races above. A CI variant that enables the timer before `sched::self_test`/`sync::self_test` would be a valuable stress gate.
