# Independent AI audit (deepseek-v4-pro)

- date: 20260820-112233
- model: deepseek-v4-pro
- tool: scripts/ai_audit.py (external reviewer, not the author)

## Executive summary

V4 found **one CRITICAL scheduler/synchronization lost-wake race**, **one HIGH priority-scheduling starvation**, plus several robustness and documentation issues that are new relative to V2/V3. The most serious issue is that `pick_next` consumes `Thread::woken` before the woken thread gets a chance to reach `block_current`; combined with the IRQ-enabled window before `sched::block_current()` in `Mutex::lock`/`Condvar::wait`, this can silently drop a wake under timer preemption and permanently deadlock a thread.

The second notable issue is that timer-driven preemption only considers `frame_valid` threads. Threads that are blocked and later woken are always `ctx_valid`-only, so a higher-priority woken thread cannot preempt a lower-priority busy thread. This means priority scheduling is broken for exactly the wake/notify path.

The memory allocator, MMU identity mapping, trap-frame protocol, IRQ-safe spinlocks, and FDT parser bounds are generally well implemented. The findings below focus on state-machine races, hardware-portability assumptions, stale docs, and scheduler API limitations.

## Findings (severity-ranked)

### CRITICAL — Lost wake: `pick_next` clears `woken` before `block_current` can consume it

- **Severity:** CRITICAL
- **Where:**
  - `kernel/src/sched.rs`, `Scheduler::pick_next` — the line `self.threads[id].woken = false;`
  - `kernel/src/sync.rs`, `Mutex::lock` — `arch::irq_restore(irq); sched::block_current();`
  - `kernel/src/sync.rs`, `Condvar::wait` — `arch::irq_restore(irq); sched::block_current();`
- **Status:** [NEW]

**Description:**

`Mutex::lock` (after registering in the waiter queue) and `Condvar::wait` (after registering in the condvar wait queue) both do:

```rust
arch::irq_restore(irq);
sched::block_current();
```

Between restoring SIE and the first instruction of `block_current`, a timer interrupt can fire. If `on_tick` preempts this thread, `on_tick` sets the thread to `Ready` and enqueues it. Now suppose the other thread runs and calls `unlock`/`notify_one`. `wake()` sees the target’s state is `Ready` (not `Blocked`), so it only sets `woken = true` and does not enqueue it again.

Later `pick_next` selects that preempted thread. `pick_next` currently does:

```rust
self.threads[id].state = ThreadState::Running;
self.threads[id].woken = false;
return id;
```

This destroys the `woken` flag that was meant to protect the thread when it finally reaches `block_current`. The thread resumes in the window before `block_current`, enters `block_current`, sees `state == Running` and `woken == false`, and blocks — despite having already been popped from the waiter queue and woken. The notifier will not notify again. Permanent deadlock.

The `woken` flag is a lost-wake guard. It must remain set until `block_current` itself consumes it. Consuming it in `pick_next` is too early and reintroduces the exact lost-wake problem the flag was designed to prevent.

**Concrete fix:**

- Remove `self.threads[id].woken = false;` from `pick_next`.
- Let `block_current` be the only consumer:
  - the early `state == Ready` branch,
  - the `woken == true` branch,
  - the post-`do_switch` wake path.
- Optionally also add a `block_current` variant that accepts/preserves the caller’s previous IRQ state so `Mutex::lock` and `Condvar::wait` can keep interrupts disabled until the block is actually registered, closing the preemption window entirely.

### HIGH — Timer preemption cannot schedule `ctx_valid` threads, so woken higher-priority threads can starve

- **Severity:** HIGH
- **Where:** `kernel/src/sched.rs`, `Scheduler::on_tick`
- **Status:** [NEW]

**Description:**

`on_tick`’s priority check and general preemption check both require `frame_valid`:

```rust
let higher = (0..cur_prio).any(|l| {
    self.ready[l].iter().any(|&id| {
        id != self.current
            && self.threads[id].state == ThreadState::Ready
            && self.threads[id].frame_valid
    })
});
...
let has_other = (0..PRIO_LEVELS).any(|l| {
    self.ready[l].iter().any(|&id| {
        id != self.current
            && self.threads[id].state == ThreadState::Ready
            && self.threads[id].frame_valid
    })
});
```

But every thread that goes through `block_current` sets:

```rust
s.threads[c].frame_valid = false;
s.threads[c].ctx_valid = true;
```

Therefore a blocked/woken thread is always `ctx_valid`-only. It can be selected by cooperative `yield`/`block`/`exit`, but **not** by timer preemption.

Scenario: a low-priority thread is running a long loop without yielding. Some other thread releases a mutex or signals a condvar, waking a high-priority thread. `wake` enqueues the high thread, but `on_tick` cannot select it because it has no valid frame. The low-priority thread keeps the CPU, and the high-priority thread starves until the low thread voluntarily yields or exits.

This also makes priority scheduling semantically inconsistent: a newly spawned high-priority thread preempts promptly because `frame_valid == true`, but a woken high-priority thread never does.

**Concrete fix:**

Provide a way for `wake()` to trigger a preemption decision, or extend the timer preemption path to handle ctx-valid candidates. For example:

- track a `need_reschedule` flag when a higher-priority thread is woken; or
- in the timer ISR, copy the current trap frame into the TCB and then perform a cooperative-style switch to a ctx-valid target.

At minimum, document this limitation explicitly; currently the comments and MED-2 wording imply immediate priority preemption, which is not true for woken threads.

### MED — `mem::self_test` hard-requires a full `MAX_ORDER` block, causing boot panic on small/fragmented RAM

- **Severity:** MED
- **Where:** `kernel/src/mem.rs`, `mem::self_test`
- **Status:** [NEW]

**Description:**

The self-test starts and ends with:

```rust
let a = alloc_pages(MAX_ORDER).ok_or("alloc(12) failed")?;
...
let big = alloc_pages(MAX_ORDER).ok_or("post-free alloc(12) failed")?;
```

`MAX_ORDER` is 12, i.e. a 16 MiB contiguous buddy block. But `board::init_from_fdt` accepts RAM sizes as small as 1 MiB (`cand_size >= 1024 * 1024`), and the buddy allocator itself can operate on smaller free extents. On a 1–15 MiB RAM platform, `alloc_pages(MAX_ORDER)` will always return `None`, causing the self-test to fail and the kernel to panic — even though the allocator is otherwise functional.

Likewise, multiple FDT reserved regions can fragment every 16 MiB alignment so no order-12 block exists, even with more total RAM.

This is a QEMU-shaped assumption, not a real allocator invariant.

**Concrete fix:**

Make the self-test adaptive:

- discover the largest currently allocatable order first, or
- only exercise `MAX_ORDER` if a full order-12 block is available, otherwise test the largest available order and verify merge/split semantics with that maximum.

Also ensure boot validation checks that the allocator will actually have at least one page after alignment (`base < ram_end` already does this) and that the self-test cannot demand more contiguity than the geometry provides.

### MED — SBI `set_timer` return values are ignored on the active fallback path

- **Severity:** MED
- **Where:**
  - `kernel/src/arch/riscv64.rs`, `enable_timer`
  - `kernel/src/arch/riscv64.rs`, `arm_timer`
- **Status:** [NEW]

**Description:**

`sbi::set_timer` returns an SBI error code, and `sbi.rs` explicitly documents that callers must check it. But both timer paths ignore it:

```rust
let _ = crate::sbi::set_timer(deadline);
...
let _ = crate::sbi::set_timer(next);
```

On any platform without SSTC, `arm_timer` uses the SBI path for every timer tick. If SBI reports an error (unsupported extension, invalid parameter, firmware policy, etc.), the kernel silently loses the timer interrupt. Preemption and heartbeat stop. The D-旧 history shows the boot-timer failure previously had a warn/panic response; this D17 rewrite appears to have lost that check.

**Concrete fix:**

Check the return code in both places. At first programming, a non-success return should panic or at least `error!` loudly. In `arm_timer`, a persistent failure should be distinguishable (e.g., rate-limited error log or one-shot diagnostic) because it means no future timer interrupts.

### MED — Early UART initialization uses the hard-coded QEMU address before FDT-based board init

- **Severity:** MED
- **Where:**
  - `kernel/src/main.rs`, `kernel_main` — `uart::init()` is called before FDT parsing
  - `kernel/src/uart.rs`, `init`/`reinit`
- **Status:** [NEW]

**Description:**

`kernel_main` initializes the UART before parsing the FDT:

```rust
uart::init();
...
let fdt_params = crate::fdt::Fdt::new(...).map(|f| f.parse())...;
board::init_from_fdt(&fdt_params);
crate::uart::reinit();
```

At that first `uart::init()`, `board::uart_base()` has not been populated from the FDT, so it returns `DEFAULT_UART_BASE = 0x1000_0000`. `uart::init_hw()` writes to LCR/DLL/DLM/IER/FCR/MCR there.

This is correct for QEMU `virt`, but on real hardware the console may be at a different MMIO address. The early writes can go to an unmapped or unrelated device region, potentially causing an access fault or hardware side effects before the FDT has a chance to tell the kernel the real UART location. This conflicts with the stated “真机就绪” direction of M1.5.

**Concrete fix:**

For real hardware, obtain the early console address before driving the UART — e.g. parse enough of the FDT first, use an SBI debug console for early output, or accept the UART base from the bootloader. The current `reinit()` path is useful but too late for the first writes.

### LOW — Timer/benchmark time conversions hard-code a 10 MHz timebase

- **Severity:** LOW
- **Where:**
  - `kernel/src/main.rs`, final `info!` — `arch::timer_interval() / 10`
  - `kernel/src/heap.rs`, `bench` — assumes 100 ns per `get_time` tick
  - `kernel/src/sched.rs`, `bench` — same assumption
- **Status:** [NEW]

**Description:**

The board layer explicitly supports runtime `timebase-frequency` from the FDT, but several diagnostics still assume QEMU’s 10 MHz clock:

- `main.rs` prints `arch::timer_interval() / 10` and calls it µs.
- `heap::bench` and `sched::bench` translate ticks with `dt * 100` ns.

If `timebase-frequency` is, say, 1 MHz or 24 MHz, the numbers are wrong. Additionally, `board::init_from_fdt` rejects frequencies above 1 GHz. Some real RISC-V platforms can have a timebase above that; falling back to 10 MHz makes tick timing dramatically wrong.

**Concrete fix:**

Use `crate::board::timer_freq()` everywhere cycles must be converted to ns/µs. Relax or platform-validate the 1 GHz upper bound rather than silently substituting a default frequency.

### LOW — FDT string bounds use `total_size` instead of `size_dt_strings`

- **Severity:** LOW
- **Where:** `kernel/src/fdt.rs`, `Fdt::read_string`
- **Status:** [NEW]

**Description:**

`read_string` bounds the string offset against:

```rust
if offset >= self.total_size - self.off_strings { ... }
let max_len = self.total_size - self.off_strings - offset;
```

It never uses `size_dt_strings`, which is read in `Fdt::new` but not stored. A malformed but length-valid FDT with `size_dt_strings` much smaller than `total_size - off_strings` can make property names point into the middle of the structure block. The reads still stay inside the FDT allocation, so this is not an OOB memory-safety bug, but the parser would no longer be parsing the actual strings block.

**Concrete fix:**

Store `size_dt_strings` in `Fdt` and use it for both the upper-bound check and `max_len`.

### LOW — Documentation/code drift after D17 and M1.5 changes

- **Severity:** LOW
- **Where:**
  - `kernel/src/cpu.rs`, module header
  - `kernel/src/arch/riscv64.rs`, `set_stimecmp` doc
  - `kernel/src/mmu.rs`, module header
  - `kernel/src/sbi.rs`, module header
  - `README.md`, repository structure description of `cpu.rs`
- **Status:** [NEW]

**Description:**

Several comments are stale:

- `cpu.rs` still says capability detection is “当前仅用于诊断输出;运行时回退由后续阶段实现,” but this module now actively drives `arch::set_sstc()` for D17.
- `riscv64.rs` `set_stimecmp` still says capability detection uses an “写读回断言” in `enable_timer`; that assertion no longer exists.
- `mmu.rs` module header lists `map_4k` and `map_region_4k` under “公开接口,” but both are private `fn`s. Only `unmap_4k`, `satp`, and `tlb_flush` are public.
- `sbi.rs` says every caller must check the return code, but timer callers ignore it (see MED finding above).
- `README.md` says `cpu.rs` runtime fallback is pending D17, but D17 is implemented.

**Concrete fix:**

Synchronize comments with the D17 implementation, make `map_4k`/`map_region_4k` public if they are intended as M2-facing APIs (or update the module header), and make the SBI error convention match the code.

### LOW — Idle thread’s allocated stack and `idle_entry` are never actually used

- **Severity:** LOW
- **Where:** `kernel/src/sched.rs`, `Scheduler::init`
- **Status:** [NEW]

**Description:**

`Scheduler::init` allocates a 16 KiB kernel stack for the idle thread, fills in `ctx.ra = idle_entry`, `ctx.sp = allocated_stack_top`, and `frame.sepc = idle_entry`, then marks the boot context as current thread 0.

However, the kernel boot continues executing on the boot stack, not the allocated idle stack. On the first `yield_`, `context_switch` overwrites `threads[0].ctx` with the real boot-context register state, so the synthetic idle Context is lost. Since `threads[0].frame_valid` is initialized to `false`, the synthetic idle frame is also never used. `idle_entry` is therefore dead, and the allocated idle stack is leaked for the lifetime of the kernel.

This is not currently harmful, but it is misleading and wastes heap/buddy memory.

**Concrete fix:**

Either:

- do not allocate a separate idle stack; document that the boot context *is* idle thread 0 and its stack is the linker boot stack, or
- explicitly switch the boot context to the allocated idle stack before enabling scheduling so the TCB representation matches reality.

## What looks correct

The following areas were checked and look sound for the current single-core QEMU stage:

- **Buddy allocator core:** split/merge logic, alignment validation, double-free rejection, interior-page rejection, reserved-region carving across multiple order-12 blocks, padding pages marked permanently used.
- **Slab heap:** size-class indexing, intrusive free-list construction, multi-page freelist traversal, large-object `ptr-8` block base storage, ZST/no-op dealloc handling.
- **Sv39 identity mapping:** root/table construction, per-section permissions (RX/R/RW), A/D handling, guard-page unmapping, UART MMIO mapping, TLB flush after satp/unmap.
- **Trap frame protocol:** full GPR/CSR save, stack-limit check, nested-trap halt, `ctx_valid`/`frame_valid` dual restoration paths, `sscratch` reset to `_trap_stack_top`.
- **IRQ-safe SpinLock:** `csrrci`-based `irq_save`, acquire/release atomic ordering, nested save/restore behavior.
- **FDT parser baseline:** bounded header/struct/rsvmap reads, 8-byte alignment, node-name stack, UTF-8 validation, aligned property skipping, reserved-region merging.
- **Timer deadline catch-up:** prevents tick storms after long interrupt-disabled periods and uses wrapping arithmetic.
- **Boot arbitration:** `BOOT_LOCK` in `.data`, single-winner `amoswap`, BSS/stack clearing by the winner, secondary harts parked.

## Blind spots & suggestions for M2

The following should be priorities before/within M2:

1. **Fix the lost-wake and wake-preemption problems first.** User processes/IPC will make `block/wake` the central primitive; the current woken-flag race becomes much easier to hit with real IPC clients.
2. **Add a proper preemption mechanism for ctx-valid targets.** Without it, priority inheritance/avoidance for IPC and mutexes will not work.
3. **Per-hart trap stacks and console locking.** Already tracked as D7/D9; user-mode syscalls and multi-core will make the current single trap stack and unlocked UART immediately unsafe.
4. **Thread TCB/ID reuse.** `Thread`s are never removed from `threads`, and `next_id` only grows. Long-running spawn/exit workloads will hit `MAX_THREADS` even though only a few threads are live.
5. **Thread-stack guard pages.** D20 is deferred; for M2, thread stacks should have guard pages or equivalent kernel-side bounds checks.
6. **Finalize the page-table API.** Decide whether `map_4k` and `map_region_4k` are public or arch-private; M2 user mappings need a clear contract, including “refuse to overwrite existing PTE” semantics.
7. **Revisit real-hardware assumptions:** early UART address, timebase frequency range, FDT memory `#address-cells`/`#size-cells` variants, multiple memory banks, and SBI timer error handling.
8. **Add regression tests for the lost-wake race.** A stress test that repeatedly preempts a thread in the `irq_restore` → `block_current` window and concurrently notifies it is needed; the current condvar/mutex tests do not deterministically exercise that window.
