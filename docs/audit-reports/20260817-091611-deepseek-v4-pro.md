# Independent AI audit (deepseek-v4-pro)

- date: 20260817-091611
- model: deepseek-v4-pro
- tool: scripts/ai_audit.py (external reviewer, not the author)

## Executive summary

The M0/M1 boot chain is generally well-structured: the entry sequence clears legacy CSR state before touching memory, the UART init handles the DLAB ordering trap, the buddy allocator has meaningful self-tests, and the trap frame save/restore path is mostly correct. However, the external FDT pointer is trusted in ways that can corrupt boot data or panic the kernel, the trap entry path writes to memory before validating a pointer derived from `sscratch`, and several latent issues will become acute on real hardware or when interrupts/user-mode are added. The most important concrete bug is the FDT reserved-region start calculation, which rounds up instead of down and can leave the first page of the device tree unprotected.

## Findings (severity-ranked)

### CRITICAL

None that break the current QEMU configuration.

### HIGH

#### H1. FDT reserved region start rounds up, leaving the first FDT page unprotected
- **Severity:** HIGH
- **File:** `kernel/src/mem.rs`, function `init`, expression `let fdt_start = fdt.div_ceil(PAGE_SIZE) * PAGE_SIZE;`
- **Description:**  
  The reserved region for the device tree blob is computed as `[fdt_start, fdt_end)` with `fdt_start` rounded **up** to the next page boundary. If the bootloader passes an FDT pointer that is not 4 KiB-aligned (e.g. 8-byte aligned, which is common), the page containing the first bytes of the FDT is **not** reserved. The buddy allocator can later allocate that page. During `mem::self_test`, pages are allocated and then freed; freeing writes a linked-list `next` pointer into the first word of the page, which overwrites the FDT magic, corrupting the device tree before any future FDT parsing.  
- **Fix:**  
  Use floor alignment for the start:  
  ```rust
  let fdt_start = fdt.div_euclid(PAGE_SIZE) * PAGE_SIZE; // or fdt & !(PAGE_SIZE - 1)
  ```
  and handle saturation if `fdt` is below `base`.

### MEDIUM

#### M1. Boot-time SBI timer programming failure causes silent hang after interrupts are enabled
- **Severity:** MEDIUM
- **File:** `kernel/src/arch/riscv64.rs`, function `enable_timer`, and `kernel/src/main.rs` boot sequence
- **Description:**  
  `enable_timer` logs a warning if the first `sbi::set_timer` fails, but then `kernel_main` continues, enables global interrupts, and enters the `wfi` idle loop. Since no timer interrupt will ever fire, the system appears to boot but then produces no further output; the only diagnostic is the boot-time warning. There is no watchdog or panic. On real hardware or a buggy SBI implementation this is a catastrophic hang that is hard to distinguish from a normal idle system.
- **Fix:**  
  Treat failure of the initial timer programming as fatal: `panic!("sbi_set_timer failed at boot")`, or retry `set_timer` with a bounded loop and then panic. In the timer ISR, track consecutive failures and escalate if the timer cannot be reprogrammed.

#### M2. Buddy allocator leaks the final partial max-order block when RAM size is not a multiple of 16 MiB and no reserve region exists
- **Severity:** MEDIUM
- **File:** `kernel/src/mem.rs`, function `init`, no-reserved-region path
- **Description:**  
  When `reserved.0 >= reserved.1`, the allocator switches to a simple loop:  
  ```rust
  let mut idx = 0usize;
  while idx + order_size <= count {
      self.push(idx, MAX_ORDER);
      idx += order_size;
  }
  return;
  ```
  If `count` is not a multiple of `order_size` (the current QEMU `-m 128M` configuration makes it a multiple), the remaining `count % order_size` pages are never pushed and never marked used. Those pages are silently lost. On future real hardware with non-multiple RAM sizes, this wastes up to ~16 MiB − 4 KiB and is non-obvious.
- **Fix:**  
  Mark the leftover partial block as permanently used, or preferably call the same `carve` path with an empty/invalid reservation so all pages are explicitly classified. Do not rely on the current QEMU memory size being a multiple of the max order.

#### M3. Trap vector writes to frame slots before validating the trap-stack pointer derived from `sscratch`
- **Severity:** MEDIUM
- **File:** `kernel/src/arch/riscv64.S`, `trap_vector` entry (the `sd t0, 4*8(t6)` and `sd t0, 30*8(t6)` stores before nested detection / bounds check)
- **Description:**  
  The trap entry immediately computes `t6 = sscratch - TRAP_FRAME_SIZE` and performs two `sd` stores to `t6 + offset`. Only later does it compare `t6` against the expected first-level frame address and branch to a halt path. If `sscratch` has been corrupted (e.g. by a kernel bug, a prior nested trap, or an attack that influences CSR state), these stores become arbitrary writes to kernel memory, potentially corrupting critical data before the fault is contained. The current halt path is therefore not fully safe.
- **Fix:**  
  Validate the `sscratch`-derived pointer **before** any memory writes. For example, load the expected stack bounds into t0/t1 first, check that `t6` is within `(_trap_stack_bottom, _trap_stack_top]`, and only then perform stores. If invalid, jump to the halt path without touching memory.

#### M4. `sbi::set_timer` inline assembly may not declare all SBI-clobbered registers
- **Severity:** MEDIUM (conditional)
- **File:** `kernel/src/sbi.rs`, `set_timer` inline asm
- **Description:**  
  The inline `ecall` wrapper declares only `a0` and `a1` as `lateout` outputs, and inputs `a6`/`a7`. It does not declare any clobbers for `a2-a5`, `t0-t6`, or other caller-saved registers. If the SBI implementation follows the standard RISC-V calling convention and may clobber all caller-saved registers (not only `a0`/`a1`), the compiler may keep live values in those registers across the `ecall`, leading to silent corruption. Some SBI specs/firmware do preserve more registers, but relying on that without an explicit guarantee is fragile.
- **Fix:**  
  Verify against the exact SBI spec/OpenSBI version whether only `a0`/`a1` are clobbered. If in doubt, add all caller-saved registers as clobbers, or better, implement an assembly shim that explicitly preserves state around `ecall`. This becomes more important when the kernel has more live state across SBI calls.

### LOW

#### L1. Untrusted FDT pointer can cause integer overflow and early panic
- **Severity:** LOW
- **File:** `kernel/src/mem.rs`, `init`, `let fdt_start = fdt.div_ceil(PAGE_SIZE) * PAGE_SIZE;`
- **Description:**  
  `fdt` comes from the bootloader without validation. If a hostile or buggy bootloader passes a value near `usize::MAX`, `fdt.div_ceil(PAGE_SIZE) * PAGE_SIZE` can overflow and panic (overflow checks are enabled) before the kernel produces useful boot output. The subsequent `saturating_add`/`saturating_sub` are safe, but the initial multiplication is not.
- **Fix:**  
  Use saturating arithmetic for the multiplication, or clamp `fdt` to the RAM range before computing the reservation.

#### L2. Trap vector header claims reentrancy, but implementation halts on any nested trap
- **Severity:** LOW
- **File:** `kernel/src/arch/riscv64.S`, top-of-file comment vs. nested-detection code (`bne t6, t0, 4f`)
- **Description:**  
  The header comment says the trap path is reentrant (“每层陷阱向下压新帧,并把 sscratch 更新为新帧底”), but the implementation explicitly treats any second trap during an active handler as fatal and halts. This is not a current bug because the timer ISR runs with interrupts disabled, but it will become a problem if M1 enables nested traps (e.g. a page fault inside a trap handler) or if a synchronous exception occurs while handling another exception.
- **Fix:**  
  Either update the documentation to reflect the current non-reentrant design, or implement true nested-trap support on the trap stack with bounded depth and proper sscratch management.

#### L3. `allocator()` returns a new `&'static mut` on every call, creating a latent aliasing hazard
- **Severity:** LOW
- **File:** `kernel/src/mem.rs`, `fn allocator()`
- **Description:**  
  The function uses `(&raw mut ALLOCATOR).as_mut().unwrap()` to create a fresh mutable reference to the global allocator each time. Current code uses it only in short, non-overlapping scopes, so it is not UB today. However, any future code that holds one `allocator()` reference and calls another function that also invokes `allocator()` will create two `&mut` references to the same object, which is undefined behavior. This will become more likely once the allocator is exposed to interrupt or multi-core contexts.
- **Fix:**  
  Use an abstraction like `OnceLock<Mutex<BuddyAllocator>>` (once lock support is available) or a `critical-section`-based guard, ensuring a single mutable reference is obtained under a proper lock/atomic protocol.

#### L4. Frame validation permits a second-level frame pointer to pass (if reached directly)
- **Severity:** LOW
- **File:** `kernel/src/arch/riscv64.rs`, `trap_handler` frame-pointer check
- **Description:**  
  The bounds check ensures `f` is within `[bottom, top - frame_bytes]`, but it does not require `f == top - frame_bytes`. A nested frame pointer (e.g. `top - 2*frame_bytes`) would pass. The assembly currently halts on nested traps before calling `trap_handler`, so this is not reachable today. If future changes allow nested traps, a corrupted or secondary frame could be accepted.
- **Fix:**  
  Tighten the check to `f != top - frame_bytes` (or a whitelist of valid frame bases) until nested support is deliberately added.

### INFO

#### I1. UART base and RAM size are hardcoded QEMU virt values
- **File:** `kernel/src/uart.rs` (`UART_BASE = 0x1000_0000`), `kernel/src/mem.rs` (`RAM_START`, `RAM_END`)
- **Description:**  
  The author already documents this as a known limitation. It will not work on real hardware without FDT-driven discovery. This is a planned M1/M1.5 task, but it is worth repeating because the current reservation logic depends on `RAM_END` and the FDT pointer.

#### I2. CI does not pin QEMU or OpenSBI versions
- **File:** `.github/workflows/ci.yml`, `Makefile`
- **Description:**  
  The workflow uses `qemu-system-misc` from `ubuntu-latest` and `-bios default`. Different QEMU/OpenSBI versions may place the FDT at different addresses or behave slightly differently. This could cause intermittent boot-test failures or hide hardware-specific bugs.
- **Fix:**  
  Pin `qemu-system-riscv64` to a known version (e.g. via a container or explicit download) and, if possible, a known OpenSBI firmware image instead of `-bios default`.

#### I3. The allocator reserves a fixed 1 MiB for the FDT, regardless of its actual size
- **File:** `kernel/src/mem.rs`, `FDT_RESERVE_SIZE`
- **Description:**  
  A malicious or unusual bootloader could supply an FDT larger than 1 MiB, causing the tail of the device tree to be allocated and overwritten. The current kernel does not parse the FDT, so this is not exploitable yet, but M1 will introduce parsing.
- **Fix:**  
  Parse the FDT header (magic and totalsize) before initializing the allocator, and reserve the actual size plus a small margin.

## What looks correct

- **Entry sequence** (`kernel/src/entry.S`, `kernel/src/main.rs`):  
  Clearing `sstatus.SIE`, `satp`, `stvec`, `sscratch`, and flushing the TLB before touching memory is correct and prevents bootloader leftovers from causing early traps or stale translations.

- **UART DLAB ordering** (`kernel/src/uart.rs`):  
  Setting DLAB before writing divisor registers and clearing DLAB before writing IER is the correct and often-missed NS16550 initialization sequence. The `fence iorw, iorw` barriers between critical MMIO writes are appropriate for RISC-V memory ordering.

- **Buddy allocator core** (`kernel/src/mem.rs`):  
  The intrusive free lists, per-page metadata, alignment checks, and double-free/interior-pointer rejection are solid. The self-test exercises allocation, freeing, coalescing, alignment, double-free, and interior-free, which is a good smoke test for this stage.

- **Trap frame save/restore** (`kernel/src/arch/riscv64.S`):  
  The register save ordering, `gp` preservation/reload, `sscratch` management, and `sstatus`/`sepc` restoration are carefully done. Saving the original `t6` via `sscratch` before clobbering it is correct.

- **Panic handler** (`kernel/src/panic.rs`):  
  The double-panic guard, interrupt disabling before output, CPU state dump, and stack watermark diagnostics are well-designed for a no_std kernel. Byte-wise volatile scanning avoids provenance problems.

- **CI smoke test** (`Makefile`, `.github/workflows/ci.yml`):  
  Running the kernel for a full 10 seconds and asserting multiple `uptime:` lines is a good way to catch timer interrupt death, and avoiding `grep -q` early termination is correct.

- **Linker script symbol boundaries**:  
  Keeping the boot/trap stacks separate from the `_kernel_end` image boundary and defining `_alloc_start` after them is clean and prevents the allocator from mistakenly managing stack memory.

## Blind spots & suggestions for the next milestone (M1: trap handling)

1. **Trap vector must be hardened before user mode exists.**  
   The current non-reentrant, halt-on-nested-trap design is acceptable for M0, but M1 needs a clear policy: bounded nested traps on a dedicated trap stack, or documented non-reentrancy with all handlers running with interrupts off. The pre-validated write issue (M3) must be fixed regardless.

2. **FDT parsing should occur before allocator init.**  
   Once UART base/RAM size are derived from the device tree, the allocator will need to know actual RAM regions and reserve the real FDT size. The current startup order (`mem::init` before any FDT parse) will need to change. Consider moving FDT parsing into early boot with minimal, non-allocating code.

3. **Introduce a proper concurrency model for the allocator and logger.**  
   The next milestone will enable timer interrupts and possibly multiple harts. The allocator’s `allocator()` API must become lock-protected, and the logger’s UART output must become ISR-safe (e.g. per-context buffers or an early console lock). The current no-lock assumptions are documented but will break quickly.

4. **Watchdog or reset on fatal boot failures.**  
   If `sbi_set_timer` fails, or if the initial trap vector install fails, the kernel should not enter a silent idle loop. M1 should define a “boot failure” state that outputs a clear error and halts, rather than appearing to boot.

5. **Review SBI register clobber assumptions.**  
   Before adding more SBI calls (e.g. for IPI, hart management, or legacy timer), verify the exact calling convention and ensure all caller-saved registers are either preserved or declared as clobbered.

6. **Test with non-aligned FDT pointers and non-multiple RAM sizes.**  
   Both are common on real hardware and would have caught H1 and M2 early. QEMU can be configured with different RAM sizes, and the FDT pointer can be manipulated in a custom bootloader or SBI shim for negative testing.

7. **Watch for orphan sections as the kernel grows.**  
   The current linker script explicitly lists many sections, but without `--orphan-handling=error`, any new section emitted by future Rust/LLVM versions could be silently placed outside kernel boundaries. Reconsider enabling `--orphan-handling=warn` or a custom check that fails CI on unexpected orphans.

8. **Preserve user interrupt enable bits when `sret` is used to return to U-mode.**  
   The current restore path clears only `SIE` (bit 1) via `andi -3`, which is correct for S-mode returns, but future U-mode support will need to ensure `UIE` (bit 0) and `UPIE` are handled according to the RISC-V privileged spec.

9. **Beware of nested-trap write-before-validation when implementing reentrancy.**  
   If nested traps are later supported, the trap stack pointer can be influenced by deeper levels. The validation order must be fixed first (M3) to avoid arbitrary writes from a corrupted `sscratch`.

10. **Expand self-test coverage for edge cases.**  
    Add tests for allocations near the ends of RAM, around reserved regions, and for out-of-range or non-aligned `free` calls under relaxed ordering. The current self-test is good, but it passes only for the QEMU 128 MiB layout.
