# Independent AI audit (deepseek-v4-pro)

- date: 20260819-122344
- model: deepseek-v4-pro
- tool: scripts/ai_audit.py (external reviewer, not the author)

## Executive summary

I reviewed all 20 source files in depth, tracing the boot path, trap machinery, scheduler state machine, both allocators, the FDT parser, and concurrency primitives. The code is generally well-structured and unusually well-commented, with many real fixed issues from the cited audit history accurately reflected in code comments.

However, I found **two CRITICAL correctness bugs** that are not exercised by the current QEMU smoke tests, plus several HIGH/MEDIUM issues that will bite on real hardware or in M2.

The most severe new findings:

1. **The buddy allocator leaks all memory beyond the first 16 MiB block whenever the FDT has any reserved region** (which is always, since the FDT reserves itself on every boot). Only the first `order-12` block is ever free-listed on the reserved path; `page_count()` reports the real total, masking the loss. The selftest still passes because it only touches that first block.
2. **The cooperative scheduler loses the current thread's context when switching to a "frame-only" (preempted-but-not-yet-resumed) thread.** `do_switch` picks `frame_restore` when the target's `ctx` is invalid, but `frame_restore` never saves the outgoing thread's context. The outgoing thread is marked `ctx_valid = true` while its `Context` still contains stale data, so when it is later resumed it restores an old register/stack state and re-executes work (double increments, corrupted locals).

These two alone make the kernel unsafe beyond the current narrow test corpus. Details, line references, and fixes follow.

---

## Findings (severity-ranked)

### CRITICAL

#### [NEW] C1. Buddy allocator only free-lists the first 16 MiB block when any reserved region exists
- **File:** `kernel/src/mem.rs` — `BuddyAllocator::init` / `carve`
- **Description:** In `init`, when `reserved.0 < reserved.1` (the non-empty-reserved branch — which is **always true on QEMU and any FDT-booted board**, because `Fdt::parse` unconditionally adds the FDT's own `[fdt_addr, fdt_addr+total_size)` to `reserved`), the code executes exactly one call: `self.carve(0, MAX_ORDER, reserved);`. `carve` only processes the block `[0, 2^MAX_ORDER)` (one 16 MiB block). The remaining top-level blocks (`[4096,8192)`, `[8192,12288)`, …, `[28672,32768)` in page indices) are never pushed onto any free list and are never re-visited. Their metadata remains `{order: 0, used: false}` from the init loop, but they are simply **lost to the allocator**. With the QEMU numbers in the README (base aligned up to `0x81000000`), the kernel actually gets ~16 MiB usable while `page_count()` continues to report 28,672 pages / 114,688 KiB. The self-test passes only because it exhausts a single 16 MiB block and reads its own report back. On any real workload (M2 user processes, page-table-heavy operations) this will surface as a mysterious OOM.
- **Concrete fix:** In the reserved branch, loop over all top-level blocks: `for base_idx in (0..padded).step_by(1 << MAX_ORDER) { self.carve(base_idx, MAX_ORDER, reserved); }`, mirroring the no-reserved branch's loop. Also assert (not just debug_assert) that `padded <= MAX_PAGES`, and consider reporting the actually-free amount instead of `real_count` in the smoke log.

#### [NEW] C2. Cooperative switch to a frame-only thread loses the outgoing thread's context
- **File:** `kernel/src/sched.rs` — `yield_`, `block_current`, `switch_target`, `do_switch`
- **Description:** In `yield_`/`block_current`, the current thread sets `ctx_valid = true; frame_valid = false` and is enqueued. `pick_next(true)` may then select a thread with `ctx_valid = false; frame_valid = true` (a thread that was preempted by the timer and not yet resumed). `switch_target` computes `use_frame = !next.ctx_valid = true`, and `do_switch` calls `arch::frame_restore(new_frame)`. `frame_restore` performs a pure sret restore — **it never saves the outgoing thread's current registers into its TCB `Context`**. So:
  - The outgoing thread's live `ra`/`sp`/`s0-s11` are discarded at the switch.
  - Its TCB `ctx` still holds the save point of its *previous* cooperative switch (stale).
  - `ctx_valid = true` on that thread now lies — the `Context` is not fresh.
  - When the thread is later selected via the cooperative path, `context_switch` resumes it from the stale `Context`, re-executing code from an earlier program point (e.g., re-running `fetch_add` + `yield_` loop iterations, duplicating side effects, and corrupting stack-local state).
  This is not just theoretical: the fixed-point rule `ctx_valid ⇔ ctx data was written by the most recent switch-out` is violated exactly on the frame-restore path. Current tests avoid it only because frame-only threads arise exclusively from busy-loop preemption and are cooperatively selected only from `exit()` (where the outgoing thread's state doesn't matter) or from idempotent main-loop yields (where re-running a `guard += 1` is harmless). Any M2 workload where a thread blocks/yields immediately after a preempted peer will hit real corruption.
- **Concrete fix:** Add a context-save-only primitive (e.g., `context_save(old_ctx)` in assembly that stores `ra/sp/s0-s11` and returns), and call it in `do_switch` before `frame_restore` when `use_frame` is true (or, equivalently, make `frame_restore` take the old `Context` pointer as a second argument and save first). Also ensure `ctx_valid` is only set after the save actually happens. If not fixed, make the selection logic in `pick_next` with `need_ctx=true` prefer `ctx_valid` candidates so the lossy path is never taken by `yield_`/`block_current` — but that trade-off must be revisited for the stranding case the comments mention.

### HIGH

#### [NEW] H1. Stack/trap-stack guard page unmapping silently fails if the stack region crosses a 2 MiB boundary
- **File:** `kernel/src/mmu.rs` — `init`
- **Description:** `init` 4K-maps only `[kernel_end, kernel_super_end)`, then 2 MiB-maps the rest of RAM from `kernel_super_end` onward. The `.stack`/`.trap_stack` region begins at `_kernel_end` and extends ~88 KiB past it. If `_kernel_end` is within 88 KiB of the next 2 MiB boundary (or if `_kernel_end` is exactly 2 MiB-aligned, so `kernel_end == kernel_super_end` and the 4K tail-mapping is skipped entirely), the guard pages (`_stack_guard`, `_trap_stack_guard`) fall inside a 2 MiB leaf. `ensure_table` then returns `Err` (leaf cannot be descended), and the code does `let _ = unmap_4k(...);` — **discarding the error**. Guard pages silently remain mapped RW, and a stack overflow corrupts the adjacent region instead of faulting. With the current kernel size this happens to work, but any growth to ~1.9 MiB+ (or any linker change that places stacks past a 2 MiB boundary) silently disables the advertised protection.
- **Concrete fix:** Assert `unmap_4k(...).is_ok()` for both guard pages, or explicitly 4K-map the full `[kernel_end, align_up(kernel_end + stack_area_size, 2MiB))` range before guard unmapping.

#### [NEW] H2. `unmap_4k` does not flush the TLB
- **File:** `kernel/src/mmu.rs` — `unmap_4k`
- **Description:** The public `unmap_4k` writes PTE=0 but never executes `sfence.vma`. During `init` this is harmless (paging not yet enabled), but the M1.5 milestone explicitly exposes `unmap_4k`/`tlb_flush` as the M2 user-mapping interface. Any post-boot caller that unmaps a page and then expects traps (or hands the page to another address space) will observe stale TLB hits — an information-leak/correctness bug on real hardware (QEMU's TCG TLB is more forgiving).
- **Concrete fix:** Either perform `sfence.vma` inside `unmap_4k` (with `vaddr,vaddr` range), or document an explicit "callers must call `tlb_flush` afterwards" contract and provide a combined `unmap_4k_flush` for the common case.

#### [NEW] H3. Scheduler `pick_next` fallback can return a Blocked current thread
- **File:** `kernel/src/sched.rs` — `pick_next`
- **Description:** The fallback path is:
  ```
  if self.threads[self.current].state == ThreadState::Exited { self.idle } else { self.current }
  ```
  `block_current` sets its own state to `Blocked` *before* calling `pick_next(true)`. If the ready queues are empty (shouldn't happen today because `idle` is always Ready; but it's a fragile invariant once multi-core or thread-affinity lands, or if an audit changes the idle path), the fallback returns the Blocked current. `switch_target(cur, cur)` then performs a context self-switch (register save/load of the same `Context`, effectively a no-op), and `block_current` proceeds with the thread still marked `Blocked`. From then on, repeated `block_current` calls can spin forever without yielding to anyone — a livelock.
- **Concrete fix:** Make the fallback always choose `self.idle` (or `panic!/halt` if no Runnable candidate exists), never a Blocked current. Add a runtime invariant check that a Blocked/Running thread is never returned from `pick_next` unless it can actually run.

#### [NEW] H4. SBI `set_timer` fallback omits t0–t6 clobbers
- **File:** `kernel/src/sbi.rs` — `set_timer`
- **Description:** The `asm!` block lists only `a0`–`a7` as `lateout`s and leaves `t0`–`t6` unmentioned. Under the RISC-V calling convention, the SBI ecall handler may clobber all caller-saved registers, including `t0`–`t6`. Rust `asm!` assumes unlisted registers are preserved, so the compiler may keep live values in `t0`–`t6` across the ecall; OpenSBI is free to destroy them → miscompilation/UB. The function is currently dead code (SSTC is used), but it is documented as the intended fallback for non-SSTC boards (D17), so the latent bug matters.
- **Concrete fix:** Add `clobber_abi("C")` (or explicitly `out("t0") _ ... out("t6") _`) to the `asm!` block, and enable/use this path before relying on it.

#### [NEW] H5. FDT parser uses `total_size` rather than `off_dt_struct + size_dt_struct` as the structure block bound
- **File:** `kernel/src/fdt.rs` — `parse`
- **Description:** `let struct_end = self.off_struct.saturating_add(self.total_size - self.off_struct);` effectively sets `struct_end == total_size`, allowing token parsing to run past the end of the structure block into the strings block if the FDT structure block lacks a proper `FDT_END`. All reads remain bounds-checked (so no UB), but property `reg`/`compatible` values could be interpreted from string bytes, yielding attacker-influenced board parameters (RAM range, UART base, reserved ranges) from a malformed FDT.
- **Concrete fix:** Bound the loop with `min(off_struct + size_dt_struct, total_size)` (or just `off_struct + size_dt_struct` after validating it), and reject/ignore FDTs whose structure block doesn't terminate with `FDT_END` before that bound.

#### [NEW] H6. `heap::dealloc` does not validate slab slot alignment/address before pushing to the free list
- **File:** `kernel/src/heap.rs` — `dealloc`
- **Description:** For a slab-class page, `dealloc` trusts that `ptr` is exactly a slot start: it overwrites the first word of the slot with the current free-list head and links it in. A caller-supplied pointer that lands in a slab page but is not slot-aligned (e.g., an off-by-one error, or M2 code deallocating an interior pointer) silently corrupts the slab's free list. The next allocation then hands out a misaligned/overlapping pointer — the classic heap-exploit primitive. `mem::free_pages` has strong validation; the slab path has none. Currently all call sites are safe Rust, but the allocator is the wrong place to assume that.
- **Concrete fix:** In the slab branch of `dealloc`, verify `(ptr as usize - page) % class_size == 0`, `ptr` is >= `page + class_size` (past the header), and the resulting slot is within the page; panic with a diagnostic otherwise (consistent with the large-object path).

### MEDIUM

#### [NEW] M1. Kernel threads (16 KiB stacks) have no guard pages
- **File:** `kernel/src/sched.rs` — `THREAD_STACK_SIZE` / `spawn`
- **Description:** Boot/trap stacks have unmapped guard pages (M1.5 D4), but per-thread stacks are ordinary heap allocations. A runaway thread recursion silently overflows into adjacent heap memory (which could be another thread's TCB-adjacent stack, slab metadata, or a large-object block), causing non-deterministic corruption rather than a diagnosable fault.
- **Concrete fix:** Either allocate thread stacks with a leading/trailing unmapped page, or (simpler for M1.5) add an explicit stack-depth watermark/limit check on `yield_`/`block_current` before it is too late, and document the residual risk for M2.

#### [NEW] M2. `board::init_from_fdt` validation accepts RAM sizes that later panic in `mmu::init`
- **File:** `kernel/src/board.rs` / `kernel/src/mmu.rs`
- **Description:** `board.rs` accepts 1 MiB ≤ `ram_size` ≤ 1 GiB (any value), and `ram_start` only needs 4 KiB alignment. `mmu::init` asserts `ram_start` and `ram_end` are 2 MiB-aligned. A FDT reporting e.g. 17 MiB RAM (not a multiple of 2 MiB) passes board validation and then panics with a late, confusing message about Sv39 alignment. Similarly, 4 KiB-aligned-but-not-2MiB-aligned RAM starts pass `board` but fail `mmu`.
- **Concrete fix:** Validate 2 MiB alignment in `board::init_from_fdt` (and fall back to defaults if invalid), or explicitly support non-2MiB RAM by mapping the tail with 4 KiB pages. At minimum, document the limitation in `board.rs`.

#### [NEW] M3. `Fdt::new` only enforces 4-byte alignment, spec requires 8-byte, and reads a Rust reference over MMIO-like external memory
- **File:** `kernel/src/fdt.rs` — `Fdt::new`
- **Description:** (a) The validity check is `fdt.is_multiple_of(4)`; the FDT spec requires 8-byte alignment. A malicious bootloader can pass a 4-aligned-but-not-8-aligned pointer that passes validation, leading to misaligned `u64` reserve-map reads (the parser uses individual byte reads via `be32`, so it is mostly tolerant — but the header/reference creation still makes assumptions). (b) `let hdr = unsafe { &*(base as *const FdtHeader) }` creates a typed Rust reference to memory written by firmware outside Rust's provenance; it is a recognized grey-area pattern, but reading fields via `be32_val` byte arrays instead would remove any lingering aliasing/alignment concerns.
- **Concrete fix:** Check 8-byte alignment; replace the `&*(...)` reference with byte-array reads to construct header fields.

#### [NEW] M4. `FDT` parser's node-name tracking is not unwound on `FDT_END_NODE`
- **File:** `kernel/src/fdt.rs` — `parse`
- **Description:** `current_node` is only overwritten on `FDT_BEGIN_NODE`. After an `FDT_END_NODE`, properties belonging to the parent node would be attributed to the just-finished child. This happens to work for QEMU's DTB layout, but a conforming FDT that places a root or sibling property after a child node's end would be misparsed (e.g., a `compatible` property on a node named `serial@...` after its descendant ends could be attributed incorrectly). Additionally, truncating node names to 63 bytes silently changes the effective node name.
- **Concrete fix:** Keep a small node-path stack (or re-read the parent name), and reject/ignore node names longer than 63 bytes instead of truncating.

#### [NEW] M5. `fdt::read_string` has an unconstrained lifetime
- **File:** `kernel/src/fdt.rs` — `read_string`
- **Description:** `fn read_string<'a>(&self, ...) -> Option<&'a str>` — the `'a` is unconstrained, so the returned `&str` can be held arbitrarily long by the caller (`handle_prop` uses it transiently, so it's currently safe in practice). This is a pattern that would be rejected by stricter lints (`elided_lifetimes_in_paths` analogue) and is a fragility trap for future edits.
- **Concrete fix:** Bind the lifetime to `&self`, or return an owned `[u8; 32]`-style probe result.

#### [NEW] M6. `woken` flag is level-based and causes spurious blocking bounce
- **File:** `kernel/src/sched.rs` — `block_current`/`wake`
- **Description:** `wake` sets `woken = true` unconditionally; when the target was `Blocked`, it is enqueued and later selected, but the flag remains set while the thread runs. The next `block_current` call spuriously consumes the stale flag and returns without blocking. The mutex/condvar loops re-check conditions, so this is currently benign, but it is an easy trap for future synchronization code, and it should be documented precisely (spurious-wake semantics) rather than implied by the C5 comments.
- **Concrete fix:** Clear `woken` in `pick_next` when a thread transitions from `Ready` to `Running` (or treat the flag as an edge by pairing it with the enqueue operation), and add a comment.

#### [NEW] M7. `ticks_run`/timer deadline can storm ticks after long interrupt-disabled stretches
- **File:** `kernel/src/arch/riscv64.rs` — `enable_timer`/`trap_handler` timer path
- **Description:** The deadline is advanced by one fixed interval per tick (`fetch_add(interval) + interval`), not clamped to `now`. If the system runs with interrupts disabled for longer than several intervals (e.g., future long critical sections or extensive M2 setup), `stimecmp` stays in the past for several consecutive ticks; the timer ISR refires immediately after each sret until the deadline catches up. This produces a rapid tick burst (and, more importantly, a preemption burst). QEMU tolerates it; real hardware may spend a long time thrashing the ISR after boot.
- **Concrete fix:** On each tick, set the next deadline to `max(current_deadline + interval, get_time() + interval)` in the ISR (or compute a catch-up stride), and keep ticks counted per actual interrupt rather than per missed deadline.

#### [NEW] M8. `mem::init` reserved-region handling is a single conservative range
- **File:** `kernel/src/mem.rs` — `init`
- **Description:** All reserved regions are merged into one `[rs, re)` interval (`rs = min(starts); re = max(ends)`). Any gap between two reserved regions (e.g., an OpenSBI entry at the bottom and the FDT at the top of the allocation range) is over-reserved and lost. QEMU's reserve map is usually empty so this doesn't bite today, but a real board with two distinct reserved areas inside the allocatable range will lose up to the entire gap.
- **Concrete fix:** Preserve the (up to 8) disjoint reserved intervals and have `carve` handle each independently (or pass a sorted list). The existing `BoardParams::reserved` fixed array is already there to support this.

### LOW

- **L1.** [NEW] `arch/sbi.rs` `set_timer` is dead code but has the t-clobber hazard (see H4) — if anyone wires up the fallback, the bug fires. Also `SBI_EXT_TIME` const is never validated against an SBI probe.
- **L2.** [NEW] `sched.rs` `pick_next`'s `need_ctx=true` path accepts `frame_valid` candidates even for the *current* (yielding) thread if it is also frame-valid — but the yield path sets `frame_valid=false` first, so this is currently okay; it is a fragile implicit ordering that should be asserted.
- **L3.** [NEW] `kernel_main`/`sched::init` never frees idle's allocated 16 KiB `KernelStack`; it is kept in `Thread.stack` forever (memory waste, not a leak in the dynamic sense, but worth a comment).
- **L4.** [NEW] Thread initial `Context`/frame leave `tp = 0`. Single-core doesn't care, and the first preemption refreshes the frame from live `tp=hartid`; on multi-core (M2) a thread first scheduled via the cooperative path inherits the boot hart's `tp` only by accident. Should be explicitly initialized from `tp` (or a hart-local source).
- **L5.** [NEW] `logger`'s "ISR must not log" rule is only a comment convention; no compile-time or runtime enforcement. A future `info!` in `on_tick` or a panic path inside an ISR would corrupt output or deadlock the UART.
- **L6.** [NEW] `GlobalAlloc::alloc` panics on OOM rather than returning null + `handle_alloc_error`; it works in this kernel but deviates from the documented contract and hides allocation-site context.
- **L7.** [NEW] `TIMER_DEADLINE` (`arch/riscv64.rs`) is written but never read. It's dead state; either use it to implement the catch-up logic from M7 or remove it.
- **L8.** [NEW] `heap::self_test` step 6 computes `slots` manually; it assumes the entire page (minus header) is slot space, which matches `new_slab` — but this test would silently pass even if `new_slab` changed the layout, because it uses the same formula.
- **L9.** [NEW] `fdt::parse` truncates `current_node` to 63 bytes and doesn't track the actual buffer length when `>= 63` (the code adds a NUL at index 63, which is safe but makes the truncation semantics implicit).
- **L10.** [NEW] `entry.S` clears `satp` and does `sfence.vma` but no `fence.i` — fine on QEMU/OpenSBI fresh boot, but a warm reboot with stale I-cache could fetch stale code after the mode/context change. Add `fence.i` after the `sfence.vma` for real-hardware robustness.
- **L11.** [NEW] `uart::init_hw` uses a fixed divisor (12) for a 1.8432 MHz reference clock; the README/CI target works, but the module docs already acknowledge this. The FDT may provide a different `clock-frequency` for the UART node, which the parser currently ignores.
- **L12.** [NEW] `Mutex::lock` contains an unreachable second-fast-path branch (`if !self.locked.swap(true)` after pushing into waiters), because interrupts are off and the first swap already set `locked=true`. It's harmless defensive code but misleading; remove or comment it as dead.
- **L13.** [NEW] `sched::pick_next`'s `round = q.len()` loop keeps candidates that fail the validity check but *doesn't* re-add threads whose `state != Ready` — currently only Exited threads can reach this, which is correct, but a future Blocked thread left in the queue would be silently dropped; consider an explicit `debug_assert!(state == Ready || state == Exited)` here.
- **L14.** [NEW] `README` and `cpu.rs` claim CPU/ISA capability detection; the implementation is a stub that always returns None (D17 acknowledges the fallback gap, but the README's RVA23 P1 wording overstates the current state).
- **L15.** [NEW] `fdt::parse`'s `read_string`/property reads use `read_volatile` on every byte, which prevents compiler hoisting; this is correct but also means the parser is noticeably slower than necessary on a large FDT. For M2 boot-time impact, consider non-volatile reads after validating the FDT region is trusted RAM.
- **L16.** [NEW] `kernel_main`'s `kernel_main` doc comment still says the FDT pointer is "当前阶段仅记录" (only recorded), which is stale — the FDT is fully parsed by M1.5. Update the comment.
- **L17.** [NEW] `mmu::init` maps the region below the kernel (`OpenSBI` space) `RW` (no X) but PMP/OpenSBI may forbid S-mode writes there; it's harmless today but confusing — consider mapping it `R` (or documenting why RW is needed).
- **L18.** [NEW] The `sync.rs` module header says `Mutex` waiters use `VecDeque` and block on contention; the `SpinLock` internal spin uses a `Relaxed` load in the inner loop, which is fine on RISC-V coherence but the waiting thread never issues `Yield`/`Pause` recommendations for hardware (use `core::hint::spin_loop()` already — nothing to fix, just a note for multi-core scaling).

## What looks correct (so the author knows what not to change)

- **Boot arbitration & BSS-clearing sequence** (`entry.S`): the `.data`-anchored `BOOT_LOCK` (explicitly not in `.bss`), the `amoswap` acquire + full `fence rw,rw`, and clearing `[_bss_start, _trap_stack_top)` are all correct and multi-hart-safe.
- **Trap frame ABI:** GPR indices in `riscv64.rs` match the assembly save order exactly, including the ticklish t0/t6 rescue dance; the compile-time `TRAP_FRAME_WORDS * 8 == 288` assert and the shared `FRAME_WORDS` constant are good hardening.
- **SSTC timer and IRQ-safe `SpinLock`:** the `csrrci` read-and-clear for `irq_save`, the `Release`/`Acquire` pairing, and the lock-retry logic are all sound. The ISR path is genuinely zero-allocation.
- **Lost-wake protection:** the `woken` flag + `remove_from_ready` race closure in `block_current` is correct (spurious continuations are handled by the mutex/condvar loops). The audit 15 round's C5 fix is working as designed.
- **`mem::free` validation:** rejecting non-head pages, double-frees, and out-of-range addresses is robust; the "block-header-only metadata" optimization does not leave an exploitable path because interior pages cannot have block-aligned indices.
- **Linker script discipline:** NOLOAD stacks, `_alloc_start` red line, and `/DISCARD/` for `.eh_frame`/`.comment` are all correct. Guard pages are physically reserved.
- **FDT `add_reserved` merge logic** is correct within its fixed 8-slot array, including the swap-and-shrink deletion.
- **MMU PTE flag constants** (V/R/W/X/A/D, PPN shift/mask, Sv39 satp mode) are correct, and the "cannot descend through a leaf" check in `ensure_table` is a real, correct hardening fix.

## Blind spots & suggestions for the next milestone (M2: user processes / IPC / capabilities / multi-core)

1. **Fix C2 before M2:** User processes will yield/block constantly while preempted peers are frame-only. The current tests' idempotent loops mask the bug; a single producer/consumer pair with a busy preempted worker will exhibit it. Budget time for a context-save primitive redesign and a regression test that forces the `ctx_valid=false ∨ frame_valid=false` interleaving deterministically.
2. **Fix C1 before M2:** User address spaces need real page budgets; the 16 MiB illusion will fail the first time a process maps more than a handful of pages. Add an assertion in `mem::self_test` that all top-level blocks are reachable (e.g., sum of free pages + used pages == real_count after init) so this class of leak can never regress silently.
3. **Introduce per-thread stack guards (M1)** and **TLB-flush-correct `unmap_4k` semantics (M2)** now, before user mappings become the primary consumer.
4. **Real hardware readiness:** the SBI timer fallback, FDT UART clock-based divisor, `fence.i` after satp change, and non-SSTC platform detection (D17) should all move from "deferred" to "implemented and tested" before any physical board bring-up.
5. **Multi-core scheduler:** D7/D8/D9/D19 will require a careful re-audit of the `ctx_valid`/`frame_valid` invariant, because per-hart ready queues or migration can produce Blocked/Ready/idle fallback states the current single-core `pick_next` has never seen. The `tp` initial-frame issue (L4) becomes real on the first secondary hart.
6. **Security perimeter:** Before any user code runs, close the slab-pointer validation gap (H6), enforce `heap::dealloc` range checks for *all* deallocation paths, and zero pages before handing them to user space (D10, already in DEFERRED).
7. **Test coverage:** add a dedicated "memory exhaustion" test that verifies `page_count()` and the actual free/used accounting match after reserving multiple disjoint FDT regions, and a fault-injection test that deliberately passes malformed FDTs from the bootloader (to exercise the parser bounds paths).
