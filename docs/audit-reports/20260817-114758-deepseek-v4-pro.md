# Independent AI audit (deepseek-v4-pro)

- date: 20260817-114758
- model: deepseek-v4-pro
- tool: scripts/ai_audit.py (external reviewer, not the author)

## Executive summary

The codebase is substantially beyond the stated “M0 boot chain” scope — it contains an M1 trap/timer/buddy/slab/Sv39/scheduler/sync implementation. The boot path itself is carefully ordered and generally well-documented. However, several serious defects are present that are mostly latent on QEMU because QEMU zero-fills RAM, ignores UART baud timing, and the current selftests do not actually exercise timer-driven preemption.

The most important issues are:

1. **Slab allocator double-allocation** when a size class pages overflows.
2. **Boot lock likely placed in `.bss`**, despite being used before BSS is cleared; this is fatal on real hardware with non-zero RAM.
3. **The preemption path is fundamentally broken** in several interacting ways: wrong frame size, corrupted `sscratch`, missing SPP, and inconsistent `ctx`/`frame` resumption.
4. **Heap page path misaligns allocations** for `align > 8 && align <= PAGE_SIZE`.
5. **Sync primitives have lost-wake races and a Condvar double-unlock.**

None of these are directly exposed by the current CI selftests, which is itself an important finding.

## Findings (severity-ranked: CRITICAL / HIGH / MEDIUM / LOW / INFO)

### CRITICAL-1: Slab allocator returns the same slot twice when a size-class page fills up

**File:** `kernel/src/heap.rs`, `slab_alloc()` — approximately line 98–104 in the sampled file.

In the full-page branch the code does:

```rust
if slot == usize::MAX {
    let nh = unsafe { self.new_slab(idx) };
    let nhdr = unsafe { &mut *nh };
    nhdr.next = head;
    self.classes[idx].head = nh;
    return nhdr.free_list as *mut u8;   // <-- returns head without unlinking
}
```

`new_slab()` sets `free_list` to the first slot in the new page. The full-page path returns that same `free_list` value **without advancing it**. The next allocation from this class will also see the same first slot and hand it out again. Memory corruption is therefore guaranteed once any slab page fills up and a second page is created.

The current selftest never fills a slab page for a second page in the same class, so CI is green.

**Suggested fix:** after creating `nh`, pop its first free slot:

```rust
let slot = nhdr.free_list;
if slot != usize::MAX {
    nhdr.free_list = unsafe { *(slot as *const usize) };
}
return slot as *mut u8;
```

or otherwise ensure the returned slot is unlinked before being handed out.

### CRITICAL-2: `BOOT_LOCK` is likely placed in `.bss`, but is consumed before BSS is cleared

**File:** `kernel/src/main.rs` (`BOOT_LOCK` static, around line 37) and `kernel/src/entry.S` (boot arbitration, around the `amoswap` block).

`BOOT_LOCK` is declared as:

```rust
#[unsafe(no_mangle)]
pub static mut BOOT_LOCK: u32 = 0;
```

The comment explicitly says it must be in `.data` because it is used before BSS zeroing. However, a zero-initialized static in Rust/LLVM is normally emitted into `.bss`/`.sbss`. The linker script then places it in `.bss`, and the winner hart only zeroes BSS **after** all harts have performed the `amoswap` arbitration.

On QEMU this is hidden because fresh machine RAM is zero. On real hardware, a warm reset or non-zero RAM would make every hart read a non-zero old value from `amo swap`, all take the loser path, and the machine parks forever.

**Suggested fix:** force the symbol into a non-BSS section, e.g.:

```rust
#[unsafe(link_section = ".data.boot_lock")]
#[unsafe(no_mangle)]
pub static mut BOOT_LOCK: u32 = 0;
```

and include `*(.data.boot_lock)` in `.data` in the linker script. Alternatively define it directly in `entry.S` inside `.section .data.boot_lock`.

### CRITICAL-3: Timer-driven preemption path is broken in multiple interacting ways

#### 3a. Frame size mismatch causes out-of-bounds trap-frame read

**File:** `kernel/src/sched.rs` (`FRAME_WORDS`, around top) and `kernel/src/arch/riscv64.rs` (`TRAP_FRAME_WORDS`).

The trap frame is 36 words / 288 bytes:

```rust
const TRAP_FRAME_WORDS: usize = 36; // riscv64.rs
```

but the scheduler uses:

```rust
const FRAME_WORDS: usize = 40;      // sched.rs
```

`on_tick()` does:

```rust
core::slice::from_raw_parts(frame, FRAME_WORDS)
```

so it reads 32 bytes past the 288-byte trap frame and into adjacent memory. This is a live out-of-bounds read whenever preemption is actually triggered.

#### 3b. `sscratch` is restored to the wrong value when switching to a TCB frame

**File:** `kernel/src/arch/riscv64.S`, restore path after `trap_handler` returns.

The assembly always executes:

```asm
addi t0, t6, TRAP_FRAME_SIZE
csrw sscratch, t0
```

For a normal trap, `t6` is the on-trap-stack frame base, so this correctly resets `sscratch` to the trap-stack top. But when `trap_handler` returns a frame pointer from `sched::on_tick()`, that pointer is the address of a `Thread.frame` inside a TCB, **not** a frame on the trap stack. Writing `TCB_frame + 288` into `sscratch` corrupts the trap-stack invariant. The next trap will enter the nested-trap path or write out of bounds, and the system will halt.

This means the first timer preemption that actually switches threads may work, and the next interrupt will hang or corrupt state.

#### 3c. Initial trap frame lacks SPP, so first `sret` to a new thread can switch to U-mode

**File:** `kernel/src/sched.rs`, initial frame setup in `Scheduler::init()` and `Scheduler::spawn()`.

Initial frames set:

```rust
frame[FRAME_SSTATUS] = 1 << 5; // SPIE
```

but they do not set SPP (`bit 8`). On RISC-V, `sret` uses SPP to choose the target privilege mode. SPP = 0 means U-mode, SPP = 1 means S-mode. A preempted thread whose initial frame is used directly would be `sret`-ed into U-mode at `sepc = thread_entry`, causing an immediate instruction/access fault.

#### 3d. `ctx` and `frame` resumption paths are inconsistent

**File:** `kernel/src/sched.rs`, especially `on_tick()`, `yield_self()`, `block_self()`, `exit_self()`.

Cooperative switches save/resume from `Thread.ctx`. Timer preemption copies the live CPU state into `Thread.frame` and resumes from `Thread.frame`. A thread can be descheduled by either mechanism, but there is no per-thread indicator of which representation holds the latest state. If a thread is preempted and later selected by a cooperative `context_switch`, its stale `ctx` is used and the preempted live state is lost. Conversely, a fresh thread selected by preemption uses a partially initialized `frame`.

This is a fundamental state-machine flaw in the hybrid switching design.

**Suggested fix for 3a–3d:** unify thread switching on the full trap frame for all switches, or maintain a per-thread `LastContext` enum and always restore from the correct location. Also always reset `sscratch` to `_trap_stack_top` in the restore path (interrupts are disabled there), use `TRAP_FRAME_WORDS` everywhere, and set SPP on initial frames.

### CRITICAL-4: Heap page allocator misaligns pointers for `8 < align <= PAGE_SIZE`

**File:** `kernel/src/heap.rs`, `page_alloc()`.

The code branches as:

```rust
if align <= mem::PAGE_SIZE {
    unsafe { *(block as *mut usize) = block };
    (block + 8) as *mut u8
} else {
    let aligned = (block + 8).div_ceil(align) * align;
    ...
}
```

`block` is page-aligned, so `block + 8` is only 8-byte aligned. Therefore any `Layout` with `align` of 16, 32, 64, …, 4096 uses the low-align path but receives a pointer that does **not** satisfy `layout.align()`. This violates the `GlobalAlloc` contract and is undefined behavior / misaligned access on real hardware.

The selftest only exercises `align = 8192`, which takes the high-align path.

**Suggested fix:** treat any `align > 8` as needing an aligned offset and reserve enough extra space:

```rust
let needed = if align <= 8 {
    size + 8
} else {
    size + 8 + align
};
```

and then store the block base at `return_ptr - 8`.

### HIGH-1: `Condvar::wait()` double-unlocks the mutex and can lose the wakeup

**File:** `kernel/src/sync.rs`, `Condvar::wait()`.

The implementation does:

```rust
let m = guard.m;
let irq = arch::irq_save();
self.waiters.lock().push_back(sched::current_id());
m.locked.store(false, Ordering::Release);   // manual release
drop(guard);                                 // <-- MutexGuard::drop calls unlock() again
arch::irq_restore(irq);
sched::block_current();
m.lock()
```

`drop(guard)` invokes `MutexGuard::drop`, which calls `m.unlock()`. That second unlock pops and wakes a waiter from the **mutex** wait queue. This is incorrect; `Condvar::wait()` must release the mutex without transferring it to an arbitrary mutex waiter. It also has a lost-wake window: after `irq_restore(irq)` and before `sched::block_current()`, another thread may notify and `sched::wake()` the current thread while its scheduler state is still not `Blocked`; `wake()` only acts on `Blocked`, so the notification is lost.

**Suggested fix:** keep the mutex state release manual and do not call the guard destructor, e.g. `core::mem::forget(guard)`. Then make the “register → release → block” transition atomic with respect to preemption, either by keeping interrupts disabled through `sched::block_current()` or by setting the thread state to `Blocked` before enabling interrupts/wake opportunities.

### HIGH-2: `Mutex::lock()` has a lost-wake race before blocking

**File:** `kernel/src/sync.rs`, `Mutex::lock()`.

The slow path registers the current thread, checks the lock again, then does:

```rust
arch::irq_restore(irq);
sched::block_current();
```

There is a window with interrupts enabled between the failed second check and the transition to `Blocked`. In that window, the lock holder can call `unlock()`, pop this thread from the waiter queue, and call `sched::wake(id)`. `wake()` checks:

```rust
if s.threads[id].state == ThreadState::Blocked {
    s.enqueue(id);
}
```

The current thread is not yet `Blocked`, so the wake is discarded. The thread then calls `block_current()`, becomes `Blocked`, and may never be woken again.

**Suggested fix:** carry the already-disabled interrupt state into `sched::block_current()`, or introduce a `sched::block_current_already_disabled()` path so that registration and blocking are atomic with respect to interruption. The same pattern must be applied to `Condvar::wait()`.

### HIGH-3: Scheduler “preemption” selftest is not actually testing preemption

**File:** `kernel/src/sched.rs`, `self_test()` preemption section, and `kernel/src/main.rs` startup ordering.

The test spawns `test_busy`, which is a busy loop that never yields, and then the main thread spins/yields. However, during `sched::self_test()` and `sync::self_test()`, `arch::irq_enable()` has not been called yet. So timer interrupts are still disabled. The main thread only regains control after `test_busy()` returns and calls `exit()` — that is a cooperative exit, not timer-driven preemption.

The test would pass even if `on_tick()` and the entire preemption restore path were completely non-functional. This is why the critical preemption bugs above are not caught.

**Suggested fix:** run a dedicated preemption selftest only after interrupts are enabled, under a controlled per-thread guard, or inject timer-driven scheduling events explicitly. Add a negative assertion/termination timeout as well.

### HIGH-4: Kernel thread stacks can be misaligned

**File:** `kernel/src/sched.rs`, `Scheduler::spawn()` and `Scheduler::init()`.

Thread stacks are allocated with:

```rust
let stack = alloc::vec![0u8; THREAD_STACK_SIZE].into_boxed_slice();
let sp = stack.as_ptr() as usize + THREAD_STACK_SIZE;
```

The global allocator page path returns `block + 8`, where `block` is page-aligned. The base is therefore only 8-byte aligned, and adding 16 KiB preserves that 8-byte alignment. RISC-V ABI requires the stack pointer to be 16-byte aligned. Real RISC-V cores may fault on misaligned accesses generated by compiled code that assumes ABI stack alignment.

**Suggested fix:** align `sp` down or up to 16 bytes, e.g. `let sp = (stack.as_ptr() as usize + THREAD_STACK_SIZE) & !0xF;` while ensuring the resulting pointer remains within the allocation.

### MEDIUM-1: FDT header fields are read with native endianness

**File:** `kernel/src/mem.rs`, `fdt_size()`.

```rust
let magic = core::ptr::read_volatile(fdt as *const u32);
if magic != 0xD00D_FEED { ... }
let total = core::ptr::read_volatile((fdt + 4) as *const u32) as usize;
```

The flattened device-tree header fields are big-endian by specification. RISC-V here is little-endian, so the magic check will always fail and the code will silently fall back to `FDT_RESERVE_SIZE` (1 MiB). The actual FDT size is never discovered. This is not fatal on QEMU because 1 MiB is conservative for the current small FDT, but it is wrong and can become insufficient or wasteful.

**Suggested fix:** read the 4 bytes and use `u32::from_be_bytes`, or use `read_volatile` on `[u8; 4]` and convert explicitly.

### MEDIUM-2: Slab page-class lookup has no bounds check and `dealloc` trusts the pointer

**File:** `kernel/src/heap.rs`, `slab_class_of()`, `slab_class_set()`, `dealloc()`.

```rust
let page_idx = (page - mem::base()) / mem::PAGE_SIZE;
unsafe { (&raw const SLAB_PAGE_CLASS).cast::<u8>().add(page_idx).read() }
```

There is no check that `page_idx < mem::MAX_PAGES`. In `dealloc()`, `page = (ptr as usize) & !(PAGE_SIZE - 1)` is computed directly from the caller-provided pointer. A freed pointer that is outside managed RAM, corrupted, or attacker-influenced in a future M2 U-mode path can cause an out-of-bounds read and then arbitrary write into the slab free-list header.

**Suggested fix:** add an explicit bounds check in `slab_class_of/set` and make `dealloc` return/panic safely for invalid page indexes before dereferencing anything.

### MEDIUM-3: `page_alloc()` silently clamps order and can under-allocate

**File:** `kernel/src/heap.rs`, `page_alloc()`.

```rust
let block = mem::alloc_pages(order.min(mem::MAX_ORDER))
    .expect("kernel heap: page OOM");
```

For very large layouts, `needed` may require more than `MAX_ORDER` pages. The code still requests a 16 MiB block. The subsequent alignment arithmetic can then write the block-base pointer outside the allocated block or otherwise overrun memory. It should detect that the required order exceeds `MAX_ORDER` and fail cleanly / panic as OOM before writing anything.

### MEDIUM-4: Trap entry writes to the frame before validating `sscratch`

**File:** `kernel/src/arch/riscv64.S`, `trap_vector` entry.

The first actions after obtaining the swapped value are:

```asm
addi t6, t6, -TRAP_FRAME_SIZE
sd t0, 4*8(t6)
csrr t0, sscratch
sd t0, 30*8(t6)
```

and only later are the nested-trap and trap-stack bounds checked. If `sscratch` has been corrupted, this writes 16 bytes to an arbitrary `sscratch - 288` address before any containment logic runs. The current check also only detects a value below `_trap_stack_bottom`; a huge `sscratch` value can evade the headroom check until after `sp` is set and `call trap_handler` is attempted.

This is a robustness issue for the stated “corrupted RAM / CSR misuse” threat model rather than an immediate QEMU failure.

**Suggested fix:** validate the new frame base against both trap-stack bounds before writing any frame slots, using registers not yet live, or use a separate early clobber-free sequence.

### MEDIUM-5: MMU maps all RAM RWX, including OpenSBI and kernel text/data

**File:** `kernel/src/mmu.rs`, `init()`.

```rust
map_super(root, vaddr, vaddr, PTE_LEAF_RWX)
```

maps the entire 128 MiB RAM as RWX. This is acknowledged in `DEFERRED.md` as D2, but it is still a meaningful security issue for the trajectory toward microkernel + untrusted user code. Memory disclosure or write-primitive bugs have a larger blast radius than necessary.

**Suggested fix:** split kernel image into `RX`/`RW`, map MMIO without X, and apply the pending D2 permissions split before M2.

### MEDIUM-6: `mem::alloc_pages()` returns non-zeroed pages, leaking allocator metadata

**File:** `kernel/src/mem.rs`, `alloc_pages()` and `push()`.

Free blocks store `next` pointers in the first word. Allocations do not zero returned pages. The code comments acknowledge this, but it remains a concrete future information-disclosure hazard for M2 user-page handoff.

**Suggested fix:** implement the already-tracked D10 page zeroing policy before handing pages to user-mode or exporting them beyond the kernel.

### LOW-1: Orphan `SHF_ALLOC` sections could be placed after `_alloc_start`

**File:** `kernel/linker.ld`, around the `_alloc_start` red line.

The script relies on the linker placing unknown non-alloc sections after the explicit red line harmlessly. If future code generation produces `.got`, `.init_array`, `.fini_array`, or other SHF_ALLOC orphans, the linker may place them after `_alloc_start` and create overlap with the buddy allocator. The current script only explicitly discards `.eh_frame` and `.comment`.

**Suggested fix:** add an explicit orphan section policy or a build-time assertion that no SHF_ALLOC output section appears after `_alloc_start` (e.g. `ASSERT(. == _alloc_start, "...")` style checks where feasible).

---

### LOW-2: UART baud divisor is QEMU-oriented and may be wrong on real hardware

**File:** `kernel/src/uart.rs`, `init()`.

The divisor `0x0C` corresponds to 9600 baud with the classic 1.8432 MHz reference, not 115200. QEMU’s virtual UART ignores timing, so this is invisible in CI. The module comment acknowledges the issue.

**Suggested fix:** as planned, derive UART base/clock from FDT and compute divisor from the actual `clock-frequency`; until then, clearly document 9600 baud and avoid claiming 115200.

## What looks correct

The following parts are sound or at least well-defended for the current stage:

- **Boot ordering in `kernel/src/main.rs`** is explicit: disable IRQs → sanitize CSRs → UART → traps → timer → logger → memory → MMU → heap → scheduler → sync → IRQ enable. This is a good dependency order.
- **CSR sanitization in `arch::sanitize_csr()`** addresses several real bootloader-left-state hazards (SIE, `sie`, `sip`, SUM/MXR/FS).
- **Buddy allocator free/merge validation** is unusually thorough: real-vs-padded area, block-head alignment, double-free rejection, interior-page rejection, and bounded merge behavior.
- **Trap frame validation in `riscv64.rs::trap_handler()`** correctly avoids the `frame + length` overflow pattern and checks both bounds and alignment before Rust-side use.
- **Panic handler defenses** — atomic reentrancy guard, IRQ disable, stack watermark, UART drop counter — are appropriate for diagnostic robustness.
- **UART DLAB handling and `fence iorw, iorw`** show good awareness of MMIO ordering and real-hardware hazards.
- **Linker-script separation of stacks from the kernel image and `_alloc_start` red line** is a good design for bootstrapping.

## Blind spots & suggestions for next milestone (M1: trap handling)

1. **Fix preemption before enabling interrupts in any real workload.** The current CI should include a test that spawns at least two long-running threads after `irq_enable`, runs through multiple timer deadlines, and asserts continued liveness/`uptime:` beyond several slices.
2. **Introduce per-hart state now.** `sscratch` currently carries a single global trap-stack top. Before multi-core bring-up, switch to a per-hart trap stack indexed by `tp`/hartid.
3. **Add guard pages.** This is already tracked as D4, but thread stacks also need guard regions; stack overflow in a kernel thread currently has no hardware boundary detection.
4. **Fix the hybrid scheduler state model.** The M2 user-process milestone will make the `ctx` vs `frame` inconsistency instantly visible. Decide on one canonical switch mechanism and stick to it.
5. **Make IRQ-safe synchronization a first-class M1 deliverable.** The current `SpinLock` is main-context-only, and `Mutex`/`Condvar` already have race conditions. This must be solved before any code runs with interrupts enabled beyond the idle loop.
6. **Validate FDT fields properly.** The FDT is the first external data structure consumed. Add endian-neutral parsing and structural validation (`totalsize`, `structure block` boundaries, `strings` block) before reserving memory.
7. **Apply MMU permission splits.** D2 (`RX`/`RW` separation) should be prioritized because later changes to trap handling and user mappings will be harder once a wider attack surface exists.
8. **Test on physical-hardware assumptions earlier.** The boot-lock placement issue is an example of a bug that QEMU’s zeroed RAM hides. A CI job that pre-fills QEMU RAM with non-zero data, or an explicit link-map check, would catch this class.
9. **Trap entry should be hardened before U-mode exists.** Validate `sscratch` before the first frame store, handle upper-bound corruption, and decide explicitly whether nested traps are recoverable or always fatal.
10. **Align strategy with the stated microkernel boundary.** The kernel still directly owns UART, MMU, heap, scheduler, and sync. As planned, these should become isolated behind `arch` and service boundaries before M2-visible user processes.
