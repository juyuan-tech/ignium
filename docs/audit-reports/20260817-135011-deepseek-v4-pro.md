# Independent AI audit (deepseek-v4-pro)

- date: 20260817-135011
- model: deepseek-v4-pro
- tool: scripts/ai_audit.py (external reviewer, not the author)

## Executive summary

The boot chain, buddy allocator, Sv39 identity mapping, UART driver, and cooperative `yield_` path are generally well constructed. The M1 **preemptive** path, however, is not actually exercised by the selftest and contains multiple independent fatal defects in the interaction between `Scheduler::on_tick`, the synthetic trap frames in `Thread::frame`, and the assembly restore path. Any real timer-driven preemption of a running thread would either resume through a stale cooperative context, enter a new thread with `sp=0`/`SPP=0`, or corrupt `sscratch` so the next trap halts. Several synchronization/locking issues would also become fatal as soon as kernel threads allocate or use condition variables with mutex waiters.

Below, findings are ordered by severity. File references point to the relevant function/symbol rather than exact line numbers, since line numbers were not supplied.

---

## Findings

### CRITICAL-1: Preempted threads are resumed through stale `Context` state

**File:** `kernel/src/sched.rs` — `Scheduler::on_tick`, `yield_`, `block_current`, `exit`

**Description:**
`on_tick` saves the full trap frame into `threads[cur].frame` and sets `frame_valid = true`. But every non-ISR dispatch path ignores `frame_valid` and always switches to the next thread through its callee-saved `Context`:

```rust
let old = (&mut s.threads[cur].ctx) as *mut Context;
let new = (&s.threads[next].ctx) as *const Context;
arch::context_switch(old, new);
```

`Frame.valid` only changes how `on_tick` selects a target; it does not cause the normal scheduler to resume that thread from the saved trap frame. A thread that was preempted will therefore eventually be resumed from the `ctx` saved at its last cooperative yield/block, or from its initial `thread_entry` context. That is stale state: the old `sp`/`ra` points into a stack frame that has already returned or been reused.

This makes the full-frame preemption protocol internally inconsistent. The first real preemption followed by any ordinary `yield_`/`block_current`/`exit` dispatch will jump to an arbitrary stale return address/stack.

**Concrete fix:**
Introduce one unified switch representation. Either:
- make cooperative switches save/restore a full GPR+CSR frame, or
- add a `resume` path that detects `frame_valid` and returns to the saved frame via a trap-like `sret`, and never dispatches a `frame_valid` thread through `Context`.

As long as `Context` and `Thread::frame` remain two incompatible representations with no conversion, the preemption feature cannot be correct.

### CRITICAL-2: Synthetic new-thread frame is invalid for `sret`: `sp=0`, `SPP=0`, `gp/tp=0`

**File:** `kernel/src/sched.rs` — `Scheduler::spawn` (`Scheduler::init` has the same pattern)

**Description:**
A new thread’s full trap frame is initialized as:

```rust
let mut frame = [0usize; FRAME_WORDS];
frame[FRAME_SEPC] = thread_entry as *const () as usize;
frame[FRAME_SSTATUS] = 1 << 5; // SPIE
```

Only `sepc` and `SPIE` are set. The restore path in `riscv64.S` loads `sp`, `gp`, `tp`, and `sstatus` from this frame before `sret`. Therefore:

- `sp` is 0 → the first stack access in `thread_entry` faults.
- `sstatus.SPP` is 0 → `sret` switches to **U-mode**, despite all pages having `U=0`.
- `gp` is 0 → the kernel global-pointer ABI is violated.
- `tp` is 0 → the per-hart `hartid` convention from `entry.S` is lost.

A never-started thread selected by `on_tick` via its frame will immediately fault/halt. This is independent of CRITICAL-1 and CRITICAL-3.

**Concrete fix:**
Build a complete synthetic frame:

```rust
frame[FRAME_X_SP] = sp;
frame[FRAME_X_GP] = /* &__global_pointer$ as usize */;
frame[FRAME_X_TP] = /* current hartid / tp */;
frame[FRAME_SSTATUS] = (1 << 8) | (1 << 5); // SPP=1, SPIE=1
```

Expose the needed GPR indices from `arch` or define them consistently with `riscv64.S`. Add a debug/compile-time assertion that the frame is fully initialized.

### CRITICAL-3: Restore path sets `sscratch` from a possibly non-trap-stack frame pointer

**File:** `kernel/src/arch/riscv64.S` — `trap_vector` restore path; `kernel/src/sched.rs` — `Scheduler::on_tick`

**Description:**
After `trap_handler` returns a frame pointer, the assembly does:

```asm
mv t6, a0
addi t0, t6, TRAP_FRAME_SIZE
csrw sscratch, t0
```

This is correct only when the returned frame is the current trap-stack frame (`frame + 288 == _trap_stack_top`). But on preemption, `on_tick` returns:

```rust
self.threads[next].frame.as_mut_ptr()
```

which points into the heap/Vec-backed TCB array, not the trap stack. `sscratch` then becomes `TCB_frame + 288`. On the next trap, the nested-trap detection in `trap_vector` computes:

```asm
la t0, _trap_stack_top
addi t0, t0, -TRAP_FRAME_SIZE
bne t6, t0, 4f
```

This comparison fails, so the next timer/interrupt takes the nested-halt path. Before that, the trap entry has already written `t0`/`t6` into what it believes is the frame area, potentially corrupting TCB/heap memory.

**Concrete fix:**
Never derive the next `sscratch` from `a0 + TRAP_FRAME_SIZE`. Restore `sscratch` from the actual trap-stack top symbol (`_trap_stack_top`, eventually a per-hart top) unconditionally. Also consider having `trap_handler` validate the returned frame pointer or return an explicit “resume this frame” envelope.

### HIGH-4: Preemption selftest is a false positive

**File:** `kernel/src/sched.rs` — `Scheduler::self_test` / `test_busy`

**Description:**
The “preemption” test spawns `test_busy(PRIO_LOW)` and then the main context repeatedly calls `yield_()`. For timer-driven preemption to occur, `Scheduler::on_tick` requires some *other* ready thread with `frame_valid == true`. But:

- the main context calls `yield_()`, which clears its own `frame_valid` to `false`;
- `test_busy` is first entered through `thread_entry`, which clears its `frame_valid` to `false`.

Thus when `test_busy` is running, `has_other` in `on_tick` is false. `test_busy` eventually finishes after 150 ms because `tick()` is advancing, and then exits cooperatively. The test would pass unchanged if `on_tick` were completely disabled.

This is why CI/green does not catch CRITICAL-1..3.

**Concrete fix:**
Create a test where at least one other ready thread has a valid frame while the current thread runs without yielding. For example, spawn two busy/blockable threads, or create a suspended thread that has not yet been entered while an already-running thread holds the CPU. Assert that the main/test observer advances while the busy thread is still logically runnable.

### HIGH-5: Timer ISR can allocate/enqueue, and `SpinLock`/heap locking is not preemption-safe

**Files:** `kernel/src/sched.rs` — `Scheduler::on_tick`; `kernel/src/heap.rs` — `HEAP`; `kernel/src/sync.rs` — `SpinLock`

**Description:**
`Scheduler::on_tick` calls `self.enqueue(cur)`, which calls `VecDeque::push_back`. `VecDeque` may allocate through the global allocator when capacity is exhausted. This happens in timer-ISR context with interrupts disabled and violates the project’s own “ISR zero allocation” rule (`docs/DEFERRED.md` D11). If the interrupted thread was inside the global allocator and held `HEAP`, the ISR spins forever on `HEAP.lock()`.

More generally, `HEAP` is an ordinary `SpinLock` and does not disable interrupts/preemption. A thread can be preempted while holding `HEAP`; after the scheduler switches to another thread, any allocation by that thread spins forever on the same lock. The current M1 selftests mostly avoid allocations from running threads, so this is latent, but it is certain to appear once threads allocate.

Also, `has_other` in `on_tick` does not consider priority, so it can decide to “preempt” to a lower-priority ready thread, or call `pick_next` and receive the current thread itself as the target.

**Concrete fix:**
- Make scheduler ready queues non-allocating in ISR (fixed-size intrusive lists, `try_reserve`/`reserve` policy, or preallocated capacity).
- Make `SpinLock` IRQ-safe (save/restore `SIE` across the guard), or use a lock that disables preemption/IRQs for heap critical sections.
- Select the preemption candidate before enqueueing the current thread, filter by priority, and handle `next == cur` as a no-switch case.

### HIGH-6: `Condvar::wait` releases the mutex without waking a mutex waiter

**File:** `kernel/src/sync.rs` — `Condvar::wait`

**Description:**

```rust
self.waiters.lock().push_back(sched::current_id());
m.locked.store(false, Ordering::Release);
core::mem::forget(guard);
```

This manually unlocks the mutex but does **not** pop/wake any thread from `m.waiters`. If thread B is blocked in `Mutex::lock()` waiting for this mutex, B remains `Blocked` and is never enqueued by `sched::wake`. Thread A then blocks on the condvar. B is lost forever; the mutex becomes unavailable to B despite being unlocked.

**Concrete fix:**
After registering the current thread on the condvar waiter list and before blocking, call `m.unlock()` (which wakes the mutex waiter) rather than `m.locked.store(false)`. Then `mem::forget(guard)` to avoid double-unlock. This should be done with interrupts still disabled to preserve the atomic “register → release → block” handshake.

### MED-7: Idle thread is never actually entered; `reap` never runs and exited thread stacks leak

**Files:** `kernel/src/main.rs` / `kernel/src/sched.rs` — `sched::init`, `idle_entry`, `reap`

**Description:**
`sched::init` creates thread 0 with `ctx = idle_entry` and an allocated idle stack. But the first `yield_` in `sched::self_test` overwrites thread 0’s `ctx` with the current boot context:

```rust
let cur = s.current; // 0
// context_switch saves the current CPU/boot context into threads[0].ctx
```

`idle_entry` is therefore never executed. `reap()` is referenced only from `idle_entry`, so the reaper queue is never drained. Every thread that exits moves its stack `Box` into `s.reaper`, but nothing frees it. The allocated idle stack is also unused.

**Concrete fix:**
Decide explicitly whether the boot context is the idle thread. If so, do not create a separate idle stack/`idle_entry`, and drain the reaper from the actual idle loop. If `idle_entry` should run, switch to it before running the idle loop and do not repurpose thread 0’s `ctx`.

### MED-8: Thread stack allocation/deallocation layout mismatch is UB

**File:** `kernel/src/sched.rs` — `alloc_zeroed_free_stack`

**Description:**

```rust
let layout = Layout::from_size_align(THREAD_STACK_SIZE, 16).expect("stack layout");
let ptr = unsafe { alloc::alloc::alloc(layout) };
...
unsafe { Box::from_raw(core::ptr::slice_from_raw_parts_mut(ptr, THREAD_STACK_SIZE)) }
```

The allocation is performed with `align=16`, but `Box<[u8]>` drops/deallocates with the layout for a `u8` slice, i.e. `align=1`. `GlobalAlloc::dealloc` requires the same layout as was used for `alloc`; using a different layout is undefined behavior. The current allocator happens to ignore `layout.align()` for page-path deallocation, which masks the bug, but it is still UB and can break under future allocator changes or optimization.

**Concrete fix:**
Use an aligned element type, e.g.:

```rust
#[repr(align(16))]
struct StackAligned([u8; THREAD_STACK_SIZE]);
Box<StackAligned>
```

or retain the original `Layout` and perform manual `alloc::alloc::dealloc` rather than relying on `Box<[u8]>` Drop.

### MED-9: Invalid-pointer bounds check in heap dealloc is too wide

**File:** `kernel/src/heap.rs` — `KernelAllocator::dealloc`

**Description:**

```rust
if page < base || page - base >= mem::MAX_PAGES * mem::PAGE_SIZE {
    panic!(...);
}
```

`mem::MAX_PAGES` is the number of pages from `RAM_START` to `RAM_END`, not the number of pages actually managed by the allocator from `mem::base()` to the end of the real/padded allocation area. With the current geometry (`base` is 16 MB aligned above RAM_START), an invalid pointer in the upper `MAX_PAGES * PAGE_SIZE` window but outside the real allocator region passes this check. It then reaches `slab_class_of` and, for the large-object path, reads `ptr - 8`, potentially outside identity-mapped RAM.

**Concrete fix:**
Validate against the actual allocator range:

```rust
let alloc_end = base + mem::page_count() * mem::PAGE_SIZE;
if page < base || page >= alloc_end { panic!(...); }
```

or expose `vec::page_count()`/`real_count` as the bound. This also makes the guard correct if `base` changes.

### LOW-10: Trap entry writes into the presumed frame before nested-trap validation

**File:** `kernel/src/arch/riscv64.S` — beginning of `trap_vector`

**Description:**
The very first action after computing the candidate frame base is:

```asm
sd t0, 4*8(t6)
csrr t0, sscratch
sd t0, 30*8(t6)
```

Only after these stores does the nested-trap check run. If `sscratch` is stale/corrupt (which CRITICAL-3 makes possible) or the vector takes a synchronous fault before `sscratch` is updated, these two stores can land in arbitrary memory before halting.

**Concrete fix:**
Validate the frame base against `_trap_stack_bottom`/`_trap_stack_top` before any store, or use a dedicated “trap active” flag in a known-safe location. The write-after-validation principle matters in a security kernel.

### LOW-11: CI heartbeat assertion does not prove continued liveness

**Files:** `.github/workflows/ci.yml`, `Makefile` `test`

**Description:**
Both smoke tests require only:

```sh
test "$(grep -c 'uptime:' /tmp/ignium-ci.log)" -ge 2
```

A silent hang or nested `wfi` halt after the second heartbeat still passes CI. Several of the trap/preemption failures above would be silent rather than printing `KERNEL PANIC` or `TRAP:`.

**Concrete fix:**
Require liveness near the end of the 10 s window, e.g. at least 8 heartbeats and/or a line like `uptime: 900 ticks`/`uptime: 1000 ticks`. Also consider adding a QEMU exit-status check for unexpected early exit.

### INFO-12: Thread-stack panic diagnostics are missing

**File:** `kernel/src/panic.rs` — `current_stack_bounds`

**Description:**
`current_stack_bounds` only knows the boot stack and trap stack. A panic in any scheduler thread is reported as:

```text
WARNING: sp=... outside all known stacks (corrupted?)
```

with `stack watermark: UNKNOWN`. That is misleading and will complicate M1.5/M2 debugging.

**Suggestion:**
Register thread stack ranges with the scheduler or panic subsystem, or maintain a per-thread stack top/bottom in the TCB for panic/diagnostic use.

## What looks correct

- **Boot flow and hart arbitration:** `entry.S` clears `SIE`, installs an early trap stub, clears `satp`, initializes `gp`, uses an atomically contested `BOOT_LOCK`, and zeroes BSS+boot/trap stacks. The losing-hart `park` path is simple and safe for M1.
- **Linker script:** the stack/trap-stack regions are outside the allocator region, `_alloc_start` is page aligned, and the red-line rule prevents alloc sections after `_alloc_start`. The BSS clear loop ends at `_trap_stack_top` by construction.
- **Buddy allocator:** metadata/free-list design is sound for single-hart locked use. The carve logic for FDT reservations, padding-page marking, block-head-only metadata, double-free/interior-page rejection, and absolute max-block alignment are all thoughtful.
- **Sv39 initial mapping:** identity mapping via 2 MB superpages plus a 4 KB UART mapping is appropriate for M1. Setting A/D at creation is a good compatibility decision. `SATP_PPN_MASK` is correctly 44 bits.
- **Trap frame GPR/CSR indices:** the Rust constants and the assembly save/restore order match. The compile-time `TRAP_FRAME_WORDS * 8 == 288` assertion is a good guard.
- **UART:** volatile accesses, `fence iorw, iorw`, bounded TX waiting with dropped-character accounting, and DLAB sequencing are all correct in shape for QEMU.
- **Panic path:** dual-panic protection, disabling interrupts before output, and bytewise stack-watermark scanning are good.
- **Build/reproducibility:** toolchain pinning, absolute linker-script path, and `rerun-if-changed` are correct.

## Blind spots & suggestions for the next milestone (M1: trap handling)

1. **Redesign/re-test the preemptive scheduler before any M2 work.** The current dual `Context`/`frame` model is the largest unresolved correctness risk. Add a deterministic test that actually causes `on_tick` to return a different TCB frame and verifies that the preempted thread later resumes correctly.
2. **Per-hart trap stacks must land before any SMP enablement** (already D7). The current global `sscratch`/trap-stack assumptions also need revisiting as part of the CRITICAL-3 fix.
3. **Make all scheduler ready queues non-allocating in ISR.** `VecDeque` is convenient but not ISR-safe under the stated policy. Fixed-size arrays or intrusive lists should be considered.
4. **Resolve `SpinLock` vs preemptive scheduling.** Every spinlock used by threads, especially the heap lock, must either disable interrupts/preemption or be replaced by a blocking lock where appropriate.
5. **Add FPU/vector state handling or explicitly forbid it.** `riscv64gc` includes F/D, but neither `Context` nor the trap frame saves floating-point state. As soon as any future code uses floats, this will corrupt user/kernel state.
6. **Improve liveness testing.** Silent trap/hang regressions should not pass CI. Require late-window heartbeats.
7. **Fault-injection tests for trap paths.** Exercise invalid frame pointers, nested trap behavior, and corrupted `sscratch` under controlled conditions before M2.

The strongest immediate action is to assume the M1 preemption path is currently unproven and broken until the three CRITICAL findings above are fixed and covered by a test that truly preempts a running thread.
