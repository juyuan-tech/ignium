# Independent AI audit (deepseek-v4-pro)

- date: 20260816-182019
- model: deepseek-v4-pro
- tool: scripts/ai_audit.py (external reviewer, not the author)

## Executive summary

The M0 boot chain is mostly coherent and well-documented. In the default QEMU `virt -m 128M` configuration, I did not find a currently-triggered memory-safety or control-flow bug in the normal boot path. The highest-risk issues are latent: the buddy allocator’s padding logic is wrong for non-16 MiB-aligned RAM sizes, the allocator has no reserved-memory model (and will happily hand out the FDT page), trap entry trusts `sscratch` enough to write memory before validation, and the “compile-time” trap-frame-size check does not actually check the assembly side. There are also several future-interrupt/SMP hazards and a weak CI timer assertion.

## Findings (severity-ranked)

### HIGH — Buddy allocator can place blocks containing out-of-RAM padding pages into free lists

**File:** `kernel/src/mem.rs` around lines 127–154 (`BuddyAllocator::init`).

**Description:**  
`init` computes `padded = count.div_ceil(order_size) * order_size`, marks pages `count..padded` as `used = true`, but then pushes **all** `order-12` blocks:

```rust
while idx < padded {
    self.push(idx, MAX_ORDER);
    idx += order_size;
}
```

If `count` is not an exact multiple of `1 << MAX_ORDER` (16 MiB / 4096 pages), the final pushed block contains a mix of real pages and padding pages. `push` only marks the block head page as free. A later `alloc` can return a block whose tail lies beyond physical RAM, and splitting/freeing can write free-list nodes to non-existent memory. The current QEMU configuration avoids this only because `base` and `RAM_END` are both 16 MiB-aligned, so `padded == count`. The planned M1.5 FDT/RAM-size replacement will expose this on non-aligned real hardware memory sizes.

**Fix suggestion:**  
Do not push any block that is not entirely within `real_count`. For example, round down to a multiple of `order_size` for the managed region (`let usable = count / order_size * order_size`), and only initialize free lists for `idx + order_size <= usable`. Leave any tail pages permanently unavailable. Keep an explicit unreachable/debug check for the padded pages.

### HIGH — No reserved-memory model; allocator can overwrite the FDT and other reserved regions

**File:** `kernel/src/mem.rs` lines 27–30 (`RAM_END` hardcoded), `kernel/src/mem.rs` public `init`, and `kernel/src/main.rs` where `fdt` is logged but not reserved.

**Description:**  
The allocator treats `[aligned _alloc_start, RAM_END)` as entirely available. On QEMU `virt -m 128M`, OpenSBI passes the FDT at the top of RAM — the log example shows `fdt=0x87e00000`, which is inside the allocator range. Nothing marks that page as reserved. The kernel also hardcodes `RAM_END = RAM_START + 128 * 1024 * 1024`, so on real hardware with a different RAM size or additional reserved regions, the allocator can either miss usable memory or fablingvásically return pages that are not RAM. As soon as M1 parses the FDT for device discovery, the FDT may already be allocatable and can be overwritten.

**Fix suggestion:**  
Before enabling the allocator or exposing `alloc_pages`, collect memory/reserved-memory information from the FDT or a platform description. Mark kernel image, stacks, trap stack, FDT, OpenSBI-reserved ranges, and any other platform reservations as occupied. Do not use a hardcoded `RAM_END`.

### MEDIUM — Trap entry writes to memory based on `sscratch` before validation; stack check only rejects the low side

**File:** `kernel/src/arch/riscv64.S` in `trap_vector` (the early `sd t0, 4*8(t6)` and later `bltu t1, t0, 2f` headroom check); Rust-side validation in `kernel/src/arch/riscv64.rs` only happens after the call-in stack pointer is set.

**Description:**  
The trap entry does:

```asm
csrrw t6, sscratch, t6
addi t6, t6, -TRAP_FRAME_SIZE
sd t0, 4*8(t6)
```

If `sscratch` is corrupted/wrapped/zero, `t6 - 288` can point anywhere, and the `sd` corrupts arbitrary memory before any validation. Later, the “headroom check” is:

```asm
la t0, _trap_stack_bottom
addi t1, t6, -2048
bltu t1, t0, 2f
mv sp, t1
call trap_handler
```

`bltu` is unsigned-less-than. It rejects only computed `sp < trap_stack_bottom`. A high or wrapped `t1` passes the test, and `call trap_handler` then writes return/stack data to an invalid address, potentially faulting or corrupting memory before Rust’s `frame` validator runs. The comment claims “强制校验余量在陷阱栈内”, but that is not what the code does.

**Fix suggestion:**  
Validate both `frame base` and computed handler `sp` against `[trap_stack_bottom, trap_stack_top)` before the first store if at all possible; at minimum, add an upper-bound/wrap check before `mv sp` and `call`. For first-store safety under corrupted `sscratch`, consider keeping the trap stack pointer in a register that cannot be clobbered by user context (or establish an even smaller trusted-entry path), and document the trust boundary.

### MEDIUM — The Rust/assembly trap-frame-size “drift check” does not check the assembly side

**File:** `kernel/src/arch/riscv64.rs` (`TRAP_FRAME_WORDS = 36`, `assert!(TRAP_FRAME_WORDS * 8 == 288)`) and `kernel/src/arch/riscv64.S` (`.equ TRAP_FRAME_SIZE, 288`).

**Description:**  
The comment claims the assertion prevents drift between the Rust and assembly frame sizes, but both values are independent literals. Changing `.equ TRAP_FRAME_SIZE, 280` in the assembly would not fail the Rust assertion, and changing `TRAP_FRAME_WORDS` to, say, 35 would fail against the hardcoded `288` but not detect a corresponding assembly error. This gives a false sense of safety for one of the most safety-critical ABI contracts in the kernel.

**Fix suggestion:**  
Use a shared generated constant/file for both Rust and assembly, or add a build-time script/CI check that parses both sources and asserts the numeric values agree. At minimum, remove the misleading comment and document that the two sides must be manually synchronized.

### MEDIUM — `irq_disable`/`irq_enable` and related CSR barriers use `nomem`, allowing compiler reordering around interrupt state changes

**File:** `kernel/src/arch/riscv64.rs` — `irq_disable`, `irq_enable`, `sanitize_csr`, `wait_for_interrupt`.

**Description:**  
These inline-asm blocks use `options(nomem, nostack)`. `nomem` tells the compiler the asm does not touch memory, so the compiler may move ordinary memory accesses across the CSR write. For interrupt enable/disable, that is dangerous: memory writes that must be visible before interrupts are enabled can be reordered after `csrsi sstatus, 2`, and memory reads after `csrci sstatus, 2` can be hoisted before interrupts are masked. The current timer ISR is small enough that this does not produce a visible bug, but the next scheduler/allocator/lock code will be exposed.

**Fix suggestion:**  
Remove `nomem` from interrupt-enable/disable asm blocks, or explicitly add `compiler_fence(Ordering::SeqCst)` / a memory clobber where needed. Do not treat CSR interrupt-control writes as memory-neutral compiler barriers.

### MEDIUM — CI/Makefile smoke test accepts a single `uptime:` line; a timer that dies after the first tick still passes

**File:** `.github/workflows/ci.yml` boot-test grep block; `Makefile` `test` target.

**Description:**  
The test greps for at least one `"uptime:"` line. The comment says this was intended to catch silent timer death (“否则定时器静默失效也会被放行”), but if `sbi_set_timer` succeeds once and then fails, the kernel still prints one uptime line and then stalls forever. The test remains green because `timeout` kills QEMU after 10 s and the negative grep still passes if no panic/trap occurred.

**Fix suggestion:**  
Require at least two uptime lines, or better, require a line corresponding to a later tick/time (e.g., `uptime: 500 ticks` or a count `gte 3`). Alternatively use QEMU’s clock/`-icount` to deterministically check repeated ticks.

### LOW — Formal strict-provenance UB in stack watermark scan and trap-frame slice

**File:** `kernel/src/panic.rs` `stack_watermark`; `kernel/src/arch/riscv64.rs` `dump_trap_frame`.

**Description:**  
`_stack_bottom` is declared as `extern "C" { static _stack_bottom: u8; }`. `stack_watermark` takes that address as a `*const u8`, adds past the single-byte object, and reads byte-by-byte. Under Rust strict provenance, pointer arithmetic/dereference beyond the declared object is formally UB, even with `read_volatile`; byte reads do not remove provenance. `dump_trap_frame` similarly creates `core::slice::from_raw_parts(frame, TRAP_FRAME_WORDS)` over raw trap-stack memory with no Rust allocation behind it. In current toolchain practice this works, but it is exactly the kind of issue that should be made explicit/clean before relying on more complex memory layouts.

**Fix suggestion:**  
Declare linker-defined regions with `usize`-address access plus `ptr::with_exposed_provenance`/`from_exposed_addr` wrappers, or model the stack/trap regions as `extern "C"` arrays whose lengths are known to the linker script. Document a project-wide physical-memory/provenance policy rather than assuming volatile accesses are sufficient.

### LOW — `TRAP_FRAME_WORDS` is 36 while actual slots are 31 GPR + 4 CSR = 35; slot `[31]` is undocumented padding

**File:** `kernel/src/arch/riscv64.rs` (`TRAP_FRAME_WORDS`, `gpr`, CSR constants); `kernel/src/arch/riscv64.S` frame-layout comments.

**Description:**  
The comment says `[0..31)` GPRs and `[32]` is `sstatus`, but there is no slot `[31]`. The extra word appears to be alignment padding so 36*8=288 is 16-byte aligned. This is probably intentional, but it is undocumented and will confuse future editors. An off-by-one in the frame-size change path is plausible.

**Fix suggestion:**  
Rename/add `const TRAP_FRAME_PAD: usize = 31;` and explicitly document the padding slot. Better, define the frame size as `(32 + 4) * 8` with an alignment-padding formula so the invariant is self-describing.

---

### LOW — Hardcoded UART base/divisor, timer frequency, and `time` CSR assumptions are QEMU-specific

**File:** `kernel/src/uart.rs` (base 0x1000_0000 and baud divisor), `kernel/src/arch/riscv64.rs` (`TIMER_INTERVAL = 100_000` and `get_time`).

**Description:**  
These work on QEMU `virt`, but real hardware may have a different UART address/clock, a different `timebase-frequency`, or may not expose `time` to S-mode if `mcounteren.TM` is not set. The timer interval is derived from a hardcoded 10 MHz. If `time` traps, the kernel currently goes through the unhandled-exception halt path, possibly before useful diagnostics. The code comments acknowledge the UART/FDT aspect, but the timer/counter assumptions are equally important.

**Fix suggestion:**  
Parse the platform description (FDT/ACPI) for UART base/clock and `timebase-frequency` during early boot; do not enable the timer until `time` has been probed. Provide a board-specific fallback for early-console before FDT parsing.

---

### LOW — Full register/CSR dumps and FDT address are printed to a shared console

**File:** `kernel/src/arch/riscv64.rs` (`dump_trap_frame`, `dump_cpu`), `kernel/src/main.rs` M0 boot log.

**Description:**  
In the current single-privilege milestone this is acceptable. In the planned multiuser/microkernel system, arbitrary user processes may be able to read console output or influence log sinks. Complete trap frames, `satp`, `sepc`, kernel pointer values, and physical addresses (FDT) can leak kernel ASLR/layout and potentially user data.

**Fix suggestion:**  
Gate detailed register dumps behind a separate diagnostic log level or a privileged ring that user-space cannot observe; redact or hash physical pointers in production logs.

## What looks correct

- **Linker script/reserved stack separation:** The stack and trap stack are kept out of the kernel image and out of the allocator’s usable region. `_alloc_start` is placed after both, which is the right idea.
- **Boot entry flow:** `entry.S` correctly clears `sstatus.SIE`, `satp`, `stvec`, `sscratch`, performs TLB invalidation, initializes `gp`, parks secondary harts before memory writes, clears BSS + stacks, and preserves OpenSBI `a0/a1` into `kernel_main`.
- **Main initialization ordering:** UART before logging, trap vector before timer, allocator self-test before `irq_enable`, and `irq_enable` last is a sensible dependency order.
- **Panic double-panic guard:** `PANICKING` plus `halt()` is a simple, effective recursion guard.
- **Buddy allocator core logic:** Under the current aligned configuration, split, merge, double-free rejection, interior-page rejection, and buddy order-11 merge behavior are correct and well-tested by `self_test`.
- **Trap frame save/restore normal path:** For a first trap with correct `sscratch`, the register/CSR save order, nested-trap detection, `gp` reload, `sret` restore path, and SIE-clearing-before-`sret` are carefully implemented.
- **UART bounded wait:** The `TX_WAIT_LIMIT` plus `TX_DROPPED` design avoids infinite hangs on a dead serial controller.
- **Toolchain/CI version pinning and documentation:** `rust-toolchain.toml`, CI action, and Makefile are synchronized; the linker-script orphan-section policy is documented.
- **Use of `#[deny(unsafe_op_in_unsafe_fn)]`:** This makes unsafe blocks explicit and is good hygiene for kernel code.

## Blind spots & suggestions for the next milestone (M1: trap handling)

- **Trap dispatch:** Current `trap_handler` is intentionally fatal for all synchronous exceptions except future timer routing. M1 must add exception delegation, page-fault handling, `ecall` dispatch from user mode, and recoverable external interrupts.
- **Per-hart trap stacks / CPU-local state:** `sscratch` currently points to a single global trap stack. Secondary-hart wakeup must install per-hart `sscratch`/`stvec` and initialize per-hart context before enabling interrupts on those harts.
- **Interrupt-safe logging:** The logger is explicitly lock-free and relies on the timer ISR not logging. M1 recoverable exceptions/IRQs will need a lock, a ring buffer, or ISR-specific output path; UART ownership will matter once `uart_server` is proposed.
- **Allocator synchronization:** `mem.rs` is single-core + interrupts-disabled only. M1/M1.5 needs a spinlock/IRQ-safe allocator path, plus reserved-memory tracking and FDT probing before any page can be handed out.
- **Guard pages:** Stack overflow is currently diagnosed only by panic watermark (post-hoc). M1 should add unmapped guard pages around boot/trap stacks and turn overflow into a handler rather than silent corruption.
- **Cross-language constants:** Trap frame offsets, sizes, and stack layout need a real single-source-of-truth mechanism, not hand-maintained comments and hardcoded constants.
- **Interrupt/memory barriers:** Revisit every CSR `asm!` that touches `sstatus`, `sie`, `sip`, `sscratch`, `stvec`, and ensure compiler/memory ordering matches the architecture. As the trap path becomes reentrant or SMP, use proper atomics/Release-Acquire rather than Relaxed-only tick/deadline counters.
- **Nested-trap policy:** The assembly currently deliberately halts on nested trap (`4f`). The roadmap mentions “可重入”, which appears inconsistent. Decide explicitly whether nested traps are supported, and if not, update the roadmap and comments before M1.
- **Physical-memory/provenance model:** As MMU/page tables arrive, define how linker-symbol-derived raw pointers are represented. The current `extern "C" static _x: u8` plus raw scanning is workable on current Rust/LLVM but is formally fragile.
- **Secure boot / hostile bootloader:** The kernel trusts OpenSBI-provided `hartid`, FDT pointer, and pre-existing CSR/register state after only light sanitization. A hostile bootloader or corrupted RAM remains outside the current assurance model. M1 should consider a minimal image/pointer sanity policy.
