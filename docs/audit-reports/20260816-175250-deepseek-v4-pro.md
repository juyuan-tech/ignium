# Independent AI audit (deepseek-v4-pro)

- date: 20260816-175250
- model: deepseek-v4-pro
- tool: scripts/ai_audit.py (external reviewer, not the author)

## Executive summary

The current M0/QEMU single-hart boot path is largely coherent: the entry code establishes a deterministic S-mode state, the UART driver handles the NS16550 DLAB ordering correctly, the basic trap save/restore path is complete, and the buddy allocator passes its own self-test. I did not find a demonstrably CRITICAL memory-safety bug that is *currently reachable* in the normal boot-to-idle path.

The most serious issues are latent trap-context and memory-management invariants that will become security-critical as soon as user mode, recoverable traps, nested traps, or non-QEMU RAM sizes are introduced. Special attention should be paid to the trap entry path: it does not switch to kernel `gp`/`tp`, and nested trap frame placement can overlap the active handler stack. The allocator also has a dormant “padding page can be freed” bug, and timer SBI failure handling can silently hang the kernel.

---

## Findings (severity-ranked)

### CRITICAL

None in the current M0/QEMU boot path.

### HIGH

#### H1. Trap entry never reloads kernel `gp` (or establishes kernel `tp`) — user-mode traps can steer kernel global accesses

File: `kernel/src/arch/riscv64.S`, `trap_vector`; `kernel/src/entry.S`, `_start`

`gp` is initialized exactly once in `_start` (`la gp, __global_pointer$`). The trap path saves the previous `gp` into the trap frame, but does **not** immediately set `gp` to the kernel `__global_pointer$` before executing load/address-generation instructions or Rust `trap_handler`.

This is fine while only kernel S-mode code runs, because `gp` remains the kernel value. Once user processes exist, user code will have an arbitrary `gp`. If a user trap is taken:

- `trap_vector` uses `la t0, _trap_stack_bottom`, which can be linker-relaxed into a `gp`-relative access if that symbol falls within `±2 KiB` of `__global_pointer$` in a future link layout;
- compiled Rust code in `trap_handler` may access globals/atomics (`TICK`, `TIMER_DEADLINE`, UART state, etc.) through `gp`-relative addressing.

A user-controlled `gp` could then turn those accesses into reads/writes of an attacker-chosen address before the kernel has established a trusted context.

Fix:

- At the very beginning of `trap_vector`, set `gp = __global_pointer$` (`la gp, __global_pointer$` with `.option norelax`), before any relaxable `la` or C/Rust code.
- Establish a kernel `tp` as soon as per-hart data exists; do not run `trap_handler` with the trapped context’s user-controlled `tp`.
- Ensure the trap vector’s own `la`/`lla` sequences cannot be relaxed against a not-yet-switched `gp`.

#### H2. Nested trap frame placement can overwrite the active `trap_handler` stack

File: `kernel/src/arch/riscv64.S`, `trap_vector` headroom/stack selection

For each trap, the vector computes:

```asm
addi t6, t6, -TRAP_FRAME_SIZE
...
addi t1, t6, -2048
mv sp, t1
```

The new handler `sp` is always `new_frame_base - 2048`, **not** derived from the interrupted context’s current `sp`. If a trap occurs while a previous `trap_handler` invocation is already active on the same trap stack, the new `sp` may be **above** the previous invocation’s current stack pointer. The nested handler can then overwrite live locals/saved registers belonging to the outer handler.

Current code only expects nested synchronous exceptions, and those paths currently log and `halt`, so this is not normally reachable in M0. But the comment claims “可重入”, and M1 will add recoverable traps and potentially nested interrupts. At that point this becomes a real stack-corruption/reentrancy bug.

Fix options:

- Make nested traps explicitly fatal before reusing the shared trap stack.
- Use a separate emergency/exception stack.
- Compute nested `sp` from the interrupted `sp` in a way that guarantees non-overlap, and verify it against trap-stack bounds before writing.
- Document that the current trap stack is not safely reentrant for recoverable nested traps.

### MEDIUM

#### M1. Trap frame comment promises reserved slots 36..40 that are not allocated

File: `kernel/src/arch/riscv64.S:24` and `kernel/src/arch/riscv64.S:29`

The frame layout comment says:

```asm
#   [36..40) 预留(M1 使用)
```

but:

```asm
.equ TRAP_FRAME_SIZE, 288
```

and in Rust:

```rust
const TRAP_FRAME_WORDS: usize = 36;
assert!(TRAP_FRAME_WORDS * 8 == 288);
```

There are only 36 words/slots (`0..36`). Slots `36..40` do not exist in the allocated frame. If an M1 contributor follows the comment and writes reserved CSRs at indices 36–39, they will overwrite adjacent memory (the previous frame or the region outside the trap stack). This is a concrete contract/implementation mismatch.

Fix: either enlarge `TRAP_FRAME_SIZE`/`TRAP_FRAME_WORDS` to 40 words (320 bytes) and update both assembly and Rust, or remove/correct the “reserved” comment.

#### M2. Timer programming failure can silently hang boot or cause an interrupt storm

Files: `kernel/src/arch/riscv64.rs`, `enable_timer` and timer path in `trap_handler`; `kernel/src/main.rs`, idle `wfi` loop

At boot:

```rust
if crate::sbi::set_timer(deadline) != 0 {
    warn!("sbi_set_timer failed at boot");
}
```

and then `kernel_main` continues to `irq_enable` and `wfi`. If the SBI `set_timer` call fails and no other wakeup exists, the CPU can sleep in `wfi` forever. A single warning may be missed; the uptime heartbeat never appears.

In the timer ISR, the result of `sbi::set_timer(next)` is ignored. If the timer compare remains in the past and `STIP` remains pending, returning with `sret` re-enables `SIE` and can immediately re-trap, producing a timer-interrupt livelock.

Fix:

- Treat boot `set_timer` failure as fatal (`panic!`) or enter a polled fallback; do not proceed to a dependably interrupt-driven idle loop.
- In the ISR, on failure either disable `STIE`/halt or log once and enter a safe shutdown path; never return as if the next deadline was programmed.

#### M3. Buddy allocator padding pages can be freed and then allocated beyond physical RAM

File: `kernel/src/mem.rs`, `init`/`free`

`init` rounds `count` up to a whole number of `order-12` blocks:

```rust
let padded = count.div_ceil(order_size) * order_size;
self.page_count = padded;
...
for i in count..padded {
    let m = self.meta(i);
    m.order = MAX_ORDER as u8;
    m.used = true; // permanent occupied
}
```

But `free` accepts any address in `[base, base + padded*PAGE_SIZE)` whose head metadata is marked `used=true`. The padding “permanently occupied” pages meet exactly that test. Therefore `free_pages` on a padding block head can push padding pages into the free lists. They can later be returned by `alloc_pages`, producing a block that extends past the true `RAM_END`.

In the current fixed QEMU 128 MiB layout, `base` and `RAM_END` are both 16 MiB aligned, so `padded == count` and there is no padding. This is dormant until FDT- or board-derived RAM sizes are introduced. It is a real allocator invariant bug nevertheless.

Fix:

- Store `usable_pages = count` separately from `page_count`.
- Reject `free` when `block_index(addr) >= usable_pages`.
- Report `usable_pages`, not `padded`, as managed memory.

#### M4. `alloc_pages` returns uninitialized pages containing free-list metadata — future user page handoff leaks data

File: `kernel/src/mem.rs`, `alloc`

Allocation does not zero memory. Freed blocks store the next free-list index in their first word. If the future memory service hands a freshly allocated page to an untrusted user process without zeroing, the user can read the previous contents, including kernel allocator metadata (`usize::MAX`/page indices) or data from other processes.

Fix:

- Add a zeroing allocation path (`alloc_pages_zeroed`) and require it for pages that will become user-visible.
- Alternatively zero all pages in `alloc` if performance allows, or zero on free/user mapping.

#### M5. Trap restore path is not exception-atomic — a fault during restore can corrupt the restored context

File: `kernel/src/arch/riscv64.S`, restore path after `trap_handler` returns

The restore path sets:

```asm
addi t0, t6, TRAP_FRAME_SIZE
csrw sscratch, t0
...
csrw sstatus, t0
...
ld ra, 0*8(t6)
...
sret
```

It clears `SIE` to avoid interrupts, but synchronous exceptions can still occur during the `ld`/`csrw` sequence. If one does, `trap_vector` uses `sscratch = frame_base + TRAP_FRAME_SIZE`, subtracts `TRAP_FRAME_SIZE`, and writes a new trap frame over the very frame currently being restored. If the nested trap returns, the outer restore completes with corrupted saved registers.

This is latent in current M0 because the restore sequence should not fault in normal memory. Once ECC faults, bad physical memory, or future MMU mappings are possible, this becomes a double-fault corruption path.

Fix:

- Treat traps taken during restore as fatal before any frame overwrite.
- Add an explicit “in-restore” guard/flag.
- Reorder the sequence or use a separate emergency frame such that re-entry cannot overwrite a frame that is still being consumed.

#### M6. Trap stack is not zeroed at boot — watermark/E CC diagnostics and real-hardware robustness

File: `kernel/src/entry.S`, zero loop; `kernel/linker.ld`, `.stack`/`.trap_stack`

The boot zero loop runs from `_bss_start` to `_stack_top`:

```asm
la t0, _bss_start
la t1, _stack_top
1:
    bgeu t0, t1, 2f
    sd zero, 0(t0)
    addi t0, t0, 8
    j 1b
```

This zeroes BSS and the boot stack, but **not** `.trap_stack`. The panic stack-watermark logic assumes zero-filled stack; a trap-stack panic can report a meaningless watermark based on stale bootloader/RAM data. On real ECC DRAM, reading an uninitialized trap stack can also raise a machine check.

QEMU commonly starts RAM zeroed, so this is easy to miss.

Fix: extend boot zeroing to `_trap_stack_top` or zero `.trap_stack` separately before `init_traps`.

#### M7. Public allocator and logger APIs are safe but non-reentrant; future ISR/multicore use is UB or corrupting

Files: `kernel/src/mem.rs`, `alloc_pages`/`free_pages`; `kernel/src/logger.rs`, module header/`log`

`alloc_pages`/`free_pages` return from and mutate a global `static mut` allocator through `&mut` without a lock. A future timer ISR or second hart calling them while a main-context allocation is in progress would create aliasing `&mut` references and corrupt allocator state. `logger::log` has no UART lock and is not ISR-safe.

Current code is carefully ordered (`mem::init`/`self_test` before `irq_enable`, no logging in the timer ISR), so this is not triggered today. But the safe APIs make accidental future use too easy.

Fix before M1:

- Add an interrupt-safe spinlock or make these functions `unsafe` with explicit reentrancy contracts.
- Design a logger path that is safe from interrupt context (ISR buffer or lock) and document panic-path behavior.

### LOW

#### L1. Early boot does not sanitize S-mode `stvec`/`sscratch` from a hostile/previous bootloader

File: `kernel/src/entry.S`, `_start`; `kernel/src/main.rs`, `kernel_main`

`_start` clears `SIE`, `satp`, TLB, and `gp`, but not `stvec`/`sscratch`. `init_traps` installs them only after `uart::init`. If a hostile bootloader or previous S-mode code left `stvec` pointing at attacker-controlled code, a synchronous exception during `uart::init`/`sanitize_csr` jumps there. OpenSBI is assumed trusted today, but the stated threat model includes hostile bootloader.

Fix: set `stvec`/`sscratch` to known safe values very early in `_start`, at least before any fault-prone instruction.

#### L2. Trap-frame bounds check can overflow on a corrupted frame pointer

File: `kernel/src/arch/riscv64.rs`, `trap_handler` frame validation

```rust
if f < bottom || f + TRAP_FRAME_WORDS * 8 > top || !f.is_multiple_of(16)
```

`f + 288` is checked in ordinary Rust arithmetic. With `overflow-checks = true`, a corrupted huge `frame` value can panic inside the trap handler during validation; with overflow checks off, the addition could wrap and bypass the upper-bound check.

Fix: write it as `f > top - TRAP_FRAME_WORDS * 8`, avoiding overflow.

#### L3. Uptime subtraction can underflow/panic after tick wrap or corruption

File: `kernel/src/main.rs`, idle loop

```rust
if t - last_tick >= 100 {
```

The code uses `t.saturating_mul(10)` to avoid multiplication panic, but not saturating subtraction. If `TICK` wraps (`AtomicU64::fetch_add` wraps without panic) or is corrupted, this panics. Extremely unlikely, but inconsistent with the nearby defensive style.

Fix: `t.saturating_sub(last_tick) >= 100` or `t.abs_diff(last_tick) >= 100`.

#### L4. Allocator bounds are mostly `debug_assert!`; free-list corruption can become OOB in release

File: `kernel/src/mem.rs`, `meta`, `push`

Checks such as `debug_assert!(idx < self.page_count)` and `debug_assert!(padded <= MAX_PAGES)` disappear in release builds. The free list itself is stored in allocatable memory; a corrupted next pointer can cause out-of-bounds writes. If corrupted RAM is in the threat model, these should be explicit runtime checks, not debug assertions.

Fix: harden `pop`, `unlink`, and `push` with release-visible bounds checks and perhaps a canary/bitmap validation strategy in M1.5.

#### L5. `trap_handler` does not coordinate with the panic guard

Files: `kernel/src/riscv64.rs`, `trap_handler`; `kernel/src/panic.rs`

`PANICKING` protects recursive panics, but `trap_handler` can still call `error!` while the panic handler is mid-log. This can interleave serial output and, in a bad enough state, recurse through trap/log paths until the trap-stack headroom check stops it.

Fix: check a trap-active/panic-active state at trap entry and go directly to `halt` if already in panic/trap fatal handling.

### INFO

#### I1. QEMU constants will need FDT/DMI replacement

Files: `uart.rs`, `mem.rs`, `riscv64.rs`

UART base `0x1000_0000`, RAM `0x8000_0000..0x8800_0000`, and the 10 MHz timer frequency are QEMU virt assumptions. Real hardware will need FDT/ACPI parsing and per-platform clock/baud derivation. The comments already acknowledge this.

#### I2. Linker orphan handling is disabled

File: `.cargo/config.toml`; `kernel/linker.ld`

`--orphan-handling` is intentionally off. New compiler-generated sections may silently land outside `_kernel_end` or the expected segment. For a security-sensitive kernel, prefer `--orphan-handling=warn/error` with explicit allow/`DISCARD` rules; add `ASSERT` checks for `_kernel_end` and section ordering.

#### I3. Full register dump on user traps will leak state

Files: `riscv64.rs`, `dump_trap_frame`; `panic.rs`, `dump_cpu`

The current trap path prints every GPR plus CSRs on any unhandled trap. Once user processes exist, a user-triggered fault can dump kernel/user register contents to the console. Keep full dumps for fatal kernel bugs, but use limited, non-secret diagnostic output for recoverable user traps.

#### I4. Trap frame does not save FPU/vector state

Files: `riscv64.S`, `riscv64.rs`

The frame covers GPRs and four CSRs only. `riscv64gc` includes F/D. Future user tasks will need FPU/vector save/restore on context switch/traps; `init/sanitize_csr` currently clears `sstatus.FS`.

## What looks correct

- **Boot entry**: `_start` clears `SIE`, clears `satp`, executes `sfence.vma`, initializes `gp`, parks secondary harts before touching shared BSS, zeroes BSS plus boot stack, then sets `sp`. The secondary-hart park path avoids shared memory contamination.
- **UART DLAB ordering**: `uart::init` sets DLAB before writing divisors, clears DLAB before writing IER, and inserts MMIO fences at the critical points. The bounded TX wait and dropped-character counter are appropriate for a debug console.
- **Trap frame save/restore basics**: all GPRs are saved exactly once, CSR slots match the Rust constants, and the compiler-time `TRAP_FRAME_WORDS * 8 == 288` check prevents Rust/assembly drift.
- **Timer deadline strategy**: deadline increment avoids cumulative drift; global interrupts are enabled only after timer/interrupt sources and the trap vector are prepared.
- **Buddy split/merge logic**: the core order-0..12 splitting/merging behavior, buddy XOR indexing, double-free rejection, and interior-page rejection are correct. The self-test covers reuse, split/merge, alignment, double-free, and interior-page free.
- **Panic path**: double-panic guard, interrupt disable before logging, halt, and best-effort CPU/stack-watermark dump are sensible for M0.
- **Linker layout**: stacks are outside the kernel image so they are not accidentally consumed by the future physical allocator; `_alloc_start` is explicitly after the reserved areas.
- **CI/Makefile**: build, clippy, fmt, and QEMU smoke test are reasonably equivalent; the CI correctly waits for full 10s output before grepping.

## Blind spots & suggestions for the next milestone (M1: trap handling)

- **Fix trap entry context switching first**: reload kernel `gp`/`tp`, and install per-hart trap stacks and per-hart CPU state. This is the highest-priority M1 trap item.
- **Define nested-trap policy**: recoverable nested traps on the current shared trap stack are not safe as noted in H2/M5. Either implement true nesting safely or treat nested traps as fatal with an explicit guard.
- **Correct the trap frame layout contract**: expand the frame to 40 slots before adding reserved CSRs, or remove the misleading comment.
- **Add guard pages**: between kernel data and boot stack, and below the trap stack, once MMU is enabled. Stack-watermark diagnostics are after-the-fact.
- **Move off QEMU constants**: parse FDT for UART base/clock, RAM size, and timer frequency early in `kernel_main`.
- **Harden allocator before user mode**:
  - store usable page count separately;
  - reject free of padding pages;
  - provide zeroed allocation for user-visible pages;
  - add interrupt-safe synchronization or make APIs `unsafe`;
  - replace security-relevant `debug_assert!` checks with runtime checks.
- **Make logger ISR-safe** before any ISR logs. Prefer a per-CPU ring buffer or a lock with a dedicated panic path.
- **User-trap policy**: user-caused exceptions must be recoverable/kill-the-process in M2+, not the current `error!`/`halt`. Reserve full register dumps for kernel bug debugging.
- **Save/restore FPU and future vector state** in trap frames/context switches; decide FS/VS policy now.
- **Test on non-zeroed RAM**: QEMU normally zero-fills DRAM, which hides uninitialized trap-stack and padding bugs. Add a bootloader/SBI test that deliberately writes a pattern to RAM before jumping to the kernel.
