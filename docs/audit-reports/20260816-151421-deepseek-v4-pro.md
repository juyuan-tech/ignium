# Independent AI audit (deepseek-v4-pro)

- date: 20260816-151421
- model: deepseek-v4-pro
- tool: scripts/ai_audit.py (external reviewer, not the author)

## Executive summary

The M0 boot chain is cleanly structured and works in QEMU. The code is mostly disciplined: single unsafe-point abstraction layer (`src/uart.rs`, `src/arch/riscv64.rs`), explicit `#[deny(unsafe_op_in_unsafe_fn)]`, bounded UART polling with drop accounting, and a reentrance-guarded panic handler. The linker script explicitly disposes of `.eh_frame` and orders `.text.entry` first.

However, there are two issues that are formally undefined behaviour or close to it, both in the arch layer, and several design decisions that will bite hard at M1 (trap handling) unless addressed now. The most important one: the inline-asm `cpu_state()` captures registers without declaring them as operands, which violates Rust's inline-asm contract and is UB even though it currently produces working code. The second: the assembly trap frame clobbers `t6` before saving it and omits all CSRs, making context restore impossible — it works for M0 only because every trap halts. Additionally, `entry.S` uses `fence` instead of `sfence.vma` after writing `satp`, a real-hardware hazard that QEMU will not expose.

## Findings (severity-ranked)

### CRITICAL

---

**Finding 1: `cpu_state()` inline assembly reads registers not declared as operands — formal UB**

- Severity: CRITICAL
- File: `src/arch/riscv64.rs:43-54`

The `asm!` block inside `cpu_state()` does:

```rust
asm!(
    "mv {ra_o}, ra",
    "mv {sp_o}, sp",
    "mv {gp_o}, gp",
    "mv {tp_o}, tp",
    "csrr {sstatus_o}, sstatus",
    ...
)
```

`ra`, `sp`, `gp` and `tp` appear in the template as source registers but are not declared as `in(...)` operands. The Rust inline-asm rules require that every register accessed inside the asm block must be listed as an operand; the compiler does **not** parse the template, so it is allowed to assume `ra`, `sp`, `gp` and `tp` are neither read nor written. This is UB.

In practice the current toolchain happens to produce correct code (LLVM reserves `gp`/`tp` on RISC-V, and `cpu_state` is a leaf so `ra` is still live), but there is no guarantee. A future optimizer pass or a different inlining decision can clobber any of these registers and the diagnostic dump will silently contain garbage.

Additionally, even when the read works, the returned `ra`/`sp` are those of `cpu_state` itself (or its inline site), not the original faulting context. In a panic path the "ra"/"sp" fields are therefore misleading. The trap frame printed by `trap_handler` is the only faithful register dump.

- Fix: Either (a) rewrite `cpu_state` in assembly in `src/arch/riscv64.S` with a defined ABI, or (b) declare the special registers explicitly, e.g. `in("x1") current_ra, in("x2") current_sp, ...`, using RISC-V register aliases, and add `options(nostack, nomem, preserves_flags)` if supported. At minimum, document that the result is "current context, not pre-fault context".

### HIGH

---

**Finding 2: `trap_vector` clobbers `t6` before saving it and stores no CSRs — the trap frame cannot be restored**

- Severity: HIGH
- File: `src/arch/riscv64.S:4-42` and `src/arch/riscv64.rs:78-105`

The very first instruction of `trap_vector` is `la t6, TRAP_FRAME`, so the interrupted `t6` is destroyed before it is stored at `30*8(t6)`. The saved frame also lacks `sstatus`/`sepc`/`scause`/`stval`/`satp` (they are only passed as arguments, then lost once `trap_handler` prints and halts). There is no `sscratch` usage to establish a trap-safe frame pointer without clobbering a GPR, and no `sret` path.

This is harmless for M0 only because `trap_handler` never returns. The roadmap explicitly promises M1 trap handling ("上下文切换 arch_thread_switch", "调度器"), which cannot be built on this frame. Any continuation from this trap would lose the pre-trap `t6` and have no way to restore the previous privilege/interrupt state.

- Fix: On entry, swap `sscratch` with a temporary GPR (`csrrw tmp, sscratch, tmp`), use the value now in `tmp` as the per-HART frame pointer, save the displaced GPR into the frame, and store `sstatus`, `sepc`, `scause`, `stval`, `satp` in dedicated frame slots. The vector should be tailored for M1: return via `sret` for exceptions and interrupts that can be handled, and only halt on unrecoverable conditions.

**Finding 3: `entry.S` uses `fence` instead of `sfence.vma` after `csrw satp, zero`**

- Severity: HIGH (real hardware; silent on QEMU)
- File: `src/entry.S:5-6`

```
csrw satp, zero
fence
```

Writing `satp` does not automatically invalidate TLB entries on every RISC-V implementation. If the previous boot stage (or SBI pass) left `satp` non-zero with cached translations, stale TLB entries may be used for the kernel's physical accesses after the switch to Bare mode. `fence` is an instruction-ordering fence, not a TLB flush. QEMU TCG flushes the TLB on `satp` write, so `make test` will pass; real hardware may corrupt memory or trap unpredictably during BSS clearing and early boot.

- Fix: replace `fence` with `sfence.vma zero, zero` after the `satp` write (and any future page-table switches must use the same pattern).

---

**Finding 4: Bootloader handoff parameters are discarded at `_start`**

- Severity: HIGH (trajectory blocker for M1+; currently masked by hardcoded QEMU values)
- File: `src/entry.S:4-18`, `src/main.rs:14`

The boot path ignores `a0` (`hartid`) and `a1` (pointer to the FDT from OpenSBI), and `kernel_main()` takes no arguments. All hardware discovery is hardcoded (`UART_BASE = 0x1000_0000`, `machine: qemu-virt`). Any real hardware or future multi-HART boot cannot discover devices, hart topology, or the platform without re-introducing the discarded FDT. This decision becomes expensive to reverse once more code is layered on top.

- Fix: Preserve `a0`/`a1` in `_start` and pass them to `kernel_main(hartid: usize, fdt: *const u8)`. In M1, parse the FDT (or pass through the SBI `fw_dynamic` info) to find the UART and timer, and route arch-dependent init through `src/arch/<platform>` modules rather than hardcoded constants in `main.rs`.

### MEDIUM

---

**Finding 5: The kernel stack lives inside `.bss` and is included in `_end`**

- Severity: MEDIUM (future allocator/MMU hazard)
- File: `linker.ld:29-37`

```
.bss : {
    *(.bss*)
    *(.sbss*)
    *(COMMON)
    . = ALIGN(16);
    _stack_bottom = .;
    . += STACK_SIZE;
    _stack_top = .;
}
. = ALIGN(4K);
_end = .;
```

Two consequences:
1. `_end` is past the 64 KiB stack. The natural meaning of `_end` ("first free physical byte after the kernel image") will cause the M1 physical memory allocator to hand out pages that overlap the boot stack, corrupting it.
2. The entry code zeroes from `_bss_start` to `_stack_top`; any future `.bss`-like section placed after the stack block but before `_end` would not be zeroed by `entry.S`.

- Fix: Move the stack out of the `.bss` output section: either into a dedicated `.stack` section (NOBITS) placed after `_end`, or keep it in `.bss` but define `_end` *before* the stack (`_end = .` before `_stack_bottom = .;`). The entry clearing loop should clear all of `.bss`, and the stack should be zeroed separately by `_start` if necessary. In the M1 allocator, explicitly reserve `[stack_bottom, stack_top)` in the physical-memory map.

**Finding 6: Log path is not trap/ISR-reentrant**

- Severity: MEDIUM now / HIGH once interrupts are enabled
- File: `src/logger.rs:51-59`, `src/uart.rs:57-72`, `src/arch/riscv64.S:38-42`

`logger::log` and `uart::putc` have no locking. If a trap is taken while a previous log statement is mid-write (the UART byte loop is a polling loop with a 65536-iteration limit), the trap handler's `error!` calls will interleave UART output with the interrupted log line. Below the WAIT limit this garbles the console; at the limit it drops bytes. After M1 enables the timer interrupt, a log call in kernel context can be interrupted and then a second log call from the ISR interleaves. If the trap handler ever returns, the nested `putc` spin path also creates the classic self-deadlock (outer context holds no lock but the inner context cannot progress until the outer context resumes).

- Fix: Add a small spinlock (`AtomicBool` compare-exchange loop) around the logger's `writeln!` call, or around the entire UART writer, and have the panic path bypass the lock after a `PANICKING` flag is set, as the existing panic guard already does. Before enabling timer interrupts in M1, prove that `logger::log` cannot be re-entered.

**Finding 7: Toolchain/reproducibility drift — `rust-toolchain.toml` omits `clippy`/`rustfmt`, `Makefile` depends on `rust-objcopy`**

- Severity: MEDIUM (build reproducibility)
- Files: `rust-toolchain.toml:2-4`, `Makefile:6-7`, `README.md` (Quick Start section)

`rust-toolchain.toml` pins `1.97.1` but lists only `rust-src` and `llvm-tools`. Local `make clippy` / `make fmt` will fail for a user whose pinned toolchain lacks those components, even though CI passes because `dtolnay/rust-toolchain` explicitly adds them. Conversely, `make bin` uses `rust-objcopy`, which is **not** installed by the `llvm-tools` rustup component; it comes from `cargo install cargo-binutils`. The README's Quick Start never mentions `cargo-binutils`, so `make bin` fails in a fresh setup. This is the kind of "works in CI, breaks locally" drift that costs maintainers time later.

- Fix: Add `cli`py and `rustfmt` to the `components` array in `rust-toolchain.toml`, change the Makefile to use `llvm-objcopy` (installed with `llvm-tools`) or document the `cargo-binutils` dependency. Run `make clippy` and `make fmt` in CI using the same entrypoints, not parallel toolchain action invocations.

### LOW

---

**Finding 8: `stvec` is not initialized until after UART init; early fault is unrecoverable**

- Severity: LOW
- File: `src/main.rs:14-16`

The `trap_vector` is installed by `arch::init_traps()` only after `uart::init()`. Before that, `stvec` contains whatever OpenSBI left behind (possibly `0`). Any exception during early boot — caused by RAM corruption, or a future refactor adding a memory access before `init_traps` — jumps to address 0 or garbage instead of a diagnostic. M0 has no reason to fault there, but the trap handler is one of the few recovery mechanisms the kernel has.

- Fix: Set `stvec` at the very start of `_start`, before BSS clearing, with a minimal vector that parks the hart or preserves the trap state. OpenSBI handoff happens with interrupts disabled, so installing the vector early is cheap and makes corrupted-RAM diagnosis possible.

---

**Finding 9: `gp` is never initialized and `__global_pointer$` is not defined**

- Severity: LOW
- Files: `src/entry.S`, `linker.ld`

The RISC-V psABI expects `gp` to point into the small data area for gp-relative linker relaxation. `_start` never sets `gp`, and the linker script does not define `__global_pointer$`, so the current binary is safe only because rust-lld disables gp-relative relaxation when the symbol is absent. If a future linker change or optimization enables relaxation, the kernel will use an uninitialized `gp` and corrupt data access.

- Fix: either explicitly avoid relaxation (current behavior, document it), or define `__global_pointer$ = _gp;` in the linker script and initialize `gp` in `_start` (`la gp, __global_pointer$`). The latter is the standard approach and future-proofs the code.

---

**Finding 10: Linker script path is relative to the working directory**

- Severity: LOW
- File: `.cargo/config.toml:4-5`

```
rustflags = ["-C", "link-arg=-Tlinker.ld"]
```

The `-Tlinker.ld` path is resolved relative to the directory where `cargo` is invoked. `make` and the CI workflow run from the repo root, but a user invoking `cargo build` from a subdirectory (or a build service using a different cwd) will fail with "cannot open linker script". Cargo does not track the linker script for rebuilds either, so editing `linker.ld` alone may not re-link.

- Fix: Generate the linker script path via a `build.rs` (e.g., `println!("cargo:rustc-link-arg=-T{}", env!("CARGO_MANIFEST_DIR") + "/linker.ld")`) or use a wrapper script that changes to the repository root. A `build.rs` also gives cargo the opportunity to emit `cargo:rerun-if-changed` for the linker script.

**Finding 11: No orphan-section policy in the linker script**

- Severity: LOW
- File: `linker.ld:1-44`

The script explicitly captures `.text*`, `.rodata*`, `.srodata*`, `.data*`, `.sdata*`, `.bss*`, `.sbss*`, `COMMON`, and discards `.eh_frame`/`.comment`. It does not mention `.riscv.attributes`, `.note.*`, `.rela.*`, `.got*`, `.plt*`, or `.eh_frame_hdr`. rust-lld currently places non-allocatable orphans after `_kernel_end`, which is benign, but the presence of any allocatable orphan would silently change the kernel image layout and potentially render `_end`/`_kernel_end` incorrect.

- Fix: Add an explicit `/DISCARD/` for known non-allocatable orphans (`.riscv.attributes`, `.note.GNU-stack`) and enable `--orphan-handling=error` in CI (via `rustflags` or in the Makefile) to catch future orphans.

---

**Finding 12: `level()` fails open for invalid atomic values**

- Severity: LOW (INFO if only internal callers)
- File: `src/logger.rs:28-36`

`LOG_LEVEL` is an `AtomicU8` that can hold any value. `level()` maps `0..=3` to `Error..Debug` and **any other value (4+) to `Trace`**. If the atomic is ever corrupted (e.g., via RAM fault or a future bug), the logger silently becomes maximally verbose, potentially printing sensitive state in debug/trace messages.

- Fix: Map unknown values to `Error` (fail closed) or clamp to the highest known level, and add a comment explaining the security choice.

---

**Finding 13: `cpu_state()` misreports `ra`/`sp` as "pre-fault" state in panic dumps**

- Severity: LOW (diagnostic quality)
- Files: `src/panic.rs:50-74`, `src/arch/riscv64.rs:33-55`

Even after fixing the inline-asm operand issue (Finding 1), the `ra`/`sp` reported by `dump_cpu` are the **current** values inside the panic handler, not the faulting context. The trap handler prints a faithful pre-trap frame (except `t6`, per Finding 2), but the panic path never reads `TRAP_FRAME`. For panics that are not preceded by a trap, the dump's `ra`/`sp` are misleading. The code even says "best-effort until M1", but M1 work should capture the actual faulting frame.

- Fix: If the panic originates from a trap, read the frame from `TRAP_FRAME` (or pass it into the panic handler via a thread-local/atomic pointer). For non-trap panics, document that `ra`/`sp` are from the panic site, not the original fault site.

## What looks correct (so the author knows what not to change)

- **BSS clearing and stack initialisation order.** `_bss_start` to `_stack_top` is cleared before `sp = _stack_top` is set, and the clearing loop uses unsigned `bgeu` with 8-byte stores — correct for the given linker alignment.
- **Linker section ordering.** `*(.text.entry)` is placed before `*(.text*)`, guaranteeing `_start` is the entry point and that the kernel starts at `0x80200000`.
- **UART register programming.** DLAB handling, DLL/DLM divisor, LCR, FCR and IER sequence are correct for a NS16550, including the DLAB/IER shared-address subtlety.
- **Logger level filtering.** `lvl > level()` with the given enum ordering correctly suppresses Debug/Trace at Info level and preserves Error/Warn.
- **Panic reentrancy guard.** `PANICKING.swap(true, ...)` + `arch::halt()` on reentry is a clean, minimal double-panic protection consistent with the single-core M0 stage.
- **UART write bounding.** The `TX_WAIT_LIMIT` spin cap with `TX_DROPPED` accounting prevents a hung UART from hanging the entire kernel in `putc`.
- **Inline asm in `irq_disable`/`wait_for_interrupt`.** `csrc sstatus, 2` and `wfi` are correctly declared with `nomem, nostack`; no hidden register operand issue there.
- **Rust safety discipline.** `#![deny(unsafe_op_in_unsafe_fn)]`, narrow `unsafe` blocks, `read_volatile`/`write_volatile` for MMIO, `overflow-checks = true` in both profiles — this is the right baseline for a security-focused kernel.
- **`#[panic_handler]` and abort panic strategy.** `panic = "abort"` together with a well-formed `PanicInfo` dump is correct for a no_std kernel.
- **CI smoke test catches boot regressions.** The pipeline asserts the exact M0 log line and runs clippy/fmt — appropriate for this milestone.

## Blind spots & suggestions for the next milestone (M1: trap handling)

The current code is structured for a "halt on trap" world. M1 changes the rules:

1. **Redesign the trap frame from scratch.** Use `sscratch` to bootstrap the frame pointer without clobbering any GPR; store all 31 GPRs plus `sstatus`, `sepc`, `scause`, `stval`, `satp`; make the frame layout a single `#[repr(C)]` Rust struct shared between assembly and `trap_handler`. Do not build on the current `TRAP_FRAME` array.
2. **Distinguish exceptions from interrupts.** Check `scause` bit 63; timer interrupt (`scause == 0x8000000000000005` for S-mode timer) should be handled and then return via `sret`, while faults can panic. The M0 "trap = halt" logic must become a proper trampoline.
3. **Establish a per-HART trap stack.** With only one kernel stack, a fault from kernel mode reuses the same SP and makes nested fault diagnosis impossible. Initialize `sscratch` in `_start` or `kernel_main`, and give each HART a dedicated trap stack.
4. **Synchronise the logger before enabling interrupts.** The reentrancy hazard in Finding 6 must be closed with a spinlock or equivalent before `sie`/`stimecmp` are enabled. Also consider a "panic lock already held" fast path.
5. **Preserve and consume the bootloader FDT.** M1's `arch_timer_init` and `arch_mmu_map` need hardware discovery. Move the UART and timer base addresses out of `main.rs` into an arch/platform module fed by the FDT.
6. **Move the stack out of the allocator's view.** Decide before the buddy allocator is written where `_end` points; either place the stack outside of `_end` or reserve the range explicitly. Otherwise early allocator tests will randomly corrupt the boot stack.
7. **Set `stvec` as early as possible in `_start`.** Once traps can be handled, the boot path should have a minimal handler before any later init code runs. The earlier `stvec` is installed, the more diagnosable early boot becomes.
8. **Use `sfence.vma` after every `satp` write.** M1 introduces page tables; the M0 `fence`-instead-of-`sfence.vma` mistake must not carry forward. Treat any `satp` write as requiring a full TLB flush.
9. **Add fault-injection tests to CI.** Illegal-instruction trap, timer interrupt, and a deliberate `panic!` from a trap context should all produce the expected register dump without hanging QEMU. This will catch trap frame regressions before they become debugging sessions.
10. **Make the trap-vector `t6`-clobber a code-review checklist item.** The M1 scheduler's context switch cannot tolerate a lost `t6`. Cross-check the trap entry and the `arch_thread_switch` implementation against each other to make sure the saved state is byte-for-byte restorable.
