# Independent AI audit (deepseek-v4-pro)

- date: 20260817-101249
- model: deepseek-v4-pro
- tool: scripts/ai_audit.py (external reviewer, not the author)

## Executive summary

The code base is exceptionally well documented for a from-scratch kernel at this stage, with careful attention to boot ordering, trap-frame layout, MMIO ordering, linker-script symbol contracts, and CI reproducibility. I found no **currently triggerable** memory-safety or control-flow bug in the single-core QEMU boot path: the entry code, trap vector, buddy allocator, Sv39 setup, UART driver, and panic path are all internally consistent for the stated M0/M1 scope.

The serious risks are **latent integration hazards** that will become live the moment the kernel moves beyond the parked-secondary-hart, single-core, QEMU-only environment:

1. The trap stack is declared in one place as “per-hart” but implemented as a **single global stack** (linker script). The nested-trap detection logic in `trap_vector` cannot distinguish “hart A already has a frame here” from “hart B also thinks it is the first trap.” When secondary harts wake up, two harts will silently overwrite each other’s trap frames, causing catastrophic state corruption with no diagnostic.
2. Sv39 leaf PTEs are created without the A/D bits. QEMU sets them automatically; some real hardware requires software to set them, producing page faults on the very first access. The kernel has no handler for that case.
3. The timer ISR ignores the return code from `sbi_set_timer`. If programming the next timer fails on real firmware, the tick silently stops and the kernel runs without a timer, which for a microkernel is a dead system.

Numerous smaller hardening items are listed below. Nothing here requires rewriting the code, but the multi-core and real-hardware assumptions should be corrected before M1 is declared complete.

## Findings (severity-ranked)

### CRITICAL

None found for the current QEMU single-core path.

### HIGH

**H1 — Single global trap stack and nested-trap detection cannot survive multi-hart wake-up**
- **Files:** `kernel/linker.ld` (`.trap_stack` region), `kernel/src/arch/riscv64.S` (`trap_vector`), `kernel/src/arch/riscv64.rs` (`init_traps`, `trap_handler`)
- **Description:** The linker script defines exactly one global `_trap_stack_top` / `_trap_stack_bottom`, and `init_traps()` writes that single `_trap_stack_top` into `sscratch`. The comment in `riscv64.rs` says “sscratch 保存 per-hart 陷阱栈顶,” but this is factually false — it is a per-hart **CSR** containing a **global** value. The nested-trap detection compares `t6` against `_trap_stack_top - 288` and considers that “first-level trap.” If a second hart enters `trap_vector`, its `sscratch` still holds the global top (each hart’s CSR write is hart-local), so it compares equal, passes the nested check, and writes its frame at exactly `_trap_stack_top - 288` — the same address where hart A’s frame is stored. The result is silent cross-hart frame corruption: saved registers, `sepc`, `sstatus`, `scause`, and `stval` of the interrupted contexts are overwritten. Recovery (`sret`) then restores garbage CSRs and GPRs, leaving the system in an undefined state.
- **Concrete fix:** Before enabling secondary-hart traps, replace the global `.trap_stack` with an array indexed by hartid (or by `tp`/`sscratch` from a per-CPU structure). The nested-detection comparison must use the per-hart stack top, not a global symbol. Update the incorrect comment in `riscv64.rs`. Until then, do not enable interrupts on secondary harts.

**H2 — Sv39 leaf PTEs lack the A (accessed) and D (dirty) bits; relies on QEMU’s automatic A/D update**
- **File:** `kernel/src/mmu.rs` — PTE flag constants, `pte()` constructor, `map_super()`, `map_4k()`
- **Description:** The kernel creates leaf PTEs with only `V`, `R`, `W`, and `X` flags. RISC-V Sv39 permits two A/D handling models: hardware-managed and software-managed. Hardware-managed implementations (including QEMU) set A/D automatically and the kernel runs fine. Some real RISC-V cores (and certain platform configurations) require software to set A/D bits; if the bits are clear, the first access to the page raises a page fault (`scause = 0xC` load / `0xD` store, `stval` = faulting address). The kernel’s trap handler treats any synchronous exception as fatal and halts, so the system fails to boot on such hardware.
- **Concrete fix:** Set `PTE_A` (bit 6) and `PTE_D` (bit 7) on all leaf PTEs during mapping. This is correct for both hardware-managed and software-managed implementations — hardware-managed hardware simply treats the set bits as already valid. If you later want to support software A/D fully, add an exception-path check that sets A/D and retries instead of halting, but setting them at creation already eliminates the boot-time fault.

### MEDIUM

**M1 — Timer ISR ignores `sbi_set_timer` return code**
- **File:** `kernel/src/arch/riscv64.rs` — `trap_handler`, timer branch: `crate::sbi::set_timer(next);`
- **Description:** In the timer interrupt handler, the result of `sbi_set_timer(next)` is discarded. If the SBI call fails (unsupported invocation, firmware bug, invalid future timer value on real hardware), the timer never fires again. `TICK` freezes, `uptime` output stops, and later scheduler/IPC code will hang indefinitely. The failure is completely silent. The module comment in `sbi.rs` even claims “ISR 内可忽略,” which is poor guidance for a microkernel where the timer is the only scheduling heartbeat.
- **Concrete fix:** Check the return code in the ISR. If non-zero, either panic with a clear diagnostic (timer loss is fatal) or maintain an error counter and log via a non-ISR-safe mechanism. At minimum, do not silently ignore it.

---

**M2 — `mem::self_test` uses a fixed 256-entry array; can fail falsely under fragmentation**
- **File:** `kernel/src/mem.rs` — `self_test()`: `let mut held = [0usize; 256];`
- **Description:** The self-test allocates all pages in decreasing order and stores each block address in a fixed-size array of 256 entries. With the current 128 MB QEMU layout and a small FDT reservation, the number of blocks after carving is far below 256, so the test passes. But on real hardware with a different RAM size, a larger or differently placed FDT, or future reserved regions, the carve logic can produce **more than 256 distinct blocks** (especially the small-order blocks around the reservation). The self-test then returns `"held overflow"` and the kernel panics during boot, even though the allocator itself is correct.
- **Concrete fix:** Make the held-buffer dynamically sized (e.g., allocate a temporary page from the allocator itself before the test, or store addresses in a fixed-size array per order with a bounded total, or simply count blocks first). Better: redesign the test to avoid storing an unbounded number of addresses — e.g., accumulate allocated addresses into a linked list on the allocated pages themselves, or run the exhaustion test against a bounded subset representative of all orders.

---

**M3 — Linker script places non-alloc sections after `_alloc_start`, inviting future allocator corruption**
- **File:** `kernel/linker.ld` — `.debug` and `.riscv.attributes` sections after `_alloc_start`
- **Description:** The allocator free-area start symbol `_alloc_start` is defined before the `.debug` and `.riscv.attributes` output sections. These specific sections are non-alloc, so they are not loaded into memory and the current binary is safe. However, the symbol is semantically exposed via `extern "C" static _alloc_start: u8` in `mem.rs`; any future section that **is** alloc placed after `_alloc_start` (e.g., a future `.init_array`, `.tdata`, or a new firmware region) would be loaded into RAM and then silently overwritten by the buddy allocator. The linker script’s comment says “新段靠 code review,” which is weak protection.
- **Concrete fix:** Either:
  - move all non-alloc sections (`.debug*`, `.riscv.attributes`, `.symtab`, `.strtab`, etc.) **before** `_alloc_start` in the script, while still ensuring they are not in a load segment, and add a `/DISCARD/` for any remaining alloc hazards, or
  - define `_alloc_start` after **all** loadable sections and use a clear `ALLOCATABLE_REGION` marker consistent with ELF program headers. Also document that no section with `SHF_ALLOC` may ever be placed after `_alloc_start`.

**M4 — Hardcoded platform constants will break real hardware**
- **Files:** `kernel/src/mem.rs` (`RAM_START`, `RAM_END`, `FDT_RESERVE_SIZE`), `kernel/src/uart.rs` (`UART_BASE`, divisor `0x0C` for 1.8432 MHz), `kernel/src/arch/riscv64.rs` (`TIMER_INTERVAL` assuming 10 MHz mtimer)
- **Description:** The kernel assumes QEMU virt’s exact memory map (128 MB at 0x8000_0000), UART base 0x1000_0000, 1.8432 MHz UART reference clock for a 9600 baud divisor, 10 MHz mtimer, and a fixed 1 MB FDT reserve. Each assumption is noted in comments as a known limitation, but together they guarantee the kernel will not boot on real silicon without modification. In particular, the UART divisor values (0x0C/0x00) produce 9600 baud on a 1.8432 MHz clock, while the module header claims “115200”; this mismatch is not just a comment error but would cause wrong baud rates on real hardware.
- **Concrete fix:** Parse the FDT (M1.5) to obtain RAM size, UART base, and clock frequency. Replace `TIMER_INTERVAL` with a value derived from the platform timer frequency. Until then, move all hardcoded platform assumptions into a single `board_config.rs` or `target/qemu_virt.rs` with `#[cfg]` separation, so real-hardware bring-up does not require editing scattered constants.

### LOW

**L1 — `.cargo/config.toml` linker-script path depends on CWD**
- **File:** `.cargo/config.toml` — `rustflags = ["-C", "link-arg=-Tkernel/linker.ld"]`
- **Description:** The path is relative to the workspace root. Running `cargo build` from inside `kernel/` resolves to `kernel/kernel/linker.ld` and fails. The comment documents this, but it is a frequent developer trap and a reproducibility hazard for scripts and IDEs.
- **Concrete fix:** Use an absolute path derived from `CARGO_MANIFEST_DIR` (e.g., a `build.rs` in `kernel/` that emits `cargo:rustc-link-arg=-T` with a canonical path), or move `linker.ld` to the workspace root and use `-Tlinker.ld`.

**L2 — Incorrect/stale comments in `sbi.rs`**
- **File:** `kernel/src/sbi.rs`
- **Description:** The module comment says “内核当前不校验返回值,” but `enable_timer` does check the return value with `assert!`, and the ISR does not (see M1). The comment about `ISR 内可忽略` directly contradicts robust timer programming.
- **Concrete fix:** Update the comment to reflect actual behavior and document which call sites check or ignore errors.

**L3 — `panic.rs` stack-bounds fallback can mask corrupt `sp`**
- **File:** `kernel/src/panic.rs` — `current_stack_bounds()`
- **Description:** If `sp` is outside both boot and trap stack ranges, `current_stack_bounds` silently falls back to boot stack. The caller then emits a warning in `dump_cpu`, but the watermark scan still runs on the wrong bounds, producing misleading diagnostics. This is best-effort diagnostic code, not a security issue, but it can confuse post-mortem analysis after a stack overflow.
- **Concrete fix:** Return an `Option<(usize, usize)>` or a third “unknown” state, and skip the watermark when `sp` is out of range, instead of scanning an unrelated stack.

---

**L4 — Logging/tick atomics use `Relaxed` ordering**
- **File:** `kernel/src/logger.rs` — `LOG_LEVEL`, `TICK`, `tick_up`; also `kernel/src/arch/riscv64.rs` — `TIMER_DEADLINE`
- **Description:** For the current single-core, non-preemptible context, `Relaxed` is correct. The module comment already warns that the log path is not ISR-safe. But when `irq_enable` is called and interrupts become active, `TICK` is updated in the timer ISR while the idle loop reads it from the main context. Single-core still makes this race benign (no lost updates on 64-bit RISC-V, and the read is only used for heartbeat), but the use of `Relaxed` means there is no formal happens-before edge. This is acceptable at M1 but should be revisited before multi-core.
- **Concrete fix:** When scheduling or multi-core arrives, change `TICK` accesses to `Relaxed`-but-documented or stronger, and introduce an ISR-safe log path as the comments require.

---

**L5 — UART `putc` drop path can lose critical panic output**
- **File:** `kernel/src/uart.rs` — `TX_WAIT_LIMIT` and `putc`
- **Description:** If the UART is not ready or TX is stuck, `putc` drops characters after 0x10000 polls and increments `TX_DROPPED`. During a panic, the diagnostic dump may be partially dropped, which is acceptable, but the panic handler does not print `TX_DROPPED` until the dump begins, and the dropped counter itself may be lost. This is best-effort by design, but on real hardware a broken UART can silently swallow all diagnostics.
- **Concrete fix:** In the panic path, first print the dropped counter with a direct, unbounded (or shorter) write, and consider a dedicated emergency UART write that does not honor the drop limit for the first N bytes of panic output.

- **File:** `kernel/src/mmu.rs` — `init()` `map_super` flags `PTE_V | PTE_R | PTE_W | PTE_X`
- **Description:** The kernel maps all 128 MB of RAM as RWX in one shot. This includes the kernel’s own text, data, stacks, and the OpenSBI region. **I3 — CI/toolchain/versioning appears sound, with one assumption about QEMU**
- **File:** `.github/workflows/ci.yml`, `Makefile`, `rust-toolchain.toml`
- **Description:** The CI pins toolchain components and runs dev/release/clippy/fmt/QEMU smoke. The smoke test’s use of `timeout 10` and full-log assertion is good. ## What looks correct

The following areas are well implemented and should not be changed without a strong reason:

1. **Entry ordering and early trap stub** (`entry.S`): clearing `SIE`, clearing `satp`, `sfence.vma`, installing `early_trap`, zeroing BSS/stacks, parking secondary harts — all correct for the stated boot flow.
2. **Trap frame layout and nested detection for the single-hart case** (`riscv64.S`): full 31 GPR + 4 CSR frame, reliable nested-trap halt, correct sscratch management, gp reload, safe restore path.
3. **`panic!` handler** (`panic.rs`): double-panic guard, interrupt disable, stack watermark, trap-stack-aware bounds — excellent diagnostic foundation.
4. **Buddy allocator** (`mem.rs`): carving logic for reservations, padding pages, double-free rejection, block-head-only metadata, exhaustive self-test — strong design.
5. **Sv39 identity mapping** (`mmu.rs`): root table construction, superpage mapping, volatile PTE access, self-test — correct for QEMU.
6. **UART driver** (`uart.rs`): DLAB handling, MMIO fences, bounded TX wait, dropped counter.
7. **Build system**: dual-profile CI, clippy/fmt gates, `objcopy` path resolution, toolchain pinning.

## Blind spots & suggestions for the next milestone (M1: trap handling)

- **Replace the global trap stack with per-hart stacks before enabling secondary-hart interrupts.** This is the single most important architectural change. The current global stack is safe only because all secondary harts are parked with `SIE` cleared. M1’s roadmap includes multi-core; the trap path must scale with it.
- **Add a dedicated trap-stack per-hart marker.** The nested detection currently uses the link-time `_trap_stack_top`. Per-hart stacks need a per-hart top value — store it in `sscratch` as a per-hart register (already done) but use an array or per-CPU struct for the actual stack memory.
- **Implement A/D bit set-on-create and/or software A/D fault handling.** At minimum, set `PTE_A | PTE_D` in `mmu::init`. This is a one-line change per PTE flag set and removes a real-hardware boot fault.
- **Handle `sbi_set_timer` errors in the ISR.** For a microkernel, losing the timer is fatal; fail loudly rather than silently.
- **Parse FDT early to remove hardcoded board constants.** UART base, RAM size, timer frequency, and FDT actual size should come from the device tree before `mem::init` and `mmu::init`.
- **Plan for PLIC/IRQ routing.** M1 only needs timer interrupts, but if any external interrupt source is enabled (UART, virtio), the trap dispatcher must distinguish supervisor-external (`scause` 1<<63|9) and query the PLIC. The current handler’s “unhandled interrupt → halt” is correct but will need extension.
- **Establish a formal ISR-safe log path.** The current unlocked logger works only because the timer ISR deliberately avoids logging. Once any ISR prints, you will get corrupted output. Introduce a small lockless ring buffer or a per-context write latch.
- **Add a guard page between the boot stack and the allocator start** (the `_kernel_end` to `_alloc_start` gap) before enabling user mode, as the linker-script comment advises.

No code modifications were made in this review.
