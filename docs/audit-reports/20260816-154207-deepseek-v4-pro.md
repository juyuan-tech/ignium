# Independent AI audit (deepseek-v4-pro)

- date: 20260816-154207
- model: deepseek-v4-pro
- tool: scripts/ai_audit.py (external reviewer, not the author)

## Executive summary

The M0 boot chain is mostly sound for its stated single-core, no-interrupt, QEMU-virt scope: the RISC-V entry sequence correctly clears `satp`, flushes the TLB, zeroes BSS and stack, and the UART DLAB ordering, bounded TX wait, and double-panic protection are sensible. However, the review found one definite diagnostic bug in the trap register dump (GPR labels are shifted from index 8 onward), and several high-severity latent design problems that will become dangerous in M1 or on real hardware: trap entry has no trap stack and is not re-entrant, the boot stack can underflow directly into kernel data, and the stack is outside the kernel-image boundary without a separate allocator reservation. There are also several medium/low build, portability, and API-safety issues.

## Findings (severity-ranked)

### [HIGH] Trap-frame GPR dump is mislabeled from index 8 onward

**File:** `kernel/src/arch/riscv64.S:35-70` (save order), `kernel/src/arch/riscv64.rs:120-150` (`trap_handler` print code)

**Description:** The assembly stores x1..x31 sequentially into `TRAP_FRAME`, so:
- index 8 = x9 = s1
- index 9 = x10 = a0
- index 10 = x11 = a1
- ...
- index 16 = x17 = a7
- index 17 = x18 = s2
- ...
- index 30 = x31 = t6

But `trap_handler` prints:
- `regs[8..11]` as `a0..a3` — actually s1, a0, a1, a2
- `regs[12..15]` as `a4..a7` — actually a3, a4, a5, a6
- `regs[16..19]` as `s2..s5` — actually a7, s2, s3, s4
- `regs[20..23]` as `s6..s9` — actually s5, s6, s7, s8
- `regs[24..27]` as `s10,s11,t3,t4` — actually s9,s10,s11,t3
- `regs[28..29]` as `t5,t6` — actually t4,t5

The real s1, a7, and t6 are never printed under their real names. Since the entire point of M0 trap handling is a collapse diagnostic, this is a real functional bug in the crash path.

**Fix:** Use symbolic offsets or ABI-named constants in both the assembly and `trap_handler`; add an M1 test that deliberately traps with known values in registers and asserts the dump layout.

### [HIGH] Trap entry does not switch to a dedicated trap stack

**File:** `kernel/src/arch/riscv64.S:35-90`

**Description:** `trap_vector` saves the interrupted `sp` into the trap frame but never loads a new `sp`. It then executes `call trap_handler` on the stack of the faulted context. In M0 with only kernel-mode code this is usually benign, but:
- a stack-overflow trap can have `sp` just below `_stack_bottom`, causing the `call` to write into kernel data;
- in M1, a trap from U-mode will run the S-mode trap handler on a user-controlled `sp`, which is a classic privilege/escalation hazard.

This is not speculative hardware behavior; it is inherent in the current entry design.

**Fix:** In M1, store a per-hart trap stack pointer in `sscratch` (or compute it from `tp`/hartid), switch `sp` to that stack before calling C, and keep the trap frame on that stack.

### [HIGH] Trap entry is not re-entrant; nested trap can corrupt arbitrary memory

**File:** `kernel/src/arch/riscv64.S:22-30` (documented limitation), `kernel/src/arch/riscv64.S:35-80`

**Description:** The comment already admits this limitation: if a second trap occurs during `trap_handler`, the entry `csrrw t6, sscratch, t6` will move the first interrupted context’s original `t6` into `t6` and use it as the trap-frame base. Subsequent `sd` writes can corrupt arbitrary memory. Even in M0 this path can be reached if logging to a faulting/nonexistent UART causes a second trap, or on corrupted-RAM scenarios. M1 with interrupts enabled makes it far more likely.

**Fix:** Do not rely on a single static frame during handler execution. Use a per-hart trap stack with a pushed frame, keep `sscratch` initialized to the active trap stack, and/or explicitly check an in-use flag at entry with a safe double-fault path.

### [HIGH] Boot stack underflow will corrupt kernel data; stack is not reserved from future allocators

**File:** `kernel/linker.ld:67-76`

**Description:** The stack is placed immediately after `_kernel_end` and grows downward. A stack overflow therefore writes below `_stack_bottom`, i.e. into `.bss`/`.data`/image memory, including `TRAP_FRAME`, `PANICKING`, `LOG_LEVEL`, `TICK`, etc. There is no guard page or canary; the watermark is only post-mortem.

Separately, `_kernel_end` is defined before `.stack`, so an M1 physical allocator initialized from `_kernel_end`/`_end` will treat the boot stack itself as free memory unless it has an explicit reserved region. The linker comment says this design avoids the stack being included in `_kernel_end`, but it does not by itself prevent an allocator from using the stack.

**Fix:** Before M1, define an explicit allocator start symbol after `_stack_top` (or reserve `[stack_bottom, stack_top)` in the allocator), and add a guard page/unmapped page below the stack once paging exists. Reconsider placing the boot stack after a reserved non-allocatable gap.

### [MEDIUM] `__global_pointer$` is defined but `gp` is never initialized

**File:** `kernel/linker.ld:55`, `kernel/src/entry.S:26-37`

**Description:** The linker script exports `__global_pointer$`, and RISC-V linker relaxation/GP-relative small-data addressing requires `gp` to be loaded with its address by startup code. `_start` never does this. Today the tiny image may not generate any GP-relative accesses, so QEMU still works; if data grows, linker relaxation changes, or small-data sections become populated, the kernel will load/store through whatever garbage `gp` the bootloader left.

**Fix:** Either initialize `gp` in `_start`:
```
la gp, __global_pointer$
```
or stop defining `__global_pointer$` until the ABI initialization is actually implemented.

### [MEDIUM] UART base and divisor are QEMU-specific; baud divisor is inconsistent with the comment

**File:** `kernel/src/uart.rs:20`, `kernel/src/uart.rs:41-47`

**Description:** `UART_BASE` is hardcoded to `0x1000_0000`, with no FDT parsing. The comment says the divisor `DLL=0x0C, DLM=0x00` is “115200 分频”, but for the classic 1.8432 MHz 16550 reference clock, divisor 12 yields 9600 baud, not 115200. QEMU’s virtual serial is tolerant of this; real hardware may emit the wrong baud or nothing. A wrong UART base on real hardware can produce silent boot or a trap before `stvec` is initialized.

**Fix:** Derive UART base from the FDT in M1; derive the divisor from the UART clock/baud rate instead of hardcoding; at minimum correct/verify the comment and document the assumed reference clock.

### [MEDIUM] Safe functions accept raw pointers or arbitrary MMIO addresses and dereference them

**File:** `kernel/src/uart.rs:65-73` (`read_u8`/`write_u8`), `kernel/src/arch/riscv64.rs:117-150` (`trap_handler`)

**Description:** `read_u8`/`write_u8` are safe functions taking arbitrary `usize` addresses and dereferencing them. `trap_handler` is a safe `extern "C"` function taking a raw `frame: *mut usize` and calling `core::slice::from_raw_parts(frame, 31)` without validation. Under Rust’s safety model, safe code must be sound for all inputs; these functions are not. They are currently private/internal and called from assembly or fixed constants, so there is no immediate exploit, but it is an unsound API boundary.

**Fix:** Mark `read_u8`/`write_u8` and `trap_handler` `unsafe`, or validate pointer ranges (`frame` within `TRAP_FRAME`) before constructing the slice; document preconditions.

### [MEDIUM] Logger and trap handler re-entrancy rules are contradictory for M1

**File:** `kernel/src/logger.rs:20-25`, `kernel/src/arch/riscv64.rs:120-140`

**Description:** The logger header says “M1 使能中断后,禁止在 trap/ISR 上下文调用本日志”, but `trap_handler` itself is trap context and already calls `error!` repeatedly. M1 will enable timer/external interrupts and may route them through trap context, so the code as designed cannot keep this rule without a separate early/trap console or an ISR-safe buffering mechanism. Interleaved UART writes can also corrupt human-readable diagnostics even if memory remains safe.

**Fix:** Before enabling interrupts, introduce a re-entrancy-safe console (lock or per-context buffer), or make trap context use a separate low-level UART path that does not share `Writer`.

### [MEDIUM] No multi-hart parking; secondary harts share a single BSS clear loop and boot stack

**File:** `kernel/src/entry.S:24-35`

**Description:** `_start` ignores `a0`/hartid. On any multi-hart configuration (real hardware, or QEMU with `-smp 2`), all harts execute the same BSS clear loop and then use the same boot stack and `TRAP_FRAME`. This can race clearing memory while another hart is already running Rust, corrupt stack allocation, and interleave UART output. The code comments say “single hart assumption”, but the project trajectory is a microkernel, so this must be fixed early.

**Fix:** In `_start`, branch secondary harts (`hartid != 0`) to a per-hart parked loop before touching shared memory; assign per-hart stacks; later bring them up explicitly.

---

### [MEDIUM] MMIO writes for UART are volatile but not ordered by RISC-V fences

**File:** `kernel/src/uart.rs:41-47`, `kernel/src/uart.rs:65-73`

**Description:** Rust `volatile` operations prevent compiler reordering but do not emit the RISC-V `fence` required to order device-register writes in hardware. The LCR/DLL/DLM/LCR/IER sequence is order-sensitive; a real out-of-order RISC-V core may legally reorder stores to different MMIO addresses and break the DLAB sequence. THR/LSR interaction has similar ordering concerns.

**Fix:** Insert appropriate `fence(w,w)`/`fence(r,r)` or platform-defined I/O fences around device register programming and before observing LSR.

---

### [MEDIUM] CI smoke test passes as soon as the boot banner is printed; later traps/panics are masked

**File:** `.github/workflows/ci.yml:37-41`, `Makefile:40-44`

**Description:** `grep -q "M0: boot ok"` exits successfully immediately after matching, sends SIGPIPE to QEMU, and does not require the kernel to remain alive. Any fault occurring after that line is undetected. This is especially dangerous for M1 trap/timer work.

**Fix:** Run QEMU for a fixed duration and collect full output, then assert both presence of `M0: boot ok` and absence of `KERNEL PANIC`/`TRAP:`. Do not rely on `grep -q` early termination. Also consider building the dev profile in CI; the comment claims dev+release but the workflow only builds release.

### [LOW] `halt()` documents “interrupts off” but does not enforce it

**File:** `kernel/src/arch/riscv64.rs` (`halt` function)

**Description:** `halt()` says “关中断后”, then loops on `wfi` without clearing `sstatus.SIE`. Current callers mostly disable interrupts or arrive via trap entry (which clears SIE), but the second-panic path in `panic.rs` calls `arch::halt()` without invoking `irq_disable` after `PANICKING.swap` returns true. A future caller can violate the documented precondition.

**Fix:** Call `irq_disable()` at the top of `halt()`.

### [LOW] Stack watermark scans live stack memory as `usize`

**File:** `kernel/src/panic.rs:61-75`

**Description:** `stack_watermark` reads every aligned word of the stack as `usize` and compares it to zero. The stack contains live Rust values, including references and possibly padding/type-bearing bytes. Under strict provenance/Stacked Borrows, reading pointer-typed memory as `usize` can be questionable even though `usize` has no invalid bit patterns. It is only used during panic diagnostics, so impact is low, but it is suspicious.

**Fix:** Scan bytes (`*const u8`) with `read_volatile` instead of `usize`, or use `MaybeUninit<u8>`/raw byte reads; this avoids typed-read provenance questions.

---

### [LOW] Orphan-section policy is not enforced; link-script path is working-directory-relative

**File:** `.cargo/config.toml:17-20`, `kernel/linker.ld:80-89`

**Description:** The comments claim new orphan sections will “warn at link”, but the build only passes `-Tkernel/linker.ld`; it does not pass `--orphan-handling=error` or `--orphan-handling=warn`. The default linker behavior may silently place unknown sections. Also, the `-Tkernel/linker.ld` path is resolved from the current working directory, so `cargo build` from any subdirectory can fail.

**Fix:** Add explicit `-C link-arg=--orphan-handling=error` (after ensuring all legitimate sections are handled), and use an absolute/manifest-relative path or document a single supported invocation directory.

---

### [LOW] Interrupt enable state is not cleared until after assembly/BSS/stack setup

**File:** `kernel/src/entry.S:17-35`, `kernel/src/main.rs:31-35`

**Description:** `kernel_main` calls `arch::irq_disable()`, but `_start` runs the entire BSS clear and stack setup before that. A hostile or careless bootloader could leave `sstatus.SIE=1` and a stale `stvec`; an asynchronous interrupt during BSS clear would jump to whatever `stvec` remained. A malicious M-mode bootloader can do far worse, so this is not a security boundary, but clearing SIE as the first S-mode instruction would be more robust.

**Fix:** Clear `sstatus.SIE` in `_start` before any multi-instruction setup, or install a minimal trap park before clearing BSS.

## What looks correct

- `_start` clears `satp` and executes `sfence.vma` before any Rust execution (`entry.S`).
- BSS clear range is correctly bounded by link symbols and uses aligned 8-byte stores.
- UART DLAB sequence (DLAB=1 → divisor → DLAB=0 → IER) is correctly ordered, despite the divisor value concern.
- Bounded TX wait with dropped-character accounting avoids an infinite UART hang.
- Panic handler sets `PANICKING` before output and disables interrupts; double panic halts instead of recursing.
- `LOG_LEVEL` corrupted-value fallback defaults to permissive logging, which is a good diagnostic choice.
- `overflow-checks = true` and `panic = "abort"` in both profiles are appropriate for a no_std kernel at this stage.
- Linker script explicitly places text/rodata/data/bss and keeps the stack `NOLOAD`, with debug/attribute sections explicitly handled.
- `cpu_state_asm` correctly matches `CpuState` offsets and avoids Rust inline-asm ABI hazards by using a separate assembly function.
- Volatile loads/stores and atomic counters are used for MMIO and shared counters, which is the right building block.

## Blind spots & suggestions for the next milestone (M1: trap handling)

1. **Trap stack first.** Before enabling interrupts or U-mode, switch to a per-hart trap stack in `sscratch` and push the frame onto that stack. Never call C on the interrupted `sp`.
2. **Re-entrant trap path.** Make trap entry safe if a trap occurs while `trap_handler` is running; use per-hart state and a dedicated double-fault path rather than a single static `TRAP_FRAME`.
3. **Fix GPR dump indexing.** Define trap-frame offsets in one place (e.g., an `enum`/`const` mapping ABI names to indices) and test with known register values.
4. **Guard/reserve the boot stack.** Add an unmapped guard page below the stack once paging exists; reserve `[stack_bottom, stack_top)` in the physical allocator.
5. **Discover hardware via FDT.** Replace hardcoded `UART_BASE`, baud divisor, memory size, and hart count with validated FDT/SBI-derived values before any real-hardware claim.
6. **Park secondary harts early.** M1 should not assume `-smp 1`; add a secondary-hart entry path with per-hart stacks.
7. **Plan the logging path now.** Decide whether trap/ISR context logs through a lock, an ISR buffer, or a separate early console; the current logger contract already conflicts with `trap_handler`.
8. **Add fault-injection tests.** M1 should deliberately execute illegal instructions and trigger traps with non-trivial register values, verifying dump content and ensuring a second trap during `trap_handler` does not corrupt memory.
