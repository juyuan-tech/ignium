# Independent AI audit (deepseek-v4-pro)

- date: 20260816-164931
- model: deepseek-v4-pro
- tool: scripts/ai_audit.py (external reviewer, not the author)

## Executive summary

The M0 boot chain is unusually well-documented and the trap/timer path is already more complete than the stated milestone. I found no obvious memory-safety defect that would crash the current QEMU single-hart path under normal conditions. The trap entry/restore logic is largely correct, including the `sret`/SPIE handling and the dead-line-increment timer scheme.

The main weaknesses are boot-state sanitization, trap-stack headroom, duplicated ABI constants, and several M1-hardening issues that are acknowledged in comments but not yet enforced. Some of these become CRITICAL once user mode, MMU, multi-hart, or real hardware are introduced, but for the current M0 QEMU stage they are best rated HIGH/MEDIUM.

## Findings (severity-ranked)

### HIGH

#### 1. Interrupt/CSR state is not fully sanitized before interrupts are enabled
- **File/line:** `kernel/src/entry.S:20` (`csrci sstatus, 2`), `kernel/src/arch/riscv64.rs:enable_timer` (ORs `0x20` into `sie`)
- **Description:** `_start` clears only `sstatus.SIE`. It does not clear `sie`, `sip`, or other `sstatus` fields such as `SUM`, `MXR`, or `FS`. `enable_timer()` then does `csrs sie, {stie}`, which preserves any stale enable bits left by hostile or rebooting firmware. If a warm boot leaves `sie.SEIE`/`sie.SSIE` set or a pending `sip` bit set, the kernel will take an unmasked/unhandled interrupt immediately after `irq_enable()` and halt. Later, with MMU, stale `SUM`/`MXR` can also silently weaken kernel memory protection.
- **Concrete fix:** In `_start` or early in `kernel_main`, set `sie` to `0` (or only `STIE`) before enabling interrupts, clear writable pending bits in `sip` if possible, and set `sstatus` to a known safe value. At minimum:
  - `csrw sie, zero`
  - `csrci/csrw` sanitize `sip`
  - clear `sstatus` protection-related bits or write a canonical zeroed S-mode state.
  Do this before `arch::enable_timer()`.

---

#### 2. Fixed 2 KB trap-handler stack headroom is not enforced; trap-stack underflow can corrupt the boot stack
- **File/line:** `kernel/src/arch/riscv64.S:addi sp, t6, -2048` and `kernel/src/arch/riscv64.rs:trap_handler` frame validation
- **Description:** The frame validation in Rust checks only that the saved frame fits inside `[_trap_stack_bottom, _trap_stack_top)`. It does not check that the additional 2 KB `sp` headroom used by the Rust handler is also inside the trap stack. If the trap stack is nearly exhausted by nested traps, or if future logging/panic code uses more than the hard-coded 2 KB, `sp` points below `_trap_stack_bottom`, i.e. into the top of the boot stack. Writes by the handler then corrupt live boot-stack frames. The current code avoids returning from nested traps except timer interrupts, but the fixed headroom is still an unenforced assumption; any future reentrant trap or larger diagnostic output can silently violate it.
- **Concrete fix:** Validate the full required region, e.g. require `frame_base - TRAP_HANDLER_HEADROOM >= bottom` before setting `sp`. Define the headroom as a named constant shared between assembly and Rust, or use a separate dedicated trap stack layout that reserves the handler area. Add a guard/canary at the trap-stack bottom.

### MEDIUM

#### 3. No guard pages between kernel data and boot/trap stacks
- **File/line:** `kernel/linker.ld` `.stack` / `.trap_stack` sections
- **Description:** The boot stack starts immediately after `_kernel_end` and grows downward; an overflow writes into kernel data. The trap stack sits immediately above the boot stack and grows downward; an underflow writes into the top of the boot stack. The comments explicitly acknowledge this is deferred until M1, but this is a real memory-safety boundary, not merely a hardening feature.
- **Concrete fix:** Before enabling MMU/user mode, insert non-allocated/guard pages between `_kernel_end`, the boot stack, and the trap stack, and fault on access. Even without MMU, an inaccessible/unmapped guard page can be laid out and later enforced.

---

#### 4. Trap frame and CPU-state ABI constants are duplicated without compile-time checks
- **File/line:** `kernel/src/arch/riscv64.S:.equ TRAP_FRAME_SIZE, 288` vs `kernel/src/arch/riscv64.rs:TRAP_FRAME_WORDS` / `gpr::*` / `CpuState`
- **Description:** Assembly and Rust independently encode:
  - frame size (288 vs `TRAP_FRAME_WORDS * 8`),
  - GPR slot indices,
  - CSR slot offsets,
  - `CpuState` field offsets (assembly writes fixed offsets).
  They currently match, but there is no compile-time assertion. A future edit that changes one side can silently produce out-of-bounds reads/writes and mislabeled register dumps.
- **Concrete fix:** Add `const` assertions using `offset_of!`/`size_of` and a shared generated constant, e.g.:
  - `const _: () = assert!(TRAP_FRAME_WORDS * core::mem::size_of::<usize>() == 288);`
  - assert each `CpuState` field offset and `gpr::` slot offset against assembly ABI.
  Better, generate the assembly constants from a single Rust source or `.s` include.

---

#### 5. `stack_watermark()` performs byte reads through an `extern static` declared as a single `u8`
- **File/line:** `kernel/src/panic.rs` `stack_watermark()`
- **Description:** `_stack_bottom` is declared as `extern "C" { static _stack_bottom: u8; }` and then `read_volatile` walks many bytes past that one-byte Rust object. This is a common bare-metal pattern, but under strict provenance and Rust’s abstract machine it is questionable: the Rust-visible object is one byte. The current code works in practice, but this diagnostic path is technically suspicious and could be misoptimized.
- **Concrete fix:** Expose the stack region as a properly sized static, e.g. `extern "C" { static _stack_bottom: [u8; STACK_SIZE]; }`, or implement the watermark scan in assembly where linker-symbol addresses are used directly. A `core::ptr::read_volatile` over a known array is less UB-prone.

---

#### 6. Panic CPU dump is boot-stack-centric and gives false positives from trap context
- **File/line:** `kernel/src/panic.rs` `dump_cpu()`
- **Description:** `dump_cpu()` checks `state.sp` only against `[_stack_bottom, _stack_top)`. If a panic occurs while executing on the trap stack, `sp` will legitimately be in the trap stack, and the dump will print a loud `WARNING: sp ... outside stack range`. The stack watermark also scans only the boot stack. As the code moves toward richer trap handling and reentrant panic paths, this will mislead diagnosis.
- **Concrete fix:** Make panic diagnostics trap-stack-aware: report both boot and trap stack bounds, and choose the watermark region based on which stack `sp` lies in.

---

#### 7. UART is completely QEMU-virt hardcoded and no platform interrupt masking is performed
- **File/line:** `kernel/src/uart.rs:UART_BASE` and `kernel/src/arch/riscv64.rs:enable_timer`
- **Description:** Base address `0x1000_0000`, FIFO/clock/divisor assumptions, and lack of FDT parsing are documented as known limitations. More importantly, external interrupts are left enabled if the bootloader set `sie.SEIE`; only `STIE` is explicitly set. On real hardware this can cause immediate unhandled external-interrupt halts after `irq_enable` until an interrupt controller driver exists.
- **Concrete fix:** In M1, parse FDT before console init, validate the UART node, compute the divisor from the platform clock, and mask external interrupts until a PLIC/aplic driver is ready. Sanitize `sie` as in finding #1.

### LOW

#### 8. `sbi::set_timer()` safety documentation contradicts its actual timer-ISR use
- **File/line:** `kernel/src/sbi.rs` `set_timer()` doc comment, called from `kernel/src/arch/riscv64.rs:trap_handler` timer path
- **Description:** The doc says the function must not be called from a non-reentrant context with interrupts off (“不可从中断关闭期间的不可重入上下文调用本函数”), but the timer interrupt handler calls it exactly in that context. The call works because SBI `ecall` is itself reentrant, but the doc is wrong and could lead a future maintainer to incorrectly “fix” the timer path or misuse the function elsewhere.
- **Concrete fix:** Rewrite the doc to state the actual contract: safe to call from the timer ISR with SIE cleared; return value should be checked at boot and may be ignored in ISR with an uptime watchdog.

---

#### 9. Out-of-box `make bin` tooling mismatch and stale README output
- **File/line:** `Makefile:bin`, `README.md` “快速开始” and expected output
- **Description:** `Makefile:bin` invokes `rust-objcopy`, but the README/rust-toolchain setup installs `llvm-tools`, not `cargo-binutils`; `rust-objcopy` may therefore be missing. The README expected output also still says `timer not yet enabled`, while the code enables the timer and emits `M1: timer enabled ...`.
- **Concrete fix:** Install/use `cargo-binutils` or switch to `llvm-objcopy`; update README expected output to the actual M0/M1 behavior shown by CI.

---

#### 10. Timer/uptime arithmetic can overflow and panic because overflow checks are enabled
- **File/line:** `kernel/src/main.rs` idle loop (`t * 10`), `kernel/src/arch/riscv64.rs:enable_timer()` (`get_time() + TIMER_INTERVAL`)
- **Description:** Release builds have `overflow-checks = true`. Although the 64-bit counter wrap is far in the future for normal operation, both expressions are unchecked additions/multiplications. A counter wrap or corrupted `time` value would panic rather than degrade gracefully.
- **Concrete fix:** Use `saturating_add`/`checked_add` for the timer deadline and `saturating_mul`/`checked_mul` for uptime printing.

---

### INFO

#### 11. Reentrant trap design is safe today only because nested exceptions halt
- **File/line:** `kernel/src/arch/riscv64.S:trap_vector`, `trap_handler`
- **Description:** The trap stack is designed for nesting, but the 2 KB handler area and fixed trap frame distances are not protected against deep reentrancy. Today, timer interrupts are masked inside the handler, and synchronous exceptions in the handler call `halt()`, so no nested return path is exercised. M1 must formalize this before enabling external interrupts or user traps.
- **Concrete fix:** Define maximum supported nesting depth, per-hart trap stacks, and explicit stack-layout assertions. Consider using a separate interrupt stack and a distinct exception stack if synchronous exceptions may reenter while handling another trap.

---

#### 12. Future FDT parser will consume a bootloader-controlled pointer
- **File/line:** `kernel/src/main.rs:kernel_main(hartid, fdt)`
- **Description:** `fdt` is logged raw and currently unused. Once M1 parses the device tree, a malicious/buggy bootloader supplying an invalid FDT pointer or malformed contents could trigger arbitrary address reads or misconfigure hardware. Treating FDT as untrusted from the start is advisable.
- **Concrete fix:** Validate the FDT magic, length, and node offsets; bound-check all traversal; never trust base addresses or interrupt numbers without additional platform checks.

## What looks correct

- **Boot order:** `SIE` clear → `satp` zero → TLB fence → `gp` init → secondary-hart park → BSS/stack zero → stack setup → `kernel_main`. Secondary harts do not touch shared memory before parking.
- **Trap entry/return:** The `csrrw`/`sscratch` protocol, full 31-GPR + CSR save, nested-frame `sscratch` update, and “restore SIE only via `sret`/SPIE” method are idiomatic and correct.
- **Timer scheme:** Deadline-increment avoids cumulative drift; `TIMER_DEADLINE` is updated only in the ISR; the missing-interrupt failure mode is exposed by uptime output.
- **UART DLAB/fence handling:** Initialization order is correct, `\r\n` handling and bounded TX waiting with dropped-byte accounting are sound.
- **Panic path:** Double-panic guard, IRQ-disable-before-output, and stack watermark are a good diagnostic foundation.
- **CI:** The smoke test correctly waits for full QEMU output instead of early `grep -q`, checks both boot and uptime, and denies `KERNEL PANIC`/`TRAP:`.

## Blind spots & suggestions for M1 trap handling

1. **Sanitize all S-mode CSR state at entry**, not just `SIE`: `sie`, `sip`, `sstatus` protection bits, `stvec`, `sscratch`, `sepc`, `scause`.
2. **Make trap-stack layouts compile-time checked and guarded.** Add `con TAINT`-style assertions for frame size/offsets, per-hart stacks indexed by `tp`, and a guard/canary page.
3. **Do not assume a fixed 2 KB handler stack.** Move to a dedicated, separately bounded trap-handler stack or enforce the arithmetic in validation.
4. **Adopt an ISR-safe logging strategy before enabling external interrupts.** The current no-lock logger is safe only because the timer ISR does not log and other traps halt. Once external/interrupt-driven I/O arrives, concurrent UART writes or a lock taken in ISR can create priority-inversion/deadlock hazards.
5. **Treat FDT and all bootloader-provided values as hostile.** Add a validated FDT parser or defer parsing to a separate trusted boot service.
6. **Plan user-mode context save/restore now:** `satp`, FPU state, `stval`, `sscratch`, and the trap frame need to be extended for U/S transitions. The current `CpuState` is diagnostic-only and the trap frame lacks fields required for future user traps.
7. **Multi-hart wake path needs per-hart trap setup before interrupts.** Currently only `hart 0` installs `stvec`/`sscratch`; parked harts must not be woken until their per-hart state is initialized.
