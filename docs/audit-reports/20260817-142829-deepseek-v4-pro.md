# Independent AI audit (deepseek-v4-pro)

- date: 20260817-142829
- model: deepseek-v4-pro
- tool: scripts/ai_audit.py (external reviewer, not the author)

## Executive summary

M1 is unusually well-documented and the core boot/trap/memory logic is substantially correct, but the review found one **critical latent bug that makes timer-driven preemption effectively unusable** (it halts on the next interrupt after the first real preemptive switch), plus several high-impact scheduler/synchronization defects and allocator issues that current selftests mask. The selftests in their present form do not actually exercise a real preemptive context switch, do not test the adversarial Condvar ordering, and contain at least one flaky completion check. Because the kernel is headed toward user processes and IPC in M2, the scheduler and sync bugs below should be fixed before M1.5 stress testing, or the stress tests will simply hang/crash.

## Findings (severity-ranked)

### CRITICAL-1: Preemptive switch leaves `sscratch` stale; next trap is misdetected as nested and halts

- **File:** `kernel/src/arch/riscv64.S`
- **Location:** restore path at label `3:` (roughly `riscv64.S:140-155`) and nested-trap check (roughly `riscv64.S:58-70`)
- **Description:**
  When `trap_handler` returns a frame that lives in a thread’s TCB (i.e., a real preemptive switch), the restore path deliberately skips resetting `sscratch` to `_trap_stack_top` because `frame + TRAP_FRAME_SIZE != _trap_stack_top`. The `sscratch` register therefore remains equal to the previous trap-stack frame base (`top - 288`).

  On the next trap, `trap_vector` computes:
  ```
  t6 = sscratch;          // top - 288
  t6 = t6 - 288;          // top - 576
  bne t6, top - 288, nested_halt
  ```
  and branches to the nested-trap halt path (`4:`). Thus **the very next timer interrupt after any real preemptive switch halts the machine**, regardless of which thread is running.

  The current `test_busy` selftest does not catch this because it never creates a second `frame_valid` ready thread. At the time `test_busy` runs, `idle`/main is `ctx_valid` but `frame_valid=false`, and all previously spawned test threads have exited or cleared their initial `frame_valid`. `on_tick` therefore always returns the original trap-stack frame; no TCB-resident frame is ever restored. The comment “必然经历至少一次抢占” is true only in the sense of timer-trap entry, not a real context switch.

- **Fix:**
  In the restore path, always reset `sscratch` to `_trap_stack_top` before restoring GPRs/`sret`, regardless of whether the frame is on the trap stack or in a TCB. `sscratch` only represents “a trap handler is currently active”; once `sret` is issued, no handler is active, even when the restored frame came from heap memory.
  Add a dedicated selftest that creates two threads with valid `frame_valid` frames and forces an actual preemptive switch, then verifies that several subsequent timer ticks complete.

### HIGH-1: `Condvar::wait` releases the mutex without waking a waiting mutex owner

- **File:** `kernel/src/sync.rs`
- **Location:** `Condvar::wait` (roughly `sync.rs:285-305`)
- **Description:**
  `wait` pushes the current thread onto the condvar wait queue, then does:
  ```rust
  m.locked.store(false, Ordering::Release);
  core::mem::forget(guard);   // guard is deliberately not dropped
  ```
  It never calls `m.unlock()` and never pops/wakes from `m.waiters`. If a second thread is already blocked in `m.lock()`, it remains queued forever.

  Classic deadlock ordering:
  1. Producer runs first and blocks in `TEST_DATA.lock()`.
  2. Consumer runs, acquires the mutex, then calls `condvar.wait()`, releasing `locked` but not waking the producer.
  3. Consumer blocks on the condvar.
  4. Producer is needed to set the data and `notify_one`, but producer is still blocked.
  5. No future owner exists to trigger `Mutex::unlock`; deadlock.

  The current selftest masks this because `cond_consumer` is spawned before `cond_producer`, and cooperative FIFO scheduling gives the consumer the mutex first.

- **Fix:**
  After `core::mem::forget(guard)`, invoke the release path that also wakes a mutex waiter, e.g.:
  ```rust
  core::mem::forget(guard);
  m.unlock(); // or a manual pop from m.waiters + sched::wake
  ```
  Then add a producer-first / contended-release test case.

### HIGH-2: Slab allocator never reuses free slots in non-head pages

- **File:** `kernel/src/heap.rs`
- **Location:** `KernelHeap::slab_alloc` (roughly `heap.rs:126-151`) and `KernelHeap::dealloc` (roughly `heap.rs:225-238`)
- **Description:**
  Each slab page has its own `free_list`, and pages are linked through `SlabHeader.next`. However, allocation only examines `self.classes[idx].head`. When the head page is full, a new page is created and becomes the head; older pages are never searched again.

  `dealloc` correctly pushes a freed slot back onto the containing page’s `free_list`, but if that page is not the current head, nothing ever looks at that free list. The `next` chain is maintained but never traversed for allocation. Under sustained churn that causes a size class to have more than one slab page, freed memory in the older pages leaks until the kernel heap exhausts memory.

  The current `bench`/`self_test` alloc/free patterns never fill a second page while an older page holds free slots, so this passes.

- **Fix:**
  In `slab_alloc`, traverse `head`/`next` looking for the first page with `free_list != usize::MAX` before creating a new slab. Alternatively, when freeing a slot in a non-head page, move that page to the class head (taking care to unlink it from any previous chain position). Add a stress test that forces ≥2 pages in one class, frees from the older page, and verifies reuse.

### MEDIUM-1: `Scheduler::pick_next` falls back to idle without validating `ctx_valid`/`frame_valid`

- **File:** `kernel/src/sched.rs`
- **Location:** end of `Scheduler::pick_next` (roughly `sched.rs:195-226`)
- **Description:**
  Both the cooperative (`need_ctx=true`) and preemptive (`need_ctx=false`) paths end with `self.idle` when no queue candidate is acceptable. No validity flag is checked for the idle thread.

  Once idle is ever preempted (`frame_valid=true`, `ctx_valid=false`), a later cooperative `pick_next(true)` — e.g., from another thread exiting or blocking when no other `ctx_valid` thread exists — can select idle’s stale `ctx`, resuming idle at an old program point with an old stack pointer. Since idle’s real state lives in its captured trap frame at that point, this reconstructs a second/duplicated idle execution with the same TCB. The current selftests never preempt idle, so this is latent.

- **Fix:**
  Make the fallback explicit and validated:
  - In cooperative path, return idle only if `threads[idle].ctx_valid`; otherwise keep the current thread running/panic rather than loading a stale context.
  - In preemptive path, return idle only if `threads[idle].frame_valid`; otherwise continue the current frame.
  Add a test that preempts idle and then forces a cooperative fallback.

### MEDIUM-2: Timer handler has no priority-preemption path

- **File:** `kernel/src/sched.rs`
- **Location:** `Scheduler::on_tick` (roughly `sched.rs:240-275`)
- **Description:**
  `on_tick` returns the current frame unless the current thread’s time slice (`SLICE_TICKS`) has elapsed. It does not check whether a newly-ready higher-priority thread should preempt the current thread immediately.

  Consequence: a `PRIO_LOW` busy thread can run for up to 100ms before a `PRIO_HIGH` thread is dispatched, contradicting the “priority preemption” design/roadmap statement. `pick_next` only sees priority levels after a slice expires or a thread voluntarily yields/blocks.

- **Fix:**
  On every tick (or when a high-priority thread is enqueued/woken), check for a ready thread at a numerically lower `prio` with a usable frame (`frame_valid`), and switch immediately if such a thread exists. Document the intended policy explicitly.

### MEDIUM-3: Spinlocks guarding heap/allocator are preemption-unsafe

- **File:** `kernel/src/sync.rs` (`SpinLock`), `kernel/src/heap.rs` (`HEAP`), `kernel/src/mem.rs` (`ALLOCATOR`)
- **Location:** `SpinLock::lock` (roughly `sync.rs:50-65`); allocator use in `heap.rs`/`mem.rs`
- **Description:**
  `SpinLock` does not save/restore `SIE`. Comments state the lock is for main context only, but normal kernel threads allocate through `Heap`/buddy with interrupts enabled. Once preemptive switching actually works (CRITICAL-1 fix), a thread can be preempted while holding `HEAP` or `ALLOCATOR`; another scheduled thread can then spin on that lock until the next timer tick rotates back to the owner. Not a permanent deadlock under the current forced round-robin timer, but it creates lock convoys and will interact badly with priority/preemption and future IPC.

  This is already partially tracked as DEFERRED D3/D11, but with M1.5 stress testing approaching it should be resolved, not merely documented.

- **Fix:**
  Introduce IRQ-safe spinlocks (`irq_save` in `lock`, `irq_restore` in guard drop) for heap and buddy allocator, or disable preemption for the allocation critical sections. Keep ISR allocation prohibited until the IRQ-safe allocator strategy is implemented.

### MEDIUM-4: Mixed-path sync selftest completion flag is not a completion counter

- **File:** `kernel/src/sync.rs`
- **Location:** `mutex_mixed` / mixed section of `self_test` (roughly `sync.rs:395-430`)
- **Description:**
  Eight threads each increment the mutex 500 times and then set the same `TEST_MUTEX_MIXED_DONE` boolean. Main waits for that boolean, then checks whether the counter equals `8 * 500`. Since only one thread needs to finish to set the flag, main can be scheduled after the first finisher and observe a partial counter, returning `Err("mixed-path mutex counter mismatch")`.

  This is a nondeterministic test failure, not a kernel synchronization guarantee. The fact that it currently passes is scheduling luck.

- **Fix:**
  Use `AtomicUsize` completion count and wait for `finished == 8`, or use per-thread completion flags/join-like synchronization. Keep the counter equality check.

### LOW-1: `mem::zero_page` is a safe function that writes to an arbitrary address

- **File:** `kernel/src/mem.rs`
- **Location:** `zero_page` (roughly `mem.rs:340-350`)
- **Description:**
  `pub fn zero_page(addr: usize)` writes 512 `u64`s to `addr` with only `debug_assert!` alignment, which disappears in release. Rust’s safety model requires the caller to prove the pointer is valid for writes; exposing this as a safe function allows safe code anywhere in the kernel to corrupt memory by passing a bogus address. This is a latent soundness/API hazard.

- **Fix:**
  Make it `unsafe fn` and document the precondition, or add a runtime bounds/aligned check against the allocator-managed physical range (as `free_pages` already does).

### LOW-2: `context_switch` is declared as a safe extern function

- **File:** `kernel/src/arch/riscv64.rs`
- **Location:** extern block (roughly `riscv64.rs:75-90`)
- **Description:**
  `pub fn context_switch(old: *mut Context, new: *const Context);` is safe to call from Rust, despite requiring valid context pointers and interrupt-off atomicity. All current call sites happen to wrap it in `unsafe {}`, but the compiler does not require it. A safe caller could invoke it with invalid pointers.

- **Fix:**
  Declare `pub unsafe fn context_switch(...)` in the extern block, or wrap it in a Rust `unsafe fn` facade.

### LOW-3: Exited thread stacks are only reclaimed in `yield_`

- **File:** `kernel/src/sched.rs`
- **Location:** reaper loop in `yield_` (roughly `sched.rs:300-312`); idle loop in `kernel/src/main.rs`
- **Description:**
  `exit()` places the dead thread’s stack into `reaper`, but the reaper is drained only when some thread calls `yield_`. The final idle/heartbeat loop in `kernel_main` never calls `yield_`; it only calls `wfi`. Any thread that exits after boot and before the next manual yield leaves its stack allocated indefinitely. In M2 with dynamic thread creation/exit, this becomes a real leak.

- **Fix:**
  Drain the reaper in a scheduler/idle periodic path, or schedule reclamation on `wake`/`on_tick`, not only inside `yield_`.

### INFO-1: `MAX_THREADS` is reserved but not enforced

- **File:** `kernel/src/sched.rs`
- **Location:** `MAX_THREADS` / `Scheduler::spawn`
- **Description:**
  Capacity is reserved for 64 threads, but `spawn` does not reject a 65th thread. Exceeding 64 is currently safe because reallocations occur in non-ISR context, but the invariant that ISR enqueue never allocates relies on callers never spawning more. With future dynamic spawn from user-mode code, exceeding reserved capacity could evict the zero-allocation ISR property.

- **Fix:**
  Enforce `threads.len() < MAX_THREADS` in `spawn` and return/track an error, or raise capacity deliberately.

### INFO-2: `ticks_run += 1` can panic after u64 overflow because overflow checks are on

- **File:** `kernel/src/sched.rs`
- **Location:** `Scheduler::on_tick` (roughly `sched.rs:247`)
- **Description:**
  `overflow-checks = true` is enabled in release. After `2^64` ticks (~5.8 billion years at 10ms), `self.ticks_run += 1` would panic inside the timer ISR. Impractical today, but inconsistent with the project’s explicit use of `wrapping_add`/`saturating_mul` elsewhere.

- **Fix:**
  Use `wrapping_add` or `saturating_add`.

### INFO-3: `mmu::init` identity-maps the OpenSBI/firmware region as RWX

- **File:** `kernel/src/mmu.rs`
- **Location:** `init` RAM mapping loop (roughly `mmu.rs:150-165`)
- **Description:**
  The mapping starts at `RAM_START` (`0x8000_0000`) and covers the entire 128MB, including `0x8000_0000..0x8020_0000` where OpenSBI and platform firmware live, with supervisor RWX. QEMU’s OpenSBI currently protects firmware via PMP (as the self-test comment notes), but real hardware may not. This is already indexed as D2 for the kernel image split, but firmware exclusion deserves explicit attention.

- **Fix:**
  When permission splitting lands, map firmware as non-accessible or supervisor-read/execute-only if needed, and do not map it RWX.

---

### INFO-4: `early_trap` silently halts before UART is usable

- **File:** `kernel/src/entry.S`
- **Location:** `early_trap` (roughly `entry.S:110-115`)
- **Description:**
  Between `_start` and `init_traps`, `stvec` points to `early_trap`, which merely disables interrupts and loops in `wfi`. If a trap occurs during this window — especially during `uart::init` on real hardware with a wrong UART base or clock — the system dies with no diagnostic output. The window is short in QEMU but is one of the most likely real-hardware bring-up failure modes.

- **Fix:**
  At minimum, document this as a bring-up hazard. Where possible, attempt a minimal UART emergency character/status output from `early_trap`, or integrate `uart::init` into/near the early trap path.

## What looks correct

- **Boot arbitration and BSS/stack clearing:** `BOOT_LOCK` in `.data`, `amoswap` arbitration, loser-park behavior, and the single-winner BSS zero of `[ _bss_start, _trap_stack_top )` are correctly ordered and multi-hart-safe for the current stage.
- **Buddy allocator:** The top-down reserved-region carve is genuinely correct; it avoids the classic “metadata only” reserved-region overwrite bug. Double-free/interior-free rejection, alignment checks, and the exhaustive self-test are strong.
- **Trap frame layout synchronization:** GPR indices, CSR slots, `TRAP_FRAME_WORDS`, and the 288-byte compile-time assertion keep Rust and assembly consistent. Frame-pointer validation before dereference is properly done.
- **Sv39 bring-up:** Identity mapping before converting `satp`, implicit TLB assumptions of bare mode avoided, A/D bits set for hardware-managed and software-managed implementations, and UART mapped no-execute. The order `mem::init → mmu::init → heap/sched → irq_enable` is sound.
- **Linker script:** Separating `.stack`/`.trap_stack` from `_kernel_end` so the buddy allocator does not hand out stack memory is correct, and the `_alloc_start` red-line comment is useful.
- **UART DLAB sequence and bounded TX polling:** Correct 16550 ordering with MMIO fences, and no infinite hang on TX timeout.
- **Logger discipline:** ISR path does not log; tick increment is lock-free; panic path is the only trap-context log path and is terminal.
- **`irq_save`/`irq_restore` per-thread restoration:** Cooperative context-switch sites correctly preserve each thread’s prior SIE state.

## Blind spots & suggestions for the next milestone (M1.5)

1. **Fix CRITICAL-1 before any scheduler stress work.** A real preemption selftest should verify:
   - thread A is preempted while another `frame_valid` thread is ready;
   - scheduler switches threads;
   - **many** subsequent timer ticks occur without `trap_vector` nested-halt.
2. **Synchronization hardening:**
   - Condvar contended-release test (producer-first).
   - Slab multi-page free/reuse stress (e.g., allocate until ≥2 pages per class, free older slots, allocate again and assert no page-count growth).
   - Replace mixed-path boolean completion with a counter.
   - Add priority-preemption tests (HIGH ready while LOW runs).
3. **Scheduler state machine:**
   - Define validity of `ctx_valid`/`frame_valid` for idle explicitly.
   - Enforce/reconcile `MAX_THREADS`.
   - Design TCB and stack reclamation for long-running systems; reaper must be drained by a non-yield path.
   - Use wrapping arithmetic in `ticks_run`.
4. **M1.5 permit split and firmware mapping:**
   - Do not RWX-map OpenSBI/firmware on real hardware.
   - Add guard pages below boot/trap stacks and per-thread stacks once MMU permissions are split.
5. **SMP readiness:**
   - Per-hart trap stacks (D7) before waking secondaries.
   - UART output lock (D9).
   - `boot`/`panic` paths should not assume a single trap stack.
6. **Hardening real-hardware bring-up:**
   - FDT-driven UART base/clock/timer frequency and SSTC detection (D5/D17).
   - Early-trap diagnostics.
   - `zero_page`/`context_switch` unsafe API hygiene.
7. **CI improvements:**
   - Extend `test-smp` to assert heartbeat/uptime on multiple harts, not only “exactly one M0”.
   - Add a no-SSTC (`-cpu` without `sstc` or `stimecmp` trap) test once fallback logic exists.
