# Independent AI audit (deepseek-v4-pro)

- date: 20260817-123305
- model: deepseek-v4-pro
- tool: scripts/ai_audit.py (external reviewer, not the author)

## Executive summary

The Ignium kernel code (scope provided spans M0 boot chain through M1 subsystems) is generally well-structured, with thoughtful comments referencing past audits, careful assembly↔Rust ABI alignment, and deliberate handling of many low‑level RISC‑V hazards (DLAB traps, TLB flushes, gp‑relative relaxation, nested trap detection, etc.). However, the review uncovered one **critical memory‑safety defect** in the scheduler/trap integration: the scheduler’s `FRAME_WORDS` constant is 40, while the actual trap frame size is 36 words. This causes an out‑of‑bounds read on every preemption event when copying the interrupted thread’s trap frame. Two further **high‑severity** issues concern FDT reservation logic (invalid pointer can cause erroneous memory reservation) and the unconditional use of the Sstc extension (causes illegal‑instruction fault on non‑Sstc platforms). A medium‑severity CI/reproducibility problem (incorrect Rust toolchain action ref) and several lower‑severity robustness issues are also noted.

The following sections list findings ranked by severity, cite locations, explain impact, and suggest concrete fixes. Code that appears correct is acknowledged to avoid unnecessary churn. Finally, blind spots and recommendations for the upcoming trap‑handling milestone (M1) are summarized.

## Findings

### CRITICAL

#### CRITICAL‑1: Scheduler `FRAME_WORDS` mismatch with actual trap frame size leads to out‑of‑bounds read on preemption

- **File/line**: `kernel/src/sched.rs`, near `const FRAME_WORDS: usize = 40;` (also used in `Thread.frame` array and in `on_tick`’s `copy_from_slice(unsafe { core::slice::from_raw_parts(frame, FRAME_WORDS) });`).  
  Related definitions: `kernel/src/arch/riscv64.rs` `const TRAP_FRAME_WORDS: usize = 36;` and `kernel/src/arch/riscv64.S` `.equ TRAP_FRAME_SIZE, 288` (i.e., 36×8 bytes).
- **Description**: When a timer interrupt triggers preemption, `trap_handler` calls `sched::on_tick(frame)`. Inside `on_tick`, the code copies the interrupted thread’s trap frame into the `Thread.frame` buffer using `from_raw_parts(frame, FRAME_WORDS)` where `FRAME_WORDS = 40`. However, the assembly trap entry only saves **36 words** (31 GPR + 4 CSRs + 1 unused padding). Reading 40 words from the trap frame pointer reads **4 words (32 bytes) beyond the frame**, into adjacent trap‑stack data or even past the trap‑stack top (into the allocator region, since `_trap_stack_top` is followed by `_alloc_start`). This is undefined behavior in Rust, may leak kernel stack / allocator metadata, and could fault if future mapping permissions change. The extra words are stored in `Thread.frame` but are never used by the restore path (which reads only 36 words), so corruption is not directly propagated, but the UB remains.
- **Concrete fix**: Change `FRAME_WORDS` to `36` to match `TRAP_FRAME_WORDS` (or, better, reuse a shared constant from `arch`). Adjust `Thread.frame` to `[usize; 36]` and any compile‑time assertions accordingly. Add a static assertion that `FRAME_WORDS == arch::TRAP_FRAME_WORDS`.

### HIGH

#### HIGH‑1: `mem::init` trusts possibly‑invalid FDT pointer when computing reservation range

- **File/line**: `kernel/src/mem.rs`, inside `pub fn init(fdt: usize)` — the code after `fdt_size(fdt).unwrap_or(FDT_RESERVE_SIZE)` computes `fdt_start = fdt / PAGE_SIZE * PAGE_SIZE`, `fdt_end = fdt.saturating_add(reserve)`, then `rs = fdt_start.saturating_sub(base) / PAGE_SIZE`, `re = fdt_end.saturating_sub(base).div_ceil(PAGE_SIZE)`.  
  The `fdt` pointer is never sanity‑checked (non‑zero, alignment, within RAM) before this arithmetic.
- **Description**: If the FDT pointer is invalid (e.g., zero, misaligned, or outside RAM), `fdt_size` returns `None` and the code falls back to the conservative `FDT_RESERVE_SIZE` (1 MiB). However, `rs`/`re` are still computed from the bogus pointer. If `fdt == 0`, `fdt_start = 0`, and `rs` becomes 0 (due to `saturating_sub`), causing the first `re` pages of the allocatable region to be marked permanently reserved even though no FDT exists there. This can unnecessarily waste memory. Worse, if `fdt` is a random non‑zero value, an arbitrary block can be excluded from allocation, potentially reducing available memory or (less likely) interacting with buddy carving in unexpected ways. The carve routine relies on reservation indices being meaningful; a bogus reservation can disrupt allocation invariants.
- **Concrete fix**: Before using `fdt` for reservation, validate it: `fdt != 0`, `fdt` is page‑aligned (or at least 4‑byte aligned), and `fdt + reserve <= RAM_END`. If any check fails, skip reservation entirely (set `rs = re = 0`) or use a fixed safe region unrelated to the pointer. The fallback conservative size should not be applied when the pointer is known bad.

#### HIGH‑2: Unconditional use of Sstc (`stimecmp`) without capability detection

- **File/line**: `kernel/src/arch/riscv64.rs`, `enable_timer()` calls `set_stimecmp(deadline)` which executes `csrw stimecmp, ...` `set_stimecmp` is also called in `trap_handler` for the next deadline. No runtime check for Sstc extension.
- **Description**: Sstc is a RISC‑V extension not present in all platforms. On QEMU with the default `-cpu` (which may not include Sstc), the first `csrw stimecmp` causes an illegal‑instruction trap. Because `init_traps` has already installed the trap vector, this leads to the exception path in `trap_handler`, which logs an error and halts the system. The kernel therefore never reaches the main loop and fails to boot on non‑Sstc hardware. The code comments acknowledge this (“无 SSTC 的平台此指令触发非法指令陷阱 → 停机诊断(可接受…)”), but this is a portability and robustness issue for the future microkernel trajectory (the project aims for RVA23, but RVA23 mandates Sstc; however, many existing RISC‑V boards lack it).
- **Concrete fix**: Probe for Sstc support at boot (e.g., read `misa` or device tree, or attempt a benign `csrr`/`csrw` to `stimecmp` and catch trap) and maintain a flag. If Sstc is not present, fall back to SBI `set_timer` (already present in `sbi.rs`) for both initial programming and tick re‑arming. Alternatively, provide a build‑time configuration option.

### MEDIUM

#### MEDIUM‑1: CI uses invalid Rust toolchain action ref, breaking reproduciblity

- **File/line**: `.github/workflows/ci.yml`, the `uses: dtolnay/rust-toolchain@1.97.1` line.
- **Description**: `dtolnay/rust-toolchain` is a GitHub Action whose version is expressed via tags like `@v1`, `@stable`, or a specific action version (e.g., `@1.78.0`), not a Rust toolchain version. `@1.97.1` is not a valid tag for the action repository; GitHub will fail to resolve it, causing the CI workflow to error before any build. The comment says “工具链版本与 rust-toolchain.toml 严格一致”, but the correct way is to use a valid action ref and specify `with: toolchain: 1.97.1`.
- **Concrete fix**: Change to `uses: dtolnay/rust-toolchain@stable` (or `@v1`) and add `with: toolchain: 1.97.1` together with the existing `targets` and `components` inputs. Update the comment to explain the correct pinning mechanism.

#### MEDIUM‑2: Heap `page_alloc` integer overflow on very large allocation requests

- **File/line**: `kernel/src/heap.rs`, in `unsafe fn page_alloc(&mut self, layout: Layout)` — `let needed = size + 8 + align - 1;`
- **Description**: If `layout.size()` is close to `usize::MAX` (which can be produced by invalid or malicious `Layout` values, though `GlobalAlloc` does not guarantee bounds), the addition may overflow before the subsequent `order > mem::MAX_ORDER` check. Overflow wraps around to a small value, causing `pages` and `order` to be computed too small. The buddy allocator then returns a block that may be smaller than the requested size, leading to heap corruption and potential memory safety violations when the caller writes to the allocation. The `Layout` type normally protects against some invalid sizes, but `Layout::from_size_align` can produce sizes up to `isize::MAX`; exceeding `usize` max is impossible, but sizes near `usize::MAX` are possible; `size + 8 + align - 1` can overflow if `align` is large. The code does have a later check for `order > MAX_ORDER`, but the overflow occurs before that check.
- **Concrete fix**: Use checked or saturating arithmetic: `let needed = size.checked_add(8).and_then(|v| v.checked_add(align - 1)).ok_or(...)` or compute `pages` with `usize::div_ceil` on checked values. If overflow occurs, panic with a clear “allocation too large” error, as is done for `order > MAX_ORDER`.

### LOW

#### LOW‑1: `SpinLock` is not IRQ‑safe; future interrupt‑context acquisition would deadlock

- **File/line**: `kernel/src/sync.rs`, `impl<T> SpinLock<T> { pub fn lock(&self) -> ... }` and `Drop` for `SpinLockGuard`.
- **Description**: The `SpinLock` only uses an atomic flag and does not disable interrupts. The module comment explicitly restricts its use to main context, and current code (scheduler) manually wraps acquisitions with `irq_save`/`irq_restore`. However, this invariant is enforced only by convention; nothing prevents a future contributor from using `SpinLock` in an interrupt handler or in code that runs with interrupts enabled and is also reachable from an interrupt context. If an interrupt fires while the spinlock is held with interrupts enabled, the ISR will spin forever on the same hart. This is a known limitation tracked as DEFERRED D3, but it deserves emphasis as a latent deadlock risk for the upcoming M1 trap milestone (where more interrupt types may be added).
- **Concrete fix**: Introduce an IRQ‑safe lock type (e.g., `IrqSafeSpinLock` that saves/disables SIE on lock and restores on unlock) and migrate all locks that could be touched from interrupt context to it. Alternatively, use a design where interrupts are always disabled when acquiring any lock, and enforce this via `#[deny(unsafe_op_in_unsafe_fn)]` and code review. For the short term, add an assertion or comment at every lock acquisition site.

#### LOW‑2: `panic.rs` `current_stack_bounds` falls back to boot stack on unknown `sp`

- **File/line**: `kernel/src/panic.rs`, `fn current_stack_bounds(sp: usize) -> (usize, usize)` — if `sp` is outside both boot and trap stack ranges, it defaults to `(boot_bottom, boot_top)`.
- **Description**: If the stack pointer is corrupted (e.g., due to a stack overflow that clobbers `sp`), the panic handler will scan the boot stack even though the crash may have occurred on the trap stack or elsewhere. The resulting watermark will be misleading, but no memory safety issue arises because the scan is bounded by the stack region. This is a diagnostic quality issue.
- **Concrete fix**: If `sp` is not within any known stack, mark the watermark as “unknown” rather than scanning a default region. This would make the panic output more honest and force developers to inspect the raw `sp` value.

#### LOW‑3: UART TX poll limit may be insufficient on slow real hardware

- **File/line**: `kernel/src/uart.rs`, `const TX_WAIT_LIMIT: u32 = 0x1_0000;`
- **Description**: The bound is chosen to avoid infinite blocking on a stuck UART. On extremely slow baud rates (e.g., 1200 baud) or real hardware with large FIFO delays, 65,536 iterations of poll‑and‑spin may be insufficient, leading to dropped characters even when the UART is functional. The console becomes lossy, which is acceptable for debug output but could hide important panic messages during bring‑up.
- **Concrete fix**: Make `TX_WAIT_LIMIT` configurable via a board‑specific constant or increase it to a larger value (e.g., several hundred thousand). Consider using a timer‑based timeout rather than a fixed loop count.

### INFO

#### INFO‑1: Full RAM mapped RWX from `RAM_START` includes OpenSBI region

- **File/line**: `kernel/src/mmu.rs`, `pub fn init()` maps the entire `[RAM_START, RAM_END)` range with `2MB` superpages and flags `RWX + A/D`. This covers the address range `0x80000000–0x80200000`, which belongs to OpenSBI. Although OpenSBI uses PMP to protect itself from S‑mode writes, mapping it as writable is unnecessary and slightly increases the attack surface if PMP is misconfigured or a future bug allows writes. Planned page‑permission splitting (DEFERRED D2) will address this, but it should be kept in mind for M1.5.
- **Suggestion**: When splitting permissions, exclude the OpenSBI region from the writable kernel mapping, or map it as read‑only/execute as needed.

#### INFO‑2: `BOOT_LOCK` placed in `.data` and cleared‑BSS loop covers stack/trap‑stack

- **File/line**: `kernel/src/main.rs` (`#[unsafe(link_section = ".data")] pub static mut BOOT_LOCK`) and `kernel/src/entry.S` (clear loop from `_bss_start` to `_trap_stack_top`).
- **Description**: The boot lock is correctly placed in `.data` to be available before BSS clearing, and the clearing loop covers all three NOLOAD sections (BSS, boot stack, trap stack). This is a well‑documented, correct design.

#### INFO‑3: Scheduler test may be timing‑sensitive

- **File/line**: `kernel/src/sched.rs`, `self_test()` (preemption test checks tick advance >= 15).
- **Description**: The preemption test uses a busy‑wait thread that does not yield and relies on the timer interrupt to preempt it. The test expects the main thread to observe completion within 200,000 yields. This could become flaky if timer frequency changes or if the test environment is loaded. It is self‑test only, but for CI robustness it might be better to make the test more deterministic (e.g., use a separate test hook to force a tick).

#### INFO‑4: Heap slab page class table uses `static mut` and raw pointer indexing

- **File/line**: `kernel/src/heap.rs`, `static mut SLAB_PAGE_CLASS` and `slab_class_of` / `slab_class_set`.
- **Description**: The table is written only during slab page creation (single‑threaded boot) and read afterwards. The raw pointer access is safe given that the table size is `mem::MAX_PAGES` and indices are validated by pointer bounds checks in `dealloc` / `alloc`. However, using `static mut` is somewhat fragile; an `UnsafeCell` or `OnceLock` would be a more idiomatic and safer choice for future multi‑core.

## What looks correct

The following design and implementation choices appear sound and should be preserved:

- **Linker script memory layout**: Explicitly sets `_kernel_start`/`_kernel_end`, reserves stack and trap stack outside the allocator region, aligns `_alloc_start` to the maximum block size for absolute alignment guarantees, discards unwanted sections, and documents the orphan‑section behavior. The careful placement of `__global_pointer$` in `.data` is acknowledged as not yet useful but reserved for future optimization.

- **Trap entry assembly**: The `trap_vector` implementation is robust: it uses `sscratch` to swap `t6`, saves all registers in a well‑defined order, implements nested‑trap detection by comparing `t6` against `_trap_stack_top - TRAP_FRAME_SIZE`, reloads `gp` to the kernel’s global pointer for handler code, and performs stack‑depth checks before calling `trap_handler`. The restore path correctly clears `SIE` before `sret` and restores `sscratch`.

- **Boot sequence**: The `_start` entry clears `sstatus.SIE`, sets up early trap stub, clears `satp` and flushes TLB, initializes `gp` with `norelax`, uses atomics for boot‑hart arbitration, and clears BSS + stacks. The ordering in `kernel_main` (IRQ off → CSR sanitize → UART init → trap vector → timer enable → logger level → memory init → MMU → heap → scheduler → sync tests → IRQ enable) is logical and commented.

- **Buddy allocator**: The init and carve logic thoroughly handles reserved regions (FDT) and padding pages. `free` validates pointer alignment, bounds, metadata used flag, and block‑alignment, preventing double free and interior‑page free. `alloc` marks only block head, which is a safe optimization given the checks. The self‑test exercises full exhaustion, merging, and alignment.

- **Heap slab allocator**: The slab design with intrusive free lists, per‑page headers, and a class table is sound. The `CRITICAL‑1` fix (pop first slot from a newly created slab) is implemented correctly. Large‑object path stores the base pointer immediately before the aligned user pointer and handles high‑alignment overallocation correctly.

- **UART driver**: The DLAB trap is handled with correct ordering and `mmio_fence`. The bounded TX wait with drop counter ensures the console never blocks indefinitely. The `\n`→`\r\n` translation is standard.

- **Panic handler**: The dual‑panic guard (`PANICKING` atomic) prevents recursion. Stack watermark scanning uses volatile byte reads and correctly distinguishes boot vs. trap stack. The CPU dump is best‑effort and clearly labeled.

- **Scheduler core**: The cooperative and preemptive switching design is conceptually correct. The `Context` (caller‑saved) for cooperative switches and the full trap‑frame model for preemption match the assembly. `frame_valid` tracking prevents resurrecting threads with stale frames. Locking discipline (manual IRQ save/restore around scheduler lock) avoids deadlocks with the timer ISR in the current single‑hart, single‑interrupt configuration.

- **Architecture abstraction**: The `arch` module cleanly isolates RISC‑V specifics, and the use of `global_asm!` with a shared `riscv64.S` is maintainable.

## Blind spots & suggestions for the next milestone (M1: trap handling)

Given the imminent M1 milestone, the following areas deserve close attention:

1. **Frame size consistency (already critical)** — Establish a single source of truth for the trap frame layout. Use compile‑time assertions between assembly `TRAP_FRAME_SIZE`, Rust `TRAP_FRAME_WORDS`, and scheduler `FRAME_WORDS`. The current mismatch is a symptom of missing cross‑layer validation.

2. **Interrupt‑safety of locks and allocators** — As more interrupt sources (UART, virtio, etc.) are enabled, the `SpinLock` used by heap, buddy allocator, and scheduler will be exposed to ISR contexts. The deferred items D3/D11 (IRQ‑safe lock, ISR allocation policy) must be resolved before M1. Consider implementing a `IrqSafeSpinLock` that saves/restores `sstatus.SIE` and migrating all shared state to it. Explicitly forbid allocation and logging in ISR paths until then.

3. **Timer mechanism flexibility** — Remove the hard dependency on Sstc. Implement runtime detection and fallback to SBI `set_timer`. This is essential for real hardware bring‑up and for the RVA23 compatibility plan (P2 includes Sstc, but many boards in the field lack it).

4. **FDT parsing robustness** — M1.5 plans to parse the FDT for RAM size, UART base/clock, and timer frequency. Ensure that any FDT pointer validation is done before use (the current bug in `mem::init` is a precursor). Use the FDT to program the UART divisor correctly for real hardware.

5. **Trap frame dump fidelity** — The current `dump_trap_frame` prints all GPRs and CSRs. For M1, consider adding more CSRs (e.g., `stval` already, `htval`, `htinst`, `sscratch`, `stvec`) to aid debugging. Also, ensure that the dump path itself cannot trigger further faults (use only memory that is guaranteed accessible).

6. **Stack guard pages** — As planned in DEFERRED D4, adding unmapped guard pages below the boot trap stacks will turn stack overflows into page faults instead of silent corruption. This should be implemented early in M1 since the MMU is now active.

7. **Per‑hart data structures** — The current single trap stack and global `sscratch` state will break with SMP. M1 may still be single‑core, but M1.5/M2 will bring up secondary harts. Design the trap stack array and per‑hart state (tp‑indexed) proactively to avoid a costly refactor.

8. **Testing under `-cpu max` and multiple QEMU CPU models** — CI should include a matrix of `-cpu rv64gc` (no Sstc, no Zicboz, etc.) and `-cpu max` (all extensions) to catch extension‑dependency issues early. The current CI only uses the default CPU, which may mask the Sstc problem.

9. **Review of `unsafe` blocks** — The code uses `unsafe` extensively in low‑level hardware interactions. While many are necessary, each should be audited with the `unsafe_op_in_unsafe_fn` lint already enabled. Pay special attention to raw pointer slicing (`from_raw_parts`) — the frame copy bug is exactly the kind of issue that slips through.

10. **Panic path resilience** — Ensure that panic handling never relies on code that could be corrupted (e.g., heap). Currently, panic logging uses UART directly and atomics, which is good. Continue to avoid heap allocations in panic/trap paths.

---

**Overall**, the kernel demonstrates strong engineering discipline and a thorough review culture. The critical frame‑size mismatch must be fixed immediately. The other findings are important for portability, robustness, and future scalability, but many are already on the project’s deferred list. I recommend addressing CRITICAL‑1, HIGH‑1, HIGH‑2, and MEDIUM‑1 before considering the M1 milestone complete.
