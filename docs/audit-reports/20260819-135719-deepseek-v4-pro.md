# Independent AI audit (deepseek-v4-pro)

- date: 20260819-135719
- model: deepseek-v4-pro
- tool: scripts/ai_audit.py (external reviewer, not the author)

## Executive summary

V3 review of the M1.5 tree. The previous V2 fixes are present and appear correctly applied (buddy free-list coverage, frame_restore C2, guard-page unmap asserts, TLB flush in unmap_4k, pick_next state check, SBI clobbers, FDT struct bounds, slab pointer validation, RAM alignment check, FDT alignment/node stack, read_string lifetime, woken clearing, timer deadline catch-up, multi-interval reserved carve).

The most consequential new findings are in the **board bring-up path that runs from untrusted bootloader data**: the FDT parser's node-name matching does not match the FDT node names that QEMU actually generates (`memory@80000000`, `uart@10000000`), so the advertised “FDT-derived RAM/UART parameters” are silently dead code on QEMU and everything passes only because the QEMU defaults happen to be correct. On real hardware this will misconfigure the buddy allocator/MMU and UART. Second, `board::init_from_fdt` accepts essentially any 4-byte-aligned non-zero UART base — including addresses inside kernel RAM — and `uart::reinit()` writes the UART init sequence to that address *before paging is even enabled*, giving a hostile or corrupt FDT an arbitrary physical-memory write primitive that corrupts the kernel image. I explain below why this is reachable even with the parser bug in place.

I found no new memory-unsafety bug in the scheduler dual-protocol that I could prove at runtime; the `ctx_valid`/`frame_valid` invariants hold on the single coherent analysis I performed, and the `woken` flag protocol is adequate for the current Mutex/Condvar single-registration model. The trap entry does, however, write through an unvalidated frame pointer before its nested-trap detection runs, which should be reordered before M2 exposes untrusted U-mode registers.

## Findings (severity-ranked)

### 1. [NEW] HIGH — FDT parser node-name matching never matches QEMU’s actual FDT, so RAM size/start and UART base extraction are dead code

`kernel/src/fdt.rs`, `Fdt::handle_prop()` (the `"reg" if node == b"memory"` and `"compatible"` branches).

QEMU’s `virt` machine produces a `/memory@80000000` node and `/soc/uart@10000000`. The parser:
- compares `node == b"memory"`, which fails for `memory@80000000`;
- compares `node == b"cpus"` (this one works — QEMU uses `/cpus`);
- only looks at nodes where `node.starts_with(b"serial@")` for the `compatible` property, but QEMU’s node is `uart@10000000`.

Consequently `params.ram_start`, `params.ram_size`, and `params.uart_base` remain 0, and `board::init_from_fdt` silently falls back to hardcoded `0x80000000` / 128 MiB / `0x10000000`. The CI boot log showing “114688 KiB managed” is precisely this default path, not FDT-derived state. `timebase-frequency` (the `/cpus` node) is the only board parameter actually parsed from FDT on QEMU.

Impact: on any real board whose RAM size/start or UART address differs from the QEMU defaults, the buddy allocator will manage the wrong physical range (phantom pages or unmanaged real RAM), the UART driver will talk to the wrong MMIO address, and the kernel will either crash or corrupt state. This also makes the M1.5 milestone claim “FDT 解析 RAM/UART 运行时参数化” inaccurate.

Fix: match on the basename after stripping the unit-address — e.g. split the node name at `@` and compare the first component to `memory`/`cpus`; for UART, match any node whose `compatible` property contains `ns16550`/`ns16550a` and read the node’s `reg` property for the base address instead of parsing the node name (with the node name as fallback). Add a boot log line explicitly stating which source (FDT vs default) was adopted for RAM/UART so CI can assert the FDT path is actually taken.

### 2. [NEW] HIGH — UART base from FDT is insufficiently validated; a hostile/corrupt FDT yields an arbitrary physical-memory write

`kernel/src/board.rs`, `init_from_fdt()` — the `uart_base` validation is only `params.uart_base != 0 && params.uart_base.is_multiple_of(4)`.

Nothing prevents `uart_base` from being a RAM address inside the kernel image or heap. The boot sequence in `kernel/src/main.rs` then calls `crate::uart::reinit()` immediately after `board::init_from_fdt()`, and `reinit()`/`init_hw()` write the DLAB/LCR/IER/FCR/MCR initialization sequence directly to `UART_REG_BASE` via `write_u8`, while the CPU is still in Bare mode — i.e. the writes go straight to physical memory. Later `mmu::init()` calls `map_4k(root, uart_base, uart_base, PTE_LEAF_RW)`, which also **overwrites whatever PTE already covered that address** (no existing-entry check).

A bootloader that supplies an FDT with a node named `serial@80200000` and `compatible = "ns16550a"` satisfies the parser’s `serial@` + hex checks (the parser converts the unit-address string), making `init_from_fdt` accept `0x80200000`. The kernel then overwrites its own entry code with UART bytes, and every subsequent `putc()` writes one attacker-partially-controlled byte to kernel text/data. The same applies to any reserved/allocator-managed RAM address.

Severity note: under the explicitly requested “hostile bootloader” threat model this is an arbitrary-write primitive and should be treated as CRITICAL; against a merely buggy bootloader it is a high-severity self-corruption footgun.

Fix: in `board::init_from_fdt`, require `uart_base` to be page-aligned, less than the Sv39 physical maximum, and outside `[ram_start, ram_end)` (or, better, outside `[kernel_start, _alloc_start)` too, or only within a known MMIO window). Also have `map_4k` refuse to replace an already-valid leaf/table entry unless the caller explicitly opts into replacement, and log a `warn!` when FDT values are rejected and defaults are used.

### 3. [NEW] MEDIUM — trap entry writes through the computed frame pointer before validating it; corrupt/foreign `sscratch` or (M2) user-controlled `t6` can fault-loop instead of reaching the safe halt path

`kernel/src/arch/riscv64.S`, `trap_vector` — the sequence:

```
csrrw t6, sscratch, t6
addi t6, t6, -TRAP_FRAME_SIZE
sd t0, 4*8(t6)          # writes through unvalidated t6
csrr t0, sscratch
sd t0, 30*8(t6)         # writes through unvalidated t6
...
la t0, _trap_stack_top
addi t0, t0, -TRAP_FRAME_SIZE
bne t6, t0, 4f          # nested detection only here
```

The nested-trap check and the `trap_handler` boundary check run *after* the first stores. If `t6`/`sscratch` is invalid (memory corruption, or once M2 introduces U-mode threads whose `t6` is attacker-controlled and a precise trap lands in the tiny window between the `csrrw` and the restore/check), these `sd` instructions can raise a synchronous access fault. The next trap entry starts the same sequence again with the same bad `sscratch` value, potentially fault-looping in the trap vector instead of reaching the intended `4f`/`2f` halt paths.

Currently S-mode-only code exercises only kernel-controlled `t6` values, so I could not demonstrate it at runtime; it is a hardening/correctness reordering for M2.

Fix: reorder the prologue so the nested/detection comparison runs immediately after computing the frame base, before any `sd`; or compute the new frame pointer from `_trap_stack_top` constant rather than `sscratch` for the first-level case.

### 4. [NEW] MEDIUM — Board fallback can manage phantom RAM on non-QEMU machines; FDT RAM values are validated for alignment but not for containing the kernel/allocator or for exceeding `MAX_PAGES`

`kernel/src/board.rs` (`init_from_fdt` defaults and the `ram_start`/`ram_size` acceptance criteria) and `kernel/src/mem.rs` (`init`).

Specific gaps:
- If the FDT is absent/malformed or the parser fails to match the memory node (see finding 1), the kernel assumes 128 MiB at `0x80000000`. On a real board with less RAM the buddy allocator manages non-existent pages; with more than 128 MiB the `assert!(count <= MAX_PAGES)` panics at boot. `board::init_from_fdt` accepts `ram_size` up to 1 GiB, so the board layer and allocator capacity disagree, leading to a late boot panic rather than a clear diagnostic.
- `ram_start` only needs to be non-zero and 2 MiB-aligned; there is no check that `[ram_start, ram_end)` contains the kernel image at `0x80200000` or `_alloc_start`. A hostile FDT can therefore produce a confusing boot trap after `mmu::enable()` or an allocator over a range that excludes the kernel.
- `ram_start + ram_size` can overflow `usize` or exceed the Sv39 512 GiB physical window. In the overflow case the Rust overflow check abort is a DoS; in the >2^39 case `vaddr & 0x1FF` indices silently alias to lower 1 GiB regions in `mmu::map_super`/`map_4k` (incorrect identity mapping, not the requested address).

Fix: validate in `board::init_from_fdt` (or immediately in `mem::init`/`mmu::init`) that `ram_start <= 0x80200000`, that `ram_end` covers `_alloc_start` and `_kernel_end`, that `ram_end <= ram_start + 128 MiB` (or otherwise ≤ `MAX_PAGES`), and that the whole range is < 2^39. Prefer a clear `panic!`/`warn!` distinguishing “FDT ignored, defaults used” from “FDT invalid for this kernel”.

### 5. [NEW] MEDIUM — `map_4k` / `map_region_4k` neither flush TLB nor check/overwrite semantics for post-boot remapping

`kernel/src/mmu.rs`, `map_4k()` and `map_region_4k()`.

`unmap_4k` correctly flushes the TLB after PTE=0, but `map_4k` writes a PTE and does not flush. During `mmu::init` this is safe (all mappings are established before `enable()`), and `self_test` passes. But these functions are declared as the M2 page-table API (“M2 用户态映射打底”). When M2 starts remapping/reusing virtual addresses after paging is enabled, a stale TLB entry can survive a `map_4k` over a previously-mapped page. There is also no check that `map_4k`/`map_super` do not overwrite an existing leaf/table entry, which is what makes finding 2’s UART mapping overwrite the kernel text mapping silently.

Fix: add `sfence.vma` (or a targeted `sfence.vma addr`) after `map_4k`/`map_super` when operating post-enable, and add an overwrite policy (deny unless a “force” flag is set) so MMIO/UART mappings cannot silently clobber kernel mappings.

### 6. [NEW] LOW — CPU capability detection is a stub while docs/DEFERRED claim ISA detection works

`kernel/src/cpu.rs`, `detect_from_fdt()` — the function always returns `None` with the comment that the FDT parser does not extract `riscv,isa`. `init_from_fdt` therefore always logs the hardcoded fallback string. This contradicts `README.md`, `docs/DEFERRED.md` (D16/D17), and the module header, which describe ISA capability detection as an implemented M1.5 artifact. It also means the RVA23 “capability detection” does not actually observe the running CPU’s ISA.

Fix: either parse `riscv,isa` from the FDT (the parser’s per-node property dispatch already has enough machinery), or update the logging/docs to state explicitly that capability detection is diagnostic-only and hardcoded until D17 is implemented.

### 7. [NEW] LOW — Scheduler self-test test 3 does not actually verify timer preemption

`kernel/src/sched.rs`, `self_test()` test 3 (`test_busy`).

The comment says the busy thread “必然经历至少一次抢占”, but with no other *frame-valid Ready* thread at slice expiry, `on_tick`’s `has_other` check returns false and the busy thread keeps running with `ticks_run` reset each slice; it exits voluntarily after 15 ticks by jumping back through `exit()`. A preemption regression would therefore pass this test. Test 4 does exercise preemption (the HIGH-vs-LOW case), so the feature is covered somewhere, but test 3’s comment and intent are inaccurate.

Fix: add a second low-priority thread that is frame-valid at slice expiry to force an actual `on_tick` switch, or re-label test 3 as “busy thread exit + cooperative resume” rather than “preemption verified”.

### 8. [NEW] LOW — Panic in a spawned thread reports misleading “sp outside all known stacks (corrupted?)” and UNKNOWN watermark

`kernel/src/panic.rs`, `current_stack_bounds()`/`dump_cpu()`.

`current_stack_bounds` knows only the boot and trap stacks from the linker script. Any panic in a scheduler-spawned thread (16 KiB heap-allocated stacks) falls into the `else None` branch and prints `WARNING: sp=... outside all known stacks (corrupted?)` and `stack watermark: UNKNOWN`, even though the sp is perfectly valid. Since thread stacks are deliberately not zeroed (`alloc_zeroed_free_stack`), watermark scanning would be meaningless there anyway.

Fix: either track per-thread stack bounds in the scheduler (and zero or record a watermark marker), or change the diagnostic wording to distinguish “known boot/trap stacks” from “thread stack (watermark unavailable)” rather than “corrupted?”.

### 9. [NEW] LOW — FDT parser robustness gaps remain

`kernel/src/fdt.rs`.

- `Fdt::new` checks `fdt + size_of::<FdtHeader>()` against `max_phys`, but does **not** check `fdt + totalsize`; `total` up to 4 GiB is accepted and the parser then performs volatile reads across that span, so a corrupt blob with a plausible magic can fault the booting CPU before any trap handler is useful (DoS). Check `fdt.checked_add(total)` against `max_phys`/a sane bound.
- In `parse()`, a tree deeper than 8 saves no parent name on the stack; upon `END_NODE` unwinding past that depth, stale `node_stack` entries are restored, which can make a property match the wrong node name in a malicious deep FDT. Clamp/saturate depth and stop matching, rather than misattributing names.
- In `mem::init`, the reserved-region conversion (`r_addr.saturating_add(r_size).div_ceil(PAGE_SIZE) * PAGE_SIZE`) can panic via overflow checks in release for near-`usize::MAX` values from a hostile reserve map. Validate the range before the arithmetic.

None of these are exploitable for more than boot DoS today, but they are exactly the FDT robustness surface the earlier audits targeted.

### 10. [NEW] LOW — Misleading function name/comment: `alloc_zeroed_free_stack` does not zero the stack

`kernel/src/sched.rs` — `alloc_zeroed_free_stack()`.

The name says “zeroed”, the comment says zeroing is intentionally skipped for performance, and the function returns an uninitialized `KernelStack`. This has already caused confusion once in this codebase; rename to `alloc_free_stack` and keep the performance note.

### 11. [NEW] INFO — CI and tooling gaps

- CI runs only the single-hart boot smoke; `make test-smp` is not part of CI, so the boot-arbitration regression test is only manual.
- CI’s `rva23` job only does a release boot smoke; it does not run `cargo fmt --check` / clippy on the RVA23 build.
- `make test`-style greps cannot detect whether FDT-derived board params were actually used (finding 1) because fallback values produce identical logs; add an explicit “board params source” log line and assert it.

### 12. [NEW] INFO — Future multi-hart hazards currently latent

- `TIMER_DEADLINE` (`kernel/src/arch/riscv64.rs`) is a single global `AtomicUsize`, but `stimecmp` is per-hart. When M2 wakes secondary harts, this global deadline model must become per-hart, or harts will reprogram each other’s timers.
- `sscratch` currently stores the global trap-stack top by convention. M2’s per-hart stacks must switch `init_traps`/`trap_vector` to a per-hart value; also, the trap entry never saves the interrupted context’s original `sscratch`, so user code that uses `sscratch` (a common RISC-V TLS/percpu convention) would lose its value on every trap.
- `sched::woken` is a single per-thread bool. This is correct for the current one-wait-registration model, but as soon as a thread can wait on multiple objects simultaneously (IPC receive + mutex), a sticky bool without a generation/queue identity will begin collapsing or misattributing wakeups.
- Exited threads are never removed from `Scheduler::threads`, and `MAX_THREADS = 64` is a hard ceiling for the whole runtime; with spawn/exit churn this becomes a leak until M2 adds thread-slot reclamation.

## What looks correct

The previously fixed items are genuinely fixed in the code I reviewed. In particular:

- **Buddy allocate/free/merge**: `mem.rs` free-list handling, header-only marking, interior-page rejection, real-vs-padded page accounting, reserved-region carve-down, and the self-test’s full exhaustion/merge cycle all look sound.
- **Scheduler dual protocol**: the `ctx_valid`/`frame_valid` transitions (spawn → both true; yield/block → ctx true, frame false; preempt → frame true, ctx false) are coherent, including the `on_tick` undo path and `frame_restore`’s save of `old_ctx` before `sret`. The no-other-candidate fallback to idle is, as analyzed, unreachable with a stale frame in the current single-core model.
- **`woken` + lost-wake protection**: Mutex/Condvar registration and preemption-window wake handling (register → drop mutex → atomic irq-off section → block) is correct for the current single-registration model.
- **SpinLock IRQ-safe nesting**: lock ordering (SCHED → HEAP → ALLOCATOR; waiters → SCHED) is acyclic, and nested `irq_save`/`irq_restore` pairing is preserved.
- **`mmu::init` layout**: the 4K-mapped kernel superpage remainder covering the boot/trap stacks and the guard-page unmapping are correctly ordered, and `trap_handler`’s frame-bound validation is subtraction-safe.
- **Boot arbitration and BSS/stack zeroing** in `entry.S`, including `fence.i` and the `.data` placement of `BOOT_LOCK`, are correct.
- **Panic handling**: double-panic flag, interrupt-off halt, and uart-dropped counter are sensible.

No new CRITICAL-rated defect that is reachable in the current QEMU/S-mode single-core configuration was confirmed; findings 1 and 2 are the candidates that become critical in the real-hardware/hostile-bootloader context.

## Blind spots & suggestions for M2

1. **Board-data trust boundary**: treat FDT-derived addresses (`ram_*`, `uart_base`, future PLIC/CLINT addresses) as untrusted input; validate every base against RAM and a reasonable physical MMIO window before the first write. Never write to an address before validation, and never let `map_*` overwrite an existing PTE silently.
2. **Trap entry hardening**: reorder validation before frame stores (finding 3); preserve/restore `sscratch` for user semantics; add per-hart trap stacks and per-hart `stimecmp`/deadline state before waking secondary harts.
3. **Page table API semantics**: define TLB-flush and overwrite semantics for `map_4k`/`unmap_4k`/`map_region` now, including `sfence.vma` discipline and a “replace vs deny” policy.
4. **Scheduler growth**: thread-slot reclamation, per-thread wake generation counters, and multi-wait-object support for synchronous IPC before building the IPC layer on the current sticky `woken` flag.
5. **Diagnostics**: teach panic to recognize thread stacks, and make the boot log state explicitly whether board parameters came from FDT or defaults so CI can prevent silent regressions like finding 1.
6. **Zero-on-handoff (D10)**: ensure every page given to user space is zeroed, and consider adding a buddy-allocation flag for “zeroed” so the slab/page allocator can enforce it cheaply at the boundary.
7. **Test integrity**: make the preemption self-test actually force a preemption, and add the SMP boot test to CI.
