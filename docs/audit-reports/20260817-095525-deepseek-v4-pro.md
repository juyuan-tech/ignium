# Independent AI audit (deepseek-v4-pro)

- date: 20260817-095525
- model: deepseek-v4-pro
- tool: scripts/ai_audit.py (external reviewer, not the author)

## Executive summary

Overall the code is substantially more defensive than a typical M0 kernel: it has a dedicated trap stack, frame-pointer validation before dereference, CSR sanitization, bounded UART output, allocator self-tests, identity-mapped Sv39 setup, and negative CI assertions. In the exact tested configuration (`qemu-system-riscv64 -M virt -m 128M` with OpenSBI and a single core), I did not find an immediately executable CRITICAL memory-safety bug.

However, there are several latent correctness and future-safety issues. The most concrete is a wrong `satp` PPN mask width in `mmu.rs` (36 bits instead of 44), which is harmless below 64 GiB but is a genuine register-layout bug. A second important issue is that `ensure_table()` treats any valid PTE as a pointer to a next-level table; if it ever runs on a leaf superpage PTE, it will interpret mapped data as a page table and corrupt kernel memory. That is especially relevant because the roadmap explicitly plans finer-grained kernel permissions later.

Other findings concern interrupt-context logging, hardcoded platform geometry, the early trap window, GP-relative addressing, and some Rust/linker-symbol validity concerns.

## Findings (severity-ranked)

### HIGH

#### H1. `SATP_PPN_MASK` is only 36 bits wide, not the Sv39 44-bit PPN mask
- **Severity:** HIGH
- **File:** `kernel/src/mmu.rs` (const `SATP_PPN_MASK`, around the Sv39 constants)
- **Description:**
  ```rust
  const SATP_PPN_MASK: usize = 0xF_FFFF_FFFF;
  ```
  The comment says “PPN 字段掩码(位 0-43)”, but `0xF_FFFF_FFFF` has only 9 hex digits = 36 bits. Sv39 `satp.PPN` is 44 bits wide.
  `mmu::self_test()` derives the root-table address with:
  ```rust
  let root = (s & SATP_PPN_MASK) << 12;
  ```
  On any machine with RAM at or above `64 GiB` (`1 << 36`), this drops physical-address bits 36..43 of the root page table, producing an invalid root pointer. In the current QEMU `-m 128M` setup the high bits are zero, so this does not currently fail, but it is a definite hardware-register bug and will fail on real hardware.
- **Fix:**
  ```rust
  const SATP_PPN_MASK: usize = (1usize << 44) - 1;
  ```
  Or use the same expression style as `PTE_PPN_MASK`.

#### H2. `ensure_table()` does not distinguish leaf PTE from next-level table PTE
- **Severity:** HIGH
- **File:** `kernel/src/mmu.rs` (`ensure_table()`, `map_4k()`, `map_super()`)
- **Description:**
  ```rust
  unsafe fn ensure_table(parent: *const u64, idx: usize) -> Result<*const u64, ()> {
      let entry = pte_read(parent, idx);
      if entry & PTE_V != 0 {
          let sub = (((entry >> PTE_PPN_SHIFT) & PTE_PPN_MASK) << 12) as usize;
          Ok(sub as *const u64)
      } else { ... }
  }
  ```
  A Valid PTE is not necessarily a pointer to a page table; it can also be a leaf 4 KiB page PTE or a leaf 2 MiB superpage PTE. If `ensure_table()` is ever called on an index already occupied by a leaf mapping, the leaf’s PPN is reused as the address of a child table, and `map_4k()` will write page-table entries into ordinary mapped data/code memory.
  The current call sites are disjoint by construction: RAM is mapped as 2 MiB superpages, and UART is mapped at a separate L1 index. But the comment relies on caller discipline:
  ```rust
  // 调用方负责不在其上继续下沉 —— map_4k/map_super 的索引互斥保证
  ```
  That assumption is fragile and will likely be violated during the planned M1.5 “kernel image code RX / data RW” permission split or any future dynamic `arch_mmu_map()` use.
- **Fix:**
  Make `ensure_table()` inspect `PTE_R|PTE_W|PTE_X`. If any are set, this is a leaf; either return an error or explicitly split a 2 MiB superpage into 512 child PTEs before descending. Do not silently interpret a leaf as a table.

### MEDIUM

#### M1. Logger is not safe against ISR/interrupt-context interleaving
- **Severity:** MEDIUM
- **File:** `kernel/src/logger.rs` (module header; `log()` implementation)
- **Description:**
  The logger is explicitly lock-free:
  ```rust
  // 当前无锁。M1 使能中断前必须引入 ISR 安全输出
  ```
  The current timer ISR only calls `tick_up()` and does not log, so normal timer operation is safe. However, `trap_handler()` already logs on unhandled exceptions/interrupts:
  ```rust
  error!("TRAP: unhandled interrupt ...");
  dump_trap_frame(frame);
  ```
  These paths can run after a trap preempts a main-context `info!`/`error!` that is partway through a multi-`putc` formatted write. The result is interleaved UART output and corrupted diagnostics exactly when the system is failing.
- **Fix:**
  Before enabling general device interrupts, introduce either an ISR-safe lock around `Writer::write_str`, or a per-context ring buffer with a single dedicated output context. Make sure the panic path either bypasses the lock or uses a documented emergency output channel.

#### M2. Hardcoded `RAM_END`/`UART_BASE`/timer frequency depends on exact QEMU configuration
- **Severity:** MEDIUM
- **File:** `kernel/src/mem.rs` (`RAM_START`, `RAM_END`, `MAX_PAGES`), `kernel/src/uart.rs` (`UART_BASE`, divisors), `kernel/src/arch/riscv64.rs` (`TIMER_INTERVAL`)
- **Description:**
  ```rust
  pub const RAM_END: usize = RAM_START + 128 * 1024 * 1024;
  ```
  ```rust
  const UART_BASE: usize = 0x1000_0000;
  ```
  ```rust
  pub const TIMER_INTERVAL: usize = 100_000;
  ```
  The allocator, MMU identity mapping, UART driver, and timer interval all assume QEMU virt with exactly 128 MiB RAM, UART at `0x1000_0000`, and a 10 MHz clock. If QEMU is started with `-m 64M` or different memory size, `mem::init()`/`mmu::init()` will manage and identity-map non-existent RAM; the UART may be absent or at another address; the timer interval is wrong. This is a likely failure on real hardware and even on alternate QEMU invocations.
- **Fix:**
  Parse the FDT early, record actual RAM size/start, UART base and clock frequency. The current code already receives `fdt: *const u8`; promote parsing from M1.5 to a mandatory early step. If FDT parsing is not available, assert at boot that the hardcoded values match and fail with a clear diagnostic.

#### M3. Early boot trap window: `stvec` is zero until after UART initialization
- **Severity:** MEDIUM
- **File:** `kernel/src/main.rs` (`kernel_main()` init order), `kernel/src/entry.S` (`csrw stvec, zero`)
- **Description:**
  The entry point deliberately zeroes `stvec`, and `init_traps()` is only installed after `uart::init()`:
  ```rust
  uart::init();
  arch::init_traps();
  ```
  If `uart::init()` faults or a synchronous exception is taken before `init_traps()`, the hart jumps to address 0 with no useful diagnostic. This is especially relevant on real hardware where the UART MMIO is absent/misconfigured. The comment in `kernel_main()` itself acknowledges:
  ```rust
  // stvec 装好之前发生异常会跳到地址 0
  ```
  The current QEMU setup masks this because the UART is always present and reachable.
- **Fix:**
  Install a minimal early trap vector before touching UART MMIO. The early handler should be able to park/halt with minimal state, perhaps writing a fixed marker or spinning with a distinctive CSR state, but it must never leave `stvec == 0` while executing potentially faulting MMIO writes.

### LOW

#### L1. `__global_pointer$` placement cannot cover `.sbss` with ±2 KiB GP-relative addressing
- **Severity:** LOW
- **File:** `kernel/linker.ld` (`.data` section, `__global_pointer$`)
- **Description:**
  The linker script places `__global_pointer$` at the end of `.data`:
  ```ld
  .data : {
      *(.data*)
      *(.sdata*)
      . = ALIGN(16);
      __global_pointer$ = .;
  }
  ```
  `.bss` then starts at a 4 KiB-aligned boundary. `.sbss` is placed inside `.bss`:
  ```ld
  .bss : {
      *(.bss*)
      *(.sbss*)
      *(COMMON)
  }
  ```
  GP-relative addressing has a signed ±2 KiB offset range. Because `.bss` is at least 4 KiB away from the GP anchor, `.sbss` cannot actually be addressed GP-relatively. The comment on the linker script claims `.sbss` is in range, but that is not true with this layout. Today this is harmless because current code does not populate `.sbss`, but future small data growth may cause either link-time relocation failures or missed GP optimization.
- **Fix:**
  Place `__global_pointer$` more centrally, e.g., at the start of `.sdata`, or move `.sbss` immediately after `.sdata` and keep the whole small-data window within 2 KiB. Alternatively document and enforce that all `sbss`/small-data must be within 2 KiB of the anchor and validate with a link assertion.

#### L2. Linker script symbols are accessed through Rust references, which is questionable under strict Rust validity
- **Severity:** LOW
- **File:** `kernel/src/panic.rs` (`_stack_bottom`, `_stack_top`, `_trap_stack_bottom`, `_trap_stack_top`), `kernel/src/mem.rs` (`_alloc_start`), `kernel/src/arch/riscv64.rs` (`_trap_stack_bottom`, `_trap_stack_top`)
- **Description:**
  The code uses patterns like:
  ```rust
  let boot_bottom = unsafe { &_stack_bottom as *const u8 as usize };
  ```
  and
  ```rust
  let raw = unsafe { &_alloc_start as *const u8 as usize };
  ```
  These create an actual Rust reference to an extern linker symbol. Linker symbols here are addresses, not guaranteed Rust `u8` objects; taking a reference to a non-object can be UB in the Rust abstract-machine sense, even if it is never dereferenced.
  The panic code comments mention provenance but not object validity. In practice this pattern is common and works on current toolchains, but it is not robust under strict aliasing/validity tools.
- **Fix:**
  Use `core::ptr::addr_of!(_stack_bottom)` / `addr_of!(_alloc_start)` or pass the symbols directly as `sym` operands to `asm!`. Avoid constructing `&_symbol` references merely to convert to an integer.

#### L3. `trap_vector` prologue has an unprotected window before `sscratch` is repointed to the frame base
- **Severity:** LOW
- **File:** `kernel/src/arch/riscv64.S` (`trap_vector` prologue)
- **Description:**
  The sequence is:
  ```asm
  csrrw t6, sscratch, t6
  addi t6, t6, -TRAP_FRAME_SIZE
  sd   t0, 4*8(t6)
  csrr t0, sscratch
  sd   t0, 30*8(t6)
  # nested detection
  ...
  csrw sscratch, t6
  ```
  Between the initial `csrrw` and the later `csrw sscratch, t6`, `sscratch` still contains the interrupted `t6` rather than the current frame base. If a synchronous trap were taken during that small window, the second trap’s entry would consume that stale `sscratch` as its stack/frame base and perform stores before the nested-detection check runs. The current kernel never corrupts `sscratch`, so this is not exploitable as written, but it is fragile for future per-hart trap-stack switching or user-mode entry.
- **Fix:**
  Rearrange the prologue so `sscratch` is immediately set to the new frame base before any store that dereferences the frame pointer, while preserving the interrupted `t6` via a register already saved to the frame (e.g., save `t1` as well, use it as a temporary, then write the old `t6`). Also consider checking the computed frame base range before the first store.

#### L4. Timer deadline catch-up after a long interrupt-disabled initialization can produce a self-sustaining interrupt storm
- **Severity:** LOW
- **File:** `kernel/src/arch/riscv64.rs` (`trap_handler()` timer path)
- **Description:**
  ```rust
  let next = TIMER_DEADLINE.fetch_add(TIMER_INTERVAL, Ordering::Relaxed) + TIMER_INTERVAL;
  crate::sbi::set_timer(next);
  ```
  The deadline is programmed from the previous deadline, not from the current time. If interrupts are disabled for longer than the interval (slow boot, debugger, future long critical sections), the next deadline can still be in the past when `sret` re-enables interrupts. The timer interrupt then fires again immediately, and the handler keeps incrementing by one interval until the deadline catches up. This preserves long-term tick accuracy but can starve the main loop for a long burst after boot.
- **Fix:**
  In the timer ISR, if `next <= get_time()`, resynchronize to `get_time() + TIMER_INTERVAL` and optionally increment `TICK` by the number of missed intervals. That avoids bursts while maintaining monotonic scheduling.

### INFO

#### I1. Orphan-section strategy is not actually enforced
- **File:** `.cargo/config.toml`, `kernel/linker.ld`
- **Description:**
  The config comment says `--orphan-handling=warn/error` is not used because of lld synthetic sections, and that new sections rely on manual review. The linker script does not explicitly collect every possible toolchain-generated section, e.g. `.eh_frame_hdr`, `.gcc_except_table`, or various synthetic/attribute sections. This is an accepted tradeoff for M0, but it means orphan sections can silently enter future binaries and cause debug/release or toolchain-dependent behavior.
- **Fix:**
  Later, add a CI linker map check or a script that lists allocated orphan sections without enabling the noisy lld warning globally.

#### I2. Padding pages are counted in the reported managed page count
- **File:** `kernel/src/mem.rs` (`page_count()`, `BuddyAllocator::init()`)
- **Description:**
  `page_count()` returns `self.page_count`, which is `padded`, including pages permanently marked occupied because the region was rounded up to a 16 MiB multiple. With the current 128 MiB layout there is no padding, so the log is correct, but with different `_alloc_start` or RAM sizes the `KiB managed` log would overstate actual allocatable memory.
- **Fix:**
  Return `real_count` for “managed pages”, or explicitly report both real and padded counts.

## What looks correct

- **Entry-state sanitization** (`entry.S`, `sanitize_csr()`): Clearing `sstatus.SIE`, `stvec`, `sscratch`, `satp`, `sie`, `sip`, `SUM`, `MXR`, and `FS` before boot is appropriate for a hostile/unknown bootloader.
- **Secondary-hart discipline** (`entry.S`): Non-zero hart IDs branch to `park` before touching BSS/stack/trap stack, avoiding early concurrent memory writes.
- **Trap frame validation and dedicated trap stack** (`riscv64.S`, `trap_handler()`): Saving all 31 GPRs plus key CSRs on a separate trap stack, validating the frame pointer before creating a Rust slice, and halting on invalid frames are all strong defenses.
- **Deadline-based timer scheduling** (`TIMER_DEADLINE`): The use of `fetch_add` avoids cumulative drift that would result from `get_time() + INTERVAL` inside the ISR.
- **UART bounded waiting** (`uart.rs`): The TX timeout prevents a stuck physical UART from permanently hanging all diagnostics.
- **Buddy-allocator validation** (`mem.rs`): `free()` rejects non-head, non-allocated, unaligned, and out-of-region addresses; the same tests are exercised by `self_test()`.
- **Allocator self-test before interrupts** (`main.rs`): The allocator is not SMP/ISR-safe yet, and the code correctly delays `irq_enable` until after allocator and MMU setup.
- **Identity mapping before enabling SATP** (`mmu.rs`): The map-first, enable-second order and `sfence.vma` immediately after satp write are correct.
- **Panic double-panic flag** (`panic.rs`): Preventing recursive panic output is appropriate.
- **CI negative assertion** (`ci.yml`, `Makefile`): Checking for “KERNEL PANIC”/“TRAP:” and requiring at least two uptime ticks catches several classes of boot/liveness failures.

## Blind spots & suggestions for the next milestone (M1: trap handling)

1. **Per-hart trap stacks**
   - The linker script and `init_traps()` currently use one static trap stack. As soon as secondary harts are woken, `sscratch` must be initialized per hart, and the trap stack must be indexed by `tp`/hartid. The current nested-detection comparison to `_trap_stack_top` assumes a single stack.

2. **Nested trap policy**
   - The current H2 path halts on any nested trap. For M1 device interrupts, determine whether nested interrupts are allowed. If not, document and enforce the non-nesting invariant. If yes, the trap-stack depth and handler stack headroom need formal analysis.

3. **Guard pages**
   - There are currently no unmapped guard pages below the boot stack or trap stack. `panic.rs` provides a post-mortem watermark, but that only detects after an overflow has already corrupted adjacent memory. With MMU now available, add unmapped pages below both stacks.

4. **Logger locking / ISR output**
   - Before enabling any interrupt handler that logs, implement an ISR-safe output path. Also decide how panic output interacts with a potentially locked UART.

5. **Page-table leaf handling**
   - `ensure_table()` must distinguish leaf PTEs from internal table PTEs, especially before M1.5 permission splitting. Add tests for mapping a sub-page or splitting a superpage.

6. **FDT parsing**
   - Move away from hardcoded RAM/UART/timer values as early as possible. Validate the FDT header, magic, size, and memory nodes before trusting them, since the pointer is bootloader-provided.

7. **Allocator concurrency**
   - `with_allocator()` does not provide actual mutual exclusion. Once timer/device ISRs or additional cores exist, introduce a spinlock or per-hart allocation contexts, and ensure no allocation can happen inside the timer ISR unless that policy is explicit.

8. **MMU/TLB maintenance**
   - Add `sfence.vma`/`fence.i` correctness rules for any future dynamic mapping changes after SATP is enabled. The current code only maps before enabling paging, so it has not exercised post-enable TLB maintenance.

9. **`satp` PPN mask bug**
   - Fix before any real hardware or larger QEMU memory testing.

10. **Split “M0” vs “M1” documentation**
    - README/ROADMAP describe M0-only startup, but the code already contains M1 trap/timer/buddy/Sv39 functionality. Synchronize documentation with the actual milestone to prevent future review and test assumptions from drifting.
