# Independent AI audit (deepseek-v4-pro)

- date: 20260816-185945
- model: deepseek-v4-pro
- tool: scripts/ai_audit.py (external reviewer, not the author)

## Executive summary

The boot chain, trap frame save/restore, logger/panic separation, and basic UART bring-up are generally careful and show real attention to RISC-V hazards. The most serious issue is in the physical allocator: **the FDT reservation is not reflected in the buddy free lists**, so the allocator can still hand out blocks that contain the reserved FDT pages. This is silent and passes the current selftest/CI only because QEMU’s FDT placement and selftest access pattern do not touch the reserved bytes. It becomes corrupting as soon as heap/page-table allocations start.

There are also real-hardware portability issues around hard-coded platform constants and incomplete MMIO ordering, plus some lower-severity trap/crash instrumentation weaknesses.

## Findings (severity-ranked)

### 1. CRITICAL — `reserve_region()` does not remove reserved pages from buddy free lists

- **File:** `kernel/src/mem.rs` — `BuddyAllocator::init`, `BuddyAllocator::reserve_region`, `BuddyAllocator::alloc`, `BuddyAllocator::free`
- **Description:**  
  `init()` pushes complete order-12 blocks onto `free_lists`. Later, `reserve_region()` only marks `PageMeta` entries with `order = 0xFF`, `used = true`. It never unlinks, splits, or otherwise removes the containing blocks from `free_lists`.  
  `alloc()` splits free blocks with `push(idx + (1 << cur), cur)` and never checks whether the buddy pages were reserved. `free()` can also merge a freed block with a buddy whose interior pages are reserved, then re-add the merged block as free.  
  Therefore, after `mem::reserve_region(fdt as usize, 1MB)`, the allocator can still return a block covering the FDT. Split operations can write free-list next pointers directly into the first word of reserved pages.  
  In the current QEMU layout (`fdt == 0x87e00000`), the selftest happens to avoid writing the exact FDT bytes, so CI stays green. A different FDT address/alignment, any future heap/page-table allocation, or even future allocator bookkeeping can overwrite the FDT.

- **Concrete fix:**  
  Reservations must be integrated into the free-list structure, not just metadata. Examples:
  1. Pass reserved ranges into allocator initialization before pushing free blocks; or
  2. Implement `reserve_region` by locating the containing free block, splitting it down to the reserved range, and permanently removing those pieces from the free lists.
  
  Add a selftest that reserves a sub-page range, performs many allocations, and asserts that no returned block intersects the reserved range and that the reserved byte pattern is never written.

### 2. HIGH — Reservation bounds round the wrong way and `addr + size` can overflow/panic

- **File:** `kernel/src/mem.rs` — `BuddyAllocator::reserve_region`
- **Description:**
  ```rust
  let start = addr.div_ceil(PAGE_SIZE) * PAGE_SIZE;
  let end = (addr + size) / PAGE_SIZE * PAGE_SIZE;
  ```
  This rounds the start **up** and the end **down**. If the FDT is not 4 KiB aligned — allowed by the FDT spec, which requires only 8-byte alignment — the first and last partial pages containing FDT bytes are left unreserved. Current QEMU places the FDT page-aligned, hiding the bug.  
  Additionally, `addr + size` is unchecked addition. Because the workspace sets `overflow-checks = true` in both dev and release, a hostile or buggy bootloader that passes `fdt` near `usize::MAX` will cause a kernel panic rather than a clean reservation error.

- **Concrete fix:**
  - Round start down and end up, e.g.:
    ```rust
    let start = addr & !(PAGE_SIZE - 1);
    let end = (addr.checked_add(size)?).checked_add(PAGE_SIZE - 1)? & !(PAGE_SIZE - 1);
    ```
  - Return `Err(())` on overflow or invalid range instead of panicking.
  - Validate `end > start` and `end <= self.base + self.real_count * PAGE_SIZE`.

### 3. MEDIUM — UART putc path is missing an MMIO order barrier before THR write

- **File:** `kernel/src/uart.rs` — `putc()`, and also the tail of `init()`
- **Description:**  
  The driver correctly notes that Rust `volatile` accesses do not produce RISC-V hardware ordering and uses `fence iorw, iorw` after key writes. However, in `putc()`:
  ```rust
  while !is_transmit_empty() { ... }   // LSR read
  unsafe {
      write_u8(UART_BASE, c);          // THR write
      mmio_fence();
  }
  ```
  There is no fence between the LSR read and the THR store. On an out-of-order real RISC-V core, the THR store may become visible before the LSR load, potentially writing while the transmitter is not empty.  
  Also, `uart::init()` has no final fence after the last IER/FCR/MCR writes before the first later LSR poll, so those initialization writes are not explicitly ordered against the first UART status read.

- **Concrete fix:**
  - Insert `mmio_fence()` after the transmitter-empty loop and before the THR write.
  - Insert `mmio_fence()` at the end of `uart::init()` after MCR write.
  - Consider adding a small comment that `fence r,w`/`fence iorw, iorw` is intentionally placed between the LSR read and THR store.

### 4. MEDIUM — Allocator trusts free-list indices without release-mode bounds validation

- **File:** `kernel/src/mem.rs` — `pop()`, `unlink()`, `free()`
- **Description:**  
  `pop()` reads `(self.block_addr(head) as *const usize).read()` without checking that `head < self.page_count` or that the block lies inside the real managed region. `unlink()` similarly traverses and dereferences free-list links without validating `cur`.  
  `free()` checks that `addr` is inside the real region and that metadata says `used`, but it does not verify that `idx + (1 << order) <= self.real_count`. Many important checks are in `debug_assert!`, which is compiled out in release; CI boots release only. Corrupted RAM or allocator metadata could therefore cause out-of-bounds reads and later return invalid physical addresses.

- **Concrete fix:**  
  Add explicit release-mode validation:
  - In `pop()`/`unlink()`: reject or fault if `head`/`cur` is not a valid block for that order.
  - In `free()`: reject blocks that would extend past `real_count`.
  - Keep `debug_assert!` for internal invariants, but make externally visible effects fail safely.

### 5. MEDIUM — Hard-coded platform constants will break on real hardware

- **Files:**  
  - `kernel/src/mem.rs` — `RAM_END = RAM_START + 128 * 1024 * 1024`
  - `kernel/src/uart.rs` — `UART_BASE = 0x1000_0000`, divisor table/clock assumptions
  - `kernel/src/arch/riscv64.rs` — `TIMER_INTERVAL = 100_000` assuming 10 MHz `time` frequency

- **Description:**  
  These values are correct for the `qemu-system-riscv64 -M virt -m 128M` configuration, but not for arbitrary RISC-V boards/bootloaders. A real platform may have a different UART address/reference clock, different RAM size, reserved memory regions, or timer frequency. The current allocator could hand out memory that OpenSBI or firmware has reserved.

- **Concrete fix:**  
  Move platform parameters behind board configuration or parse the FDT early for RAM size, UART base/clock, and reserved-memory nodes. Until then, document these as QEMU-virt-only constants near the top of the relevant modules.

### 6. LOW — Trap vector uses an unrelaxed `_trap_stack_top` load before gp is saved/reloaded

- **File:** `kernel/src/arch/riscv64.S` — `trap_vector`
- **Description:**  
  The nested-trap detection executes:
  ```asm
  la t0, _trap_stack_top
  addi t0, t0, -TRAP_FRAME_SIZE
  bne t6, t0, 4f
  ```
  **before** saving the interrupted `gp` and before `la gp, __global_pointer$`. This `la` is outside the surrounding `.option norelax` block. If the linker ever relaxes it to gp-relative, it will use the interrupted context’s gp, not the kernel gp. In the current layout, `_trap_stack_top` is far outside `__global_pointer$ ± 2 KiB` due to the 64 KiB `PAGE_META` and stacks, so the issue is latent. Future user mode (with user-controlled gp) or linker-layout changes could make it real.

- **Concrete fix:**  
  Wrap this `la` in `.option norelax` / `.option relax`, or move the `gp` save and kernel-gp reload ahead of the nested-trap detection. Audit all `la`s before the kernel gp is established.

### 7. LOW — Trap restore resets `sscratch` before fully restoring the frame

- **File:** `kernel/src/arch/riscv64.S` — restore path after `call trap_handler`
- **Description:**  
  The restore path does:
  ```asm
  addi t0, t6, TRAP_FRAME_SIZE
  csrw sscratch, t0
  ```
  then restores CSRs/GPRs and finally `sret`. If a synchronous exception occurs during this window, `sscratch` is already the trap-stack top, so the trap vector will classify it as a first-level trap and write the new frame over the partially restored frame. This is not normally triggerable now, but it weakens double-fault behavior and can destroy diagnostics after a corrupted frame or stack memory.

- **Concrete fix:**  
  Keep `sscratch` pointing at the active frame until all frame reads are complete, or introduce an explicit “restore in progress” sentinel/flag that the trap vector recognizes. Revalidate the returned frame pointer before relying on it.

---

### 8. LOW — Trap-stack overflow can be misclassified as valid boot-stack usage

- **File:** `kernel/src/panic.rs` — `current_stack_bounds()`
- **Description:**  
  Linker layout places the trap stack immediately above the boot stack (`_trap_stack_bottom == _stack_top`). If a trap handler overflows downward past `_trap_stack_bottom` but is still inside the boot-stack address range, `current_stack_bounds` classifies `sp` as boot stack and does not emit the trap-stack overflow warning. The watermark scan also scans the wrong stack. This is a diagnostic weakness, not direct memory unsafety.

- **Concrete fix:**  
  Add a guard gap/page between boot and trap stacks, or track the active stack explicitly at trap entry/exit. With MMU in M1, an unmapped guard page is the robust solution.

### 9. INFO — Miscellaneous hardening / reproducibility notes

- **File:** `.cargo/config.toml`  
  `-Tkernel/linker.ld` is relative to the cargo invocation directory. Running cargo from `kernel/` instead of the workspace root fails. Consider using an absolute/workspace-root-derived path or a checked build script.

- **File:** `kernel/src/main.rs`  
  `info!("... fdt={:#x}", fdt as usize)` prints a physical address at the default Info log level. On a real device with accessible serial logs, this leaks physical memory layout.

- **File:** `kernel/src/mem.rs` — `alloc_pages()`  
  Allocated pages are not zeroed. Free pages currently store allocator-list pointers in their first word. M2 userspace page handoff must zero pages before mapping, or the kernel will disclose its physical allocator layout.

- **File:** `kernel/src/main.rs` / `entry.S`  
  `stvec` is zero until `init_traps()`. Any synchronous exception before that point (for example, a UART MMIO fault on real hardware) jumps to address 0 with no diagnostic. A tiny early fatal trap stub would materially help board bring-up.

## What looks correct

- **Boot entry ordering:** `_start` clears SIE, zeroes `stvec`/`sscratch`, clears `satp`, issues `sfence.vma`, initializes gp with `norelax`, and parks secondary harts before any shared memory touches. BSS, boot stack, and trap stack are zeroed before C/Rust execution.

- **Trap frame design:** The assembly saves all 31 GPRs plus `sstatus`, `sepc`, `scause`, `stval`; the Rust `gpr` indices match the assembly save order; the compile-time assert ties `TRAP_FRAME_WORDS` to the assembly size.

- **Trap handler validation:** `trap_handler` validates the frame pointer against trap-stack bounds using subtraction to avoid overflow wraparound, and checks alignment before constructing a slice.

- **Interrupt restore:** The restore path clears `SIE` in `sstatus` before `sret`, allowing `SPIE` to atomically re-enable interrupts after the frame is fully restored.

- **Panic discipline:** `PANICKING` prevents recursive panic output loops; IRQs are disabled before logging; CPU dump and stack watermarks are best-effort and labeled.

- **Logger filtering:** Level checks happen before formatting, and the macro path is simple and allocation-free.

- **UART DLAB handling:** The DLAB set/fence/divisor/fence/clear sequence is correct for NS16550-style controllers.

- **CI smoke test:** Running QEMU to completion before grepping avoids the SIGPIPE/early-kill failure mode; requiring at least two uptime lines catches “first tick then timer death”.

- **Basic buddy allocator:** allocation, split/merge, double-free rejection, and interior-page rejection are structured coherently and the selftest covers the main invariants except the reservation issue above.

## Blind spots & suggestions for the next milestone (M1: trap handling)

1. **Fix allocator reservation before M1 MMU/page-table work.** This is the most urgent item. Once page tables and kernel heap start consuming pages, the current FDT reservation bug becomes active.

2. **Parse the FDT before enabling the allocator.** M1 needs RAM size, UART base/clock, timer frequency, and reserved-memory nodes. Doing this early removes most hard-coded platform constants.

3. **Make the trap path SMP/user-mode ready before it is needed:**
   - Per-hart trap stacks indexed by `tp/hartid`.
   - Per-hart timer deadline state.
   - Revalidate restored frame pointers or keep `sscratch` until the frame is fully restored.
   - Add a `restore-in-progress` state or otherwise harden the double-fault window.

4. **Add guard pages for both boot and trap stacks** once MMU is present. This will prevent overflow from silently corrupting the adjacent stack and will make `panic` watermark/detection trustworthy.

5. **Introduce ISR-safe logging and UART ownership policy.** The current timer ISR intentionally does not log, but M1 fault handlers and device interrupts will. A fallback emergency UART path for panic is needed to avoid deadlocking on a UART lock held by a preempted context.

6. **Add explicit trap-path tests:** nested trap (synchronous exception inside `trap_handler`), invalid/truncated trap frame, trap-stack exhaustion, spurious interrupt with unknown cause, timer deadline wrap, and a trap taken during the restore path.

7. **Harden allocator state against corrupted RAM** with checked list traversal and block-index bounds, at least failing safely instead of dereferencing arbitrary physical addresses.

8. **Review all uses of `&linker_symbol` for linker-defined symbols.** Prefer `core::ptr::addr_of!`/`sym` operands where possible, and avoid `norelax`-sensitive `la`s before kernel gp is established.

9. **Decide release-run debug checks.** CI currently boots release only, so `debug_assert!`/dev-only checks are not exercised. Add at least one dev-profile QEMU smoke run, and consider retaining critical allocator frame/list checks in release.

10. **Clean up early boot diagnostics.** A minimal pre-`init_traps` early trap handler or early UART fault policy would make real-hardware bring-up failures visible instead of a PC-0 hang.
