# Independent AI audit (deepseek-v4-pro)

- date: 20260816-162430
- model: deepseek-v4-pro
- tool: scripts/ai_audit.py (external reviewer, not the author)

## Executive summary

The M0 boot chain is cohesively structured: assembly entry, BSS clearing, trap vector install, UART, logger, panic handler, and timer setup are separated cleanly. The trap frame ABI is documented and mostly matches between `.S` and `.rs`, the use of `volatile` plus MMIO `fence` is appropriate, and the double-panic guard is a good defensive measure.

However, I found one **critical** CSR instruction misuse that makes `irq_disable`/`irq_enable` effectively no-ops under normal ABI state, which breaks the timer interrupt path and the intended panic/halt interrupt suppression. I also found a trap frame size mismatch (288 vs 320 bytes) that could allow an invalid frame pointer to pass validation and later corrupt state. Several medium/low issues relate to future real-hardware portability and CI coverage.

All findings below are based on the source as provided.

---

## Findings (severity-ranked)

### CRITICAL

**1. `csrc`/`csrs` used with an immediate constant, but these are register-only pseudo-instructions — `irq_disable`/`irq_enable` are no-ops in practice**

- **File:** `kernel/src/arch/riscv64.rs`
  - `pub fn irq_disable()`
  - `pub fn irq_enable()`
- **File:** `kernel/src/entry.S`
  - `_start` sequence: `csrc sstatus, 2`

**Description**

The code uses:

```rust
asm!("csrc sstatus, {imm}", imm = const 2, options(nomem, nostack));
```

and similarly:

```rust
asm!("csrs sstatus, {imm}", imm = const 2, options(nomem, nostack));
```

`csrc` and `csrs` are RISC-V assembly pseudo-instructions for **register** forms:

- `csrc csr, rs` → `csrrc x0, csr, rs`
- `csrs csr, rs` → `csrrs x0, csr, rs`

The immediate-clear/set forms are `csrci` and `csrsi`, not `csrc`/`csrs`.

Because the operand `2` is interpreted as register `x2` (`sp`), and the stack pointer is 16-byte aligned in RISC-V ABI, **bit 1 of `sp` is always 0**. Therefore:

- `irq_disable` clears only bits that are set in `sp`, so it does **not** clear `sstatus.SIE` (bit 1).
- `irq_enable` sets only bits that are set in `sp`, so it does **not** set `sstatus.SIE`.

The same bug exists in `entry.S`:

```asm
csrc sstatus, 2   # intended to clear SIE, actually uses x2/sp
```

**Consequences**

- Timer interrupts are never enabled after `arch::irq_enable()`, so the heartbeat `uptime:` log never appears.
- `panic` and `halt` call `irq_disable()`, but it does not actually disable interrupts if they were enabled.
- The boot-time interrupt-disable in `_start` is also ineffective if the bootloader left `sstatus.SIE` set and `sp` doesn’t happen to have bit 1 set.

This currently passes CI because the smoke test only checks for `"M0: boot ok"` and absence of panic/trap, not correctness of the timer heartbeat.

**Fix**

Use the immediate CSR forms:

```rust
asm!("csrci sstatus, 2", options(nomem, nostack)); // clear SIE
asm!("csrsi sstatus, 2", options(nomem, nostack)); // set SIE
```

Or load `2` into a register and use `csrc`/`csrs`.

In `entry.S`, replace `csrc sstatus, 2` with:

```asm
csrci sstatus, 2
```

### HIGH

**2. Trap frame size mismatch: validation uses 288 bytes, assembly allocates/restores 320 bytes**

- **File:** `kernel/src/arch/riscv64.rs`
  - `const TRAP_FRAME_WORDS: usize = 36;`
  - `trap_handler` validation: `f + TRAP_FRAME_WORDS * 8 > top`
- **File:** `kernel/src/arch/riscv64.S`
  - `addi t6, t6, -320` at entry
  - `addi t0, t6, 320` in recovery

**Description**

The Rust side defines the trap frame as 36 words:

```rust
const TRAP_FRAME_WORDS: usize = 36; // 36 * 8 = 288 bytes
```

The assembly, however, reserves and restores a 320-byte region:

```asm
addi t6, t6, -320        # reserve
...
addi t0, t6, 320         # restore sscratch
```

The comment in `riscv64.S` acknowledges that 320 = 288 + 32 bytes of padding, but the Rust validation only checks:

```rust
if f < bottom || f + TRAP_FRAME_WORDS * 8 > top || !f.is_multiple_of(16)
```

This means the validator can accept a frame pointer that is valid for 288 bytes but whose full 320-byte allocation would exceed `_trap_stack_top`. A corrupt `sscratch` or a future bug could pass validation, and then the recovery path could set `sscratch` beyond the trap stack, leading to subsequent corruption.

**Fix**

Either:

- Define `TRAP_FRAME_WORDS = 40` and update the slice/dump/restore paths consistently, or
- Change the assembly to reserve exactly `TRAP_FRAME_WORDS * 8` bytes and use the same constant in the recovery `addi`.

Make the frame size a single named constant shared between Rust and assembly or at least keep the two numerically equal.

### MEDIUM

**3. Nested trap stack overflow can spill into the active boot stack**

- **File:** `kernel/src/arch/riscv64.rs`
  - `trap_handler`
- **File:** `kernel/src/arch/riscv64.S`
  - `addi sp, t6, -1024`

**Description**

The trap vector reserves a 320-byte frame, then sets the handler stack pointer to `frame_base - 1024`:

```asm
addi sp, t6, -1024
```

`trap_handler` validates only the frame pointer’s placement inside the trap stack:

```rust
if f < bottom || f + TRAP_FRAME_WORDS * 8 > top || !f.is_multiple_of(16)
```

It does **not** validate that the handler stack region `frame_base - 1024 .. frame_base` lies entirely within the trap stack.

With enough nested traps (e.g., repeated synchronous exceptions caused by a kernel bug, or later by malicious user input), `sp` can drop below `_trap_stack_bottom` and into the boot stack region. The boot stack is live for the interrupted context, so this can corrupt real kernel state. The comment says overflow would go into “内核保留区，不破坏内核数据,” but the boot stack is an active reserved region, not inert padding.

**Fix**

In `trap_handler`, also validate the intended handler stack pointer:

```rust
let handler_sp = f.checked_sub(1024).ok_or_else(halt);
if handler_sp < bottom || handler_sp + 1024 > top { halt(); }
```

Or redesign the trap-stack allocation to include guard space and a hard limit on nesting before the entry writes below the trap stack.

**4. Hardcoded UART base and divisor are not portable to real hardware**

- **File:** `kernel/src/uart.rs`
  - `const UART_BASE: usize = 0x1000_0000;`
  - `write_u8(UART_DLL, 0x0C);` / `write_u8(UART_DLM, 0x00);`
- **File:** `kernel/src/main.rs`
  - `kernel_main(hartid, fdt)` logs `fdt` but never uses it.

**Description**

The UART driver is fully hardcoded for QEMU `virt`:

- Base `0x1000_0000`
- Divisor `0x0C` for a 1.8432 MHz reference clock / 9600 baud

The FDT pointer is passed from OpenSBI via `a1` but only printed. On real hardware, the UART base/clock will almost certainly differ, causing no output or garbage. This is already noted in comments, but it is a medium-severity portability blocker for any physical deployment.

**Fix**

In M1, parse the FDT to discover the UART base address and clock, compute the divisor from the actual clock and desired baud rate, and store platform data rather than using hardcoded constants.

**5. SBI `set_timer` return value is ignored**

- **File:** `kernel/src/sbi.rs`
  - `lateout("a0") _`, `lateout("a1") _`
- **File:** `kernel/src/arch/riscv64.rs`
  - `enable_timer`
  - timer interrupt path in `trap_handler`

**Description**

`set_timer` discards both `a0` and `a1`:

```rust
lateout("a0") _,
lateout("a1") _,
```

Callers never check whether the SBI call succeeded. If the call fails, the deadline has already been advanced by `fetch_add`, but no next timer interrupt will be programmed. The tick then silently stops, which is difficult to diagnose.

**Fix**

Return the error code from `set_timer` and handle it:

```rust
pub fn set_timer(stime_value: usize) -> usize { ... }
```

In `enable_timer` and the interrupt handler, check the result and log/panic on failure.

### LOW

**6. Logger macros evaluate arguments even when the level is filtered**

- **File:** `kernel/src/logger.rs`
  - `log` function and `debug!`/`trace!` macros

**Description**

The module comment claims:

> 级别过滤发生在 `format_args!` 展开之前，被过滤的调用零格式化开销

But the macros expand to:

```rust
$crate::logger::log(Level::Debug, format_args!(...))
```

In Rust, function arguments are evaluated before the call, so `format_args!` is still evaluated, along with any argument expressions such as `crate::logger::tick()`. The `log` function later filters the level, but the work of evaluating arguments and constructing the `Arguments` value is already done.

This is not a correctness bug in the current code, but it can cause unwanted side effects or waste in performance-sensitive paths.

**Fix**

Guard the macro body with a level check before constructing `format_args!`, e.g.:

```rust
if $crate::logger::level() >= Level::Debug {
    $crate::logger::log(Level::Debug, format_args!(...))
}
```

**7. `__global_pointer$` placement is at the end of `.data`, not “偏前” as the comment claims**

- **File:** `kernel/linker.ld`

**Description**

The linker script places `__global_pointer$` after all of `*(.data*)` and `*(.sdata*)`:

```ld
.data : {
    *(.data*)
    *(.sdata*)
    . = ALIGN(16);
    __global_pointer$ = .;
}
```

The comment says this is “位置偏前可覆盖更多静态数据,” but it is actually the tail of the data section. RISC-V gp-relative addressing only covers ±2 KiB, so placing `__global_pointer$` at the end may reduce coverage for earlier data and prevent relaxation.

**Fix**

Place `__global_pointer$` at the midpoint of the small data region, or at least before the bulk of `.sdata`/`.data`, so more static data is within ±2 KiB.

**8. CI smoke test misses the timer non-functional state**

- **File:** `.github/workflows/ci.yml`
- **File:** `Makefile`

**Description**

The CI test greps only for:

- `"M0: boot ok"`
- absence of `"KERNEL PANIC"` / `"TRAP:"`

Because `irq_enable` is currently broken (see finding 1), the `uptime:` heartbeat never appears, but CI still passes. This allowed the critical interrupt-disable/enable bug to go unnoticed.

**Fix**

After the timer is intended to be enabled, assert at least one `uptime:` line appears in the log.

### INFO

**9. Linker script may not cover future orphan sections**

- **File:** `kernel/linker.ld`

**Description**

The linker script explicitly places:

- `.text*`, `.rodata*`, `.data*`, `.bss*`, `.stack`, `.trap_stack`, `.debug*`, `.riscv.attributes`
- Discards `.eh_frame`, `.comment`

But it does not mention possible future sections such as:

- `.got`, `.got.plt`
- `.init_array`, `.fini_array`
- `.tdata`, `.tbss`
- `.data.rel.ro`, etc.

The current bare-metal statically-linked Rust kernel likely does not generate these, so it builds fine. However, as the kernel grows or if certain compiler options are enabled, these could become orphan sections and cause link errors or misplacement.

**Fix**

Enable `--orphan-handling=error` or add explicit placement/discard rules for any sections that appear.

## What looks correct

The following aspects are well done and should not be changed carelessly:

- **Boot sequence:** `_start` → clear BSS → set stack → `kernel_main` is clear. The secondary hart parking before touching shared memory is correct.
- **BSS clearing range:** `[ _bss_start, _stack_top )` correctly includes boot stack but not trap stack.
- **Trap frame GPR indexing:** The assembly save/restore order matches the `gpr` constants in `riscv64.rs`.
- **Use of `volatile` plus MMIO `fence`:** UART register accesses are appropriately protected against compiler/hardware reordering.
- **Double-panic guard:** `PANICKING.swap(true)` prevents recursive panic spam.
- **Stack watermark:** Scanning from stack bottom for the first non-zero byte is a clever diagnostic, and using `read_volatile` byte reads avoids provenance issues.
- **Deadline-based timer programming:** The `TIMER_DEADLINE.fetch_add(TIMER_INTERVAL) + TIMER_INTERVAL` logic avoids cumulative drift, assuming interrupts are actually enabled.
- **Trap stack separated from boot stack:** The `NOLOAD` stack sections are correctly placed outside `_kernel_end` so M1 physical allocator can start at `_alloc_start`.

## Blind spots & suggestions for the next milestone (M1: trap handling)

1. **Per-hart trap stacks**  
   The current static `_trap_stack_top` and single `sscratch` are fine for one hart. M1 must allocate per-hart trap stacks and initialize `sscratch` for each hart.

2. **Interrupt-safe UART/logging**  
   The logger is explicitly not ISR-safe. Timer ISR currently avoids logging, which is good. Before enabling any ISR that logs, introduce a spinlock or per-CPU ring buffer, and document which contexts may log.

3. **User pointer validation before kernel access**  
   When user mode exists, `trap_handler` must not blindly dereference `stval` or user-provided addresses. Invalid user pointers must return errors, not panic/halt.

4. **Atomic ordering for multi-hart**  
   `Relaxed` is currently sufficient for single-core and timer-only writes, but will be insufficient when multiple harts share `TIMER_DEADLINE` or tick counts. Plan `Acquire/Release` or stronger ordering for shared state.

5. **SBI error handling**  
   Return and check SBI call errors, especially `set_timer`. A missed timer interrupt should be detected during M1 tests.

6. **Guard pages**  
   The linker script already mentions adding a guard page between `_kernel_end` and the boot stack. Implement this before MMU/paging to catch stack overflows early.

7. **Trap frame size constant**  
   Fix the 288 vs 320 mismatch immediately before adding more trap handling; otherwise all M1 frame-layout changes will be built on an inconsistent foundation.

8. **CI timer heartbeat assertion**  
   Once `irq_enable` is fixed, add a CI assertion for `uptime:` output to catch regressions in the timer path.

9. **FDT-based UART discovery**  
   M1 should parse the FDT to obtain UART base/clock and remove the hardcoded QEMU `virt` values before any real hardware bring-up.

10. **Nested trap stack bound checking**  
    As traps become more complex, add a hard nesting limit and validate the handler stack pointer in `trap_handler` before writing a new frame.
