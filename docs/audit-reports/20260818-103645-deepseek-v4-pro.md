# Independent AI audit (deepseek-v4-pro)

- date: 20260818-103645
- model: deepseek-v4-pro
- tool: scripts/ai_audit.py (external reviewer, not the author)

## Executive summary

The kernel is a solid foundation for a RISC-V microkernel: the boot sequence, trap frame protocol, cooperative/preemptive scheduler split, and IRQ-safe locking show careful design and several rounds of self-audit. However, this independent review found **one critical build/runtime defect** (the scheduler’s preemption selftest cannot pass with interrupts disabled, which is how it is invoked), **two memory-safety vulnerabilities in FDT parsing** (unbounded reserve-map reads and `from_utf8_unchecked` on arbitrary bootloader bytes), and **a static-array overflow risk when RAM exceeds 128 MiB**. Several smaller medium/low issues around alignment, diagnostics, and portability also remain.

None of the synchronized primitives or the trap entry/exit assembly showed immediate correctness problems; the `sscratch`/nested-trap protocol and frame/context dual-restore logic are particularly well considered.

## Findings (severity-ranked)

### CRITICAL

#### C1: Scheduler preemption selftest deadlocks/hangs because it runs with interrupts disabled
**File:** `kernel/src/main.rs` (call to `sched::self_test` before `arch::irq_enable`), `kernel/src/sched.rs` (`self_test`, step 3 and step 4)

**Description:**  
`kernel_main` calls `sched::self_test()` while `sstatus.SIE = 0` (interrupts disabled). The preemption test (`test_busy` and `test_prio_low`) relies on the timer tick (`crate::logger::tick()`) advancing, which only happens in the timer ISR. With interrupts disabled, `tick` remains `0`, and the busy threads loop forever. The main test thread yields into the busy thread and never regains control, so `self_test` never returns. CI (`make test`, boot smoke) would hang and eventually be killed by the 10 s timeout, never printing `"scheduler selftest ok"`. The comments in `self_test` state “tick 前进 >= 15” and “必被抢占至少一次”, confirming the test expects interrupts to be active, but they are not.

**Fix suggestion:**  
Split the scheduler selftest into two parts:
- cooperative-only tests (yield, exit, block/wake) that can run with interrupts disabled;
- preemption and priority-preemption tests that must run after `arch::irq_enable()` (or temporarily enable interrupts around only those tests, with careful state handling).

Alternatively, enable interrupts before running `sched::self_test` and ensure all other initialization that must happen with interrupts off is done first (though this changes boot ordering and may race with MMU/heap setup). The simplest robust fix is to move the preemption-specific test to a separate function called after `arch::irq_enable()`.

### HIGH

#### H1: FDT reserve-map parsing lacks bounds check → out-of-bounds reads from bootloader-controlled data
**File:** `kernel/src/fdt.rs`, `Fdt::parse` — reserve map loop

```rust
let mut off = self.off_rsvmap;
loop {
    let addr_hi = unsafe { be32(self.base as usize + off) };
    ...
    off += 16;
    ...
}
```

**Description:**  
The loop reads 16 bytes at `off` each iteration and terminates only when both address and size are zero. `off_rsvmap` is validated only as `< total`, not that `off + 12` remains within `total_size`. A malicious or corrupted FDT (bootloader influenced) can place a non-zero entry near the end of the buffer, causing the parser to read past the FDT into arbitrary memory. This is a memory-safety violation and information leak / crash vector.

**Fix suggestion:**  
Inside the loop, before each read, check:
```rust
if off.checked_add(16).map_or(true, |end| end > self.total_size) {
    break; // or return params
}
```
Use `checked_add` to avoid overflow. Also validate that `off_rsvmap` is a multiple of 8 (or at least 4) and within `total`.

#### H2: `from_utf8_unchecked` on FDT property names can trigger UB with non-UTF-8 input
**File:** `kernel/src/fdt.rs`, `Fdt::read_string`

```rust
let s = unsafe { core::str::from_utf8_unchecked(core::slice::from_raw_parts(start, len)) };
Some(s)
```

**Description:**  
FDT strings are arbitrary bytes. `from_utf8_unchecked` requires valid UTF-8; feeding it malformed bytes from a hostile/corrupted FDT is undefined behavior. This is a trivial crash/UB vector if the bootloader passes a crafted device tree.

**Fix suggestion:**  
Use `core::str::from_utf8(...).ok()?` and return `None` on invalid UTF-8. That safely rejects malformed names; comparisons to known names will then skip the property.

#### H3: Static `MAX_PAGES` (128 MiB) not enforced → heap/buddy metadata out-of-bounds write if RAM > 128 MiB
**Files:** `kernel/src/mem.rs` (`MAX_PAGES`, `PAGE_META`, `init`), `kernel/src/heap.rs` (`SLAB_PAGE_CLASS`)

**Description:**  
`MAX_PAGES` is a hard-coded `128*1024*1024 / PAGE_SIZE = 32768`. In `mem::init`, the actual page count `count` is computed from FDT-provided RAM size. `BuddyAllocator::init` only `debug_assert!(count <= MAX_PAGES)`, which disappears in release builds. If the board has more than 128 MiB of RAM (or a malicious FDT reports a larger size), `count` and `padded` can exceed `MAX_PAGES`, and the code writes past the end of `PAGE_META` (in `mem::init`) and `SLAB_PAGE_CLASS` (in `heap::slab_class_set`), causing memory corruption and undefined behavior.

**Fix suggestion:**  
In `mem::init`, after computing `count`, explicitly check:
```rust
if count > MAX_PAGES {
    panic!("RAM size exceeds metadata capacity; increase MAX_PAGES or use dynamic allocation");
}
```
Do the same check for `padded`. Ensure `count * PAGE_SIZE` matches the actual RAM range and reject absurd values.

### MEDIUM

#### M1: `mmu::init` assumes RAM start is 2 MiB aligned for superpage identity mapping
**File:** `kernel/src/mmu.rs`, `mmu::init` – the `while vaddr < ram_end` loop using `map_super`

**Description:**  
`map_super` writes a leaf PTE for the 2 MiB region containing `vaddr`. If `ram_start` from the FDT is not aligned to 2 MiB, the low 21 bits of the physical address are lost, resulting in a non-identity mapping and immediate page faults or silent corruption. QEMU’s default RAM start (0x8000_0000) is aligned, so this works in CI, but real hardware may place DRAM at a non-2 MiB-aligned address.

**Fix suggestion:**  
Before using superpages, assert that both `ram_start` and `ram_end` (or the region being mapped) are 2 MiB aligned. If not, fall back to 4 KiB page mapping for the unaligned edges, or set `ram_start` to the aligned boundary (changing how the kernel sees memory is more invasive). At minimum, add a runtime check that panics with a clear message if alignment is violated.

#### M2: `Fdt::new` uses `board::ram_end()` before board parameters are initialized
**File:** `kernel/src/fdt.rs`, `Fdt::new`; `kernel/src/main.rs` (order of `Fdt::new` vs `board::init_from_fdt`)

**Description:**  
`Fdt::new` validates that the FDT header fits within `crate::board::ram_end()`. At that point `board::init_from_fdt` has not yet run, so `ram_end()` returns the default 128 MiB. If the actual FDT location is beyond the default RAM (e.g., on a platform with more memory and FDT placed high), parsing is skipped even though the FDT is valid. This is a functional bug, not a memory-safety issue.

**Fix suggestion:**  
Reorder initialization: parse the FDT header validity without depending on `board::ram_end` (e.g., use a conservative absolute check or just attempt to read the header with proper pointer checks), then call `board::init_from_fdt` early, and afterwards use board values for subsequent initialization. Or make the FDT check independent of board RAM end by ensuring the pointer is within a plausible physical range (e.g., using the kernel’s own `_kernel_end` as a lower bound and the maximum physical address from the platform description).

#### M3: `sched::pick_next` fallback to current when no ready candidate may cause exiting thread to halt the system if idle is not in ready queue
**File:** `kernel/src/sched.rs`, `Scheduler::pick_next` fallback `self.current`; `exit` path

**Description:**  
The fallback `self.current` is returned when no ready/candidate thread exists. In `exit()`, the current thread is marked `Exited` and then `pick_next` is called. If the ready queues are empty and `self.current` is the exiting thread (possible if idle was never enqueued due to no prior yield/preemption), the scheduler selects the exiting thread again. `exit` will then resume, restore IRQs, and call `arch::halt()`, even though the idle thread (which should run forever) exists. This may be rare because idle typically gets enqueued when another thread runs, but it is a fragility that could become a real bug during early boot or unusual scheduling sequences.

**Fix suggestion:**  
Always ensure the idle thread is in the ready queue when not running (e.g., enqueue idle in `Scheduler::init` and update state accordingly), or make `pick_next` return idle explicitly when no other candidate exists and the caller is not idle. Add a debug assert that `next` is not the exiting thread.

### LOW

#### L1: UART baud-rate divisor hardcoded; does not match many platforms
**File:** `kernel/src/uart.rs`, `init` (divisor values `0x0C`, `0x00`)

**Description:**  
The driver programs a divisor of 12 (9600 baud at 1.8432 MHz reference) but the comment states 115200 expected. On real hardware with a different reference clock, output will be corrupted or absent. The FDT parser already extracts `timebase-frequency`; the UART clock should be read and used to compute the divisor.

**Fix suggestion:**  
Extend `BoardParams` with UART clock frequency, parse it from the FDT (or use a platform-defined value), and compute the divisor at init time. Fallback to a sane default for QEMU.

---

#### L2: `panic::stack_watermark` can under-report usage if deepest used byte is zero
**File:** `kernel/src/panic.rs`, `stack_watermark`

**Description:**  
The watermark scan stops at the first non-zero byte from the bottom. If the actual deepest stack usage wrote only zeros (e.g., a large zeroed buffer), the watermark will be overestimated (lower than actual depth), leading to misleading diagnostics. This is a diagnostic quality issue, not a safety problem.

**Fix suggestion:**  
Scan from both directions or use a pattern fill during init (e.g., write a known pattern during BSS clearing and look for the first byte not matching the pattern). However, BSS clearing writes zeros; changing the initialization pattern would be required. Alternatively, document the limitation clearly.

---

#### L3: Logger is not reentrant and relies on “no logging in ISR” discipline (documented)
**File:** `kernel/src/logger.rs` module docs

**Description:**  
The logger is lock-free and writes directly to UART. Any future ISR or interrupt-context log (e.g., debug output) would interleave with main-context output, corrupting the stream. The current discipline is documented and enforced by code review, but there is no compile-time or runtime guard. This is an intentional design constraint, but worth noting as a future hazard.

**Fix suggestion:**  
When multi-context logging becomes necessary, implement an IRQ-safe lock or an ISR buffer that is flushed by a non-interrupt context. For now, keep the discipline but add a debug assertion or explicit comment at all call sites.

## What looks correct

- **Trap entry/exit assembly** (`riscv64.S`): The `sscratch` swap, nested-trap detection, frame validation, stack-reserve check, and restoration of `sscratch` to trap stack top are correct and well documented. The comments accurately describe the protocol.
- **`frame_restore` and `context_switch`** are properly separated and used according to the `ctx_valid`/`frame_valid` invariant. The dual-restore mechanism is sound under the current single-CPU, interrupts-disabled-during-switch discipline.
- **Buddy allocator** (`mem.rs`): The coalescing, alignment checks, reserved-region carving, and double-free/interior-page rejection are carefully implemented. The `PAGE_META` `static mut` access via raw pointers is disciplined and avoids aliasing UB.
- **Waking/blocking protocol** in `sync.rs` and `sched.rs`: The `woken` flag, unconditional wake, and `block_current`’s consumption of the flag correctly handle lost-wake scenarios. The `Condvar::wait` manually releases the mutex and forgets the guard to prevent double-unlock.
- **IRQ-safe spinlocks** (`sync.rs`): The `lock`/`drop` pair saves/restores `SIE` correctly, preventing preemption during critical sections. This is necessary for allocator and scheduler safety.
- **Boot arbitration in `entry.S`** with `BOOT_LOCK` in `.data` and `amoswap` handles multiple harts correctly.
- **Linker script** reserves stacks and trap stack outside the allocator region, clears them in BSS, and places `_alloc_start` after them—good hygiene.
- **CI and Makefile** align with the toolchain and use sensible checks; the `-smp` test appropriately verifies only one boot hart proceeds.

## Blind spots & suggestions for next milestone (M1: trap handling)

1. **Run selftests with interrupts enabled for preemption tests** (fix C1). This is a showstopper for CI correctness.
2. **Harden FDT parser**: add bounds checks and UTF-8 validation; consider fuzzing the parser with malformed FDTs (this may be a good CI task).
3. **Make `MAX_PAGES` dynamic or enforce limit**: either use a `const` based on actual platform limits or allocate metadata at runtime with `Vec` (requires alloc before buddy init, which may be problematic; a fixed generous size with a runtime check is simpler).
4. **Validate RAM base/size alignment and ranges**: ensure RAM start/size are sane, aligned, and do not overlap with kernel/reserved areas.
5. **Add guard pages and page permission splitting (already planned M1.5)**: valuable for catching stack overflows and enforcing W^X.
6. **Implement per-hart trap stacks (D7)**: currently a single global trap stack; even though only one hart runs, the design is ready for per-hart via `sscratch`, but the stack itself is global. Prepare for multi-hart bring-up.
7. **Consider enabling interrupts earlier in a controlled way** to allow timer-based selftests while still protecting initialization. A phased boot (e.g., cooperative-only init, then enable interrupts, then run interrupt-dependent selftests) would be more robust.
8. **Add a simple UART clock configuration from FDT** (M1.5) to avoid hard-coded divisors.
9. **Add a `debug` build variant that runs with overflow checks and extra assertions** in CI to catch issues like `MAX_PAGES` overflow early.
10. **Document the “no logging in ISR” rule more strongly**: perhaps add a lint or a runtime token that panics if called from interrupt context (by checking a flag set in `trap_handler`).

These findings should be addressed before proceeding to M1.5 stabilization and especially before enabling multiple harts or supporting user processes.
